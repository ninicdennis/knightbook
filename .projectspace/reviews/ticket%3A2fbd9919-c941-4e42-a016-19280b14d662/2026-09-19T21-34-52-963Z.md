# Uninitialized folder guidance and one-click setup

## Intended outcome
Opening a folder with no project records explains what will happen and lets the user set it up in the app, without an AI tool and without spending any AI credit.

## Acceptance criteria
- The screen says what a Projectspace project is, and that setup adds only a .projectspace folder and changes no existing file.
- A Set up this folder button initializes it through the same core operation MCP uses, and the project opens straight away.
- If a README.md or a docs folder exists, offer to include them in place. The user confirms; nothing is included silently.
- Never write into an existing .projectspace that holds unrelated files. Say why and change nothing.
- Explains how to connect an AI client afterwards, with the copy-configuration action beside it.
- Failures are specific: permission denied, read-only folder, and so on.

## Notes
Today the screen tells the user to use an AI tool, which costs credit just to get an empty project. The AI-driven onboarding for an existing application stays available but becomes optional.

## Handoff
**What changed:** Choosing a folder with no project records now opens a Set up this folder screen instead of telling the user to use an AI tool. It explains what a project is and that setup adds only a .projectspace folder and changes no existing file, says nothing has been written yet, and offers a project name (defaults to the folder name). If README.md or a docs folder exist they are offered as ticked checkboxes; only what stays ticked is included, in place. The Set up this folder button initializes through the same core operation MCP uses (initializeProject, includeDocuments) and the project opens straight away. A Copy MCP configuration button for that folder sits on the same screen. Failures are specific: permission denied, read-only location, disk full, folder gone, an existing .projectspace holding unrelated files, an already-existing project. If the project is set up but a document could not be included, it opens anyway and says so. The main process only sets up the one folder the user just picked in the dialog, so the renderer cannot make it write elsewhere.
**How it was checked:** pnpm check green (desktop 101 tests: 20 for main-process setup against real temp folders, 12 for the screen). Tests confirm existing files are byte-identical after setup and that only .projectspace is added, that an unrelated .projectspace is refused with nothing changed, and that the renderer cannot widen the include list (I broke that filter on purpose and the test failed). The screen was viewed in real Chromium via the preview harness, which found and fixed a clipped title on a short window. The packaged build launches cleanly with a throwaway profile.
**Not verified:** the packaged window itself was not driven or screenshotted; a real folder was not set up through the packaged app; a genuine permission-denied or read-only failure was not produced (only unit-tested from error codes, since Windows cannot easily simulate them); light mode; macOS and Linux.
**For you to check:** in the app, open the drawer, choose Open folder, and pick a folder with no .projectspace (a scratch copy of a repo is ideal). Check the wording, that ticking and unticking README.md and docs does what it says, that the project opens with a board and its documents listed, and that your existing files are untouched. Note one choice I made that you may want flipped: README.md and docs start ticked, so setting up includes them unless you untick them.
