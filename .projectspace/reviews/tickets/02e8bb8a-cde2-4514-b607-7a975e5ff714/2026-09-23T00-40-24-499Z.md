# Flag a completion block that was edited outside the app

## Intended outcome
A Done ticket whose completion record was edited by hand is not presented as an attributable user decision.

## Acceptance criteria
- A completion whose recorded fields could not have been produced by either write path is reported as unattributed, or with an equivalent distinct signal.
- At minimum, `decision_source: direct_user_action` together with `recorded_by: agent` is treated as untrustworthy: a direct in-app action is recorded by the user by definition.
- The app and MCP agree on what they show for such a ticket.
- Decide and write down whether a stronger check is wanted (for example a fingerprint over the completion fields), including the argument for not doing so.
- `completion.ts`'s docblock is corrected to describe what is actually detected.

## Notes
Found running the specification validation scenario (ticket 2e4a254f), step 9, which asks explicitly for "handling of externally edited completion fields under the selected design".

Measured, both cases on the same ticket:
- completion block deleted entirely, `status: done` left behind -> `completion_unattributed=true`. Correct.
- block left in place but edited to `decision_source: direct_user_action` + `recorded_by: agent` -> `completion_unattributed=false`, and `ticket_list` returns the forged block as a normal completion.

`isUnattributedCompletion` (packages/core/src/completion.ts:92-94) is `status === 'done' && completion === undefined`, so only the first case can ever be caught.

This is not claimed to be a security boundary — the module already says a forged assertion is outside what a local design can prevent, and that is a reasonable position. The gap is narrower: the same docblock says completion recorded outside this path "is shown as unattributed", and that sentence is only true when the block is missing. Either the check or the sentence should change. The contradictory pair above is cheap to detect and is the obvious first case.

## Handoff
**What changed:** (uncommitted, branch `feature/easy-wins`)
- `isUnattributedCompletion` in `packages/core/src/completion.ts` now also flags a completion whose `decision_source` and `recorded_by` contradict each other. The write path only ever produces `direct_user_action` + `user` (the app) and `reported_user_instruction` + `agent` (MCP), so either other pairing — including the measured case, a direct action recorded by an agent — was written by hand.
- The app and MCP now agree because both call that one check. The desktop view in `apps/desktop/src/main/ticket-view.ts` had its own copy that only looked for a missing block. Both surfaces also withhold the forged block (`completion: null`), so the card cannot say "Accepted by you" from it.
- **Decision on a stronger check:** a block hand-edited into one of the two producible shapes is still not detected, on purpose. A fingerprint over the fields could be recomputed by anything that can edit the file, so it would claim tamper evidence this local design cannot back. This is written in the docblock of `isUnattributedCompletion`, and the module docblock's sentence now says what is actually caught. There is also a dated follow-up in `docs/validation-scenario-results.md` step 9.
- The notice text now reads "…with no recorded decision from the app or an AI tool…", and the skill line on `completion_unattributed` is updated.

**How it was checked:**
- New core `completion-provenance.test.ts` completes real tickets through both paths, then edits the file into each of the four pairings: two are trusted, two are flagged, and one test pins the deliberate blind spot.
- New MCP `completion-provenance.test.ts` checks that `ticket_read` and `ticket_list` report `completion_unattributed: true` with `completion: null` for the forged file.
- New desktop `main/ticket-view.test.ts` checks that the board view reads the same file the same way.
- Suites: core 185, MCP 40, desktop 266 plus the existing skip. Typecheck is clean in all three.
- All 31 Done tickets on this board were checked: every one uses a producible pairing, so none of them changes.

**Not verified:** the packaged app has not been rebuilt, and the notice was not viewed in the running app.

**For you to check:** in a scratch project, edit a Done ticket's `decision_source` to `direct_user_action` while leaving `recorded_by: agent`. Refresh, and confirm the card shows Unattributed rather than "Accepted by you"; a client's `ticket_read` should say the same.
