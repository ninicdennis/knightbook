# A line-ending change alone marks a reviewed record "changed since review"

## Intended outcome
Converting a ticket or document between LF and CRLF, and making no other change, leaves its review status as Reviewed. Users do not have to configure anything in their own project for this to hold.

## Problem
Found on 2026-09-24. Ticket 7ae60785 ("Copy the MCP configuration in the format of Claude, Codex, or OpenCode") showed "Changed since review" although Git showed no change to it.

- The ticket was created and reviewed while the file had LF line endings. The review recorded `reviewed_revision: 629f96b8…`.
- It was committed in `99eee24`. Git for Windows sets `core.autocrlf=true` by default, and it is set on this machine, so the next checkout rewrote the file on disk with CRLF. Git stores LF (`git ls-files --eol` reports `i/lf w/crlf`), so `git status` and `git diff` show nothing.
- `reviewStatus` compares raw bytes first: the CRLF file hashes to `4dee3e1b…`, not `629f96b8…`.
- The fallback, `contentFingerprint`, does not absorb the difference either. `parseRecord` keeps `\r` in the body, and the fingerprint splits blocks on `\n{2,}`, which never matches `\r\n\r\n`. The whole CRLF body becomes one block and the paragraph breaks are lost, so the fingerprint differs as well.

Converting the file back to LF gives an exact match on both revision and fingerprint. Six Done tickets are affected the same way: 2765e314, 62fa4846, 85d4faf9, 94a24b34, 9ca4698b, 9fe82d5a. Most other reviews match only because they were recorded after a checkout had already made their files CRLF.

This affects any Windows user whose `.projectspace` is in Git, not only this repository.

## Acceptance criteria
- `contentFingerprint` gives the same result for LF and CRLF versions of the same content.
- The quick "unchanged" check in review status treats content that differs only in line endings as unchanged.
- The revision used for write conflicts stays byte-exact. A file rewritten on disk still produces a conflict before any write overwrites it.
- Existing reviews keep working with no migration step for users. Snapshots whose stored fingerprint was computed from CRLF bytes, and those computed from LF bytes, both compare correctly against current content in either line ending. Recomputing the fingerprint from the stored snapshot body is one way to do it.
- A real change still shows as changed: a merged paragraph, an edited acceptance criterion, or changed non-bookkeeping frontmatter, in either line ending.
- Unit tests cover: an LF review with CRLF current content, a CRLF review with LF current content, mixed line endings, and a real change combined with a line-ending change.
- The seven tickets listed above show Reviewed again without being re-reviewed or edited.
- The decision is recorded in the technical design (section 7) as a numbered, dated decision.

## Notes
- No per-project setup. A `.gitattributes` rule such as `.projectspace/** text eol=lf` would fix it only for projects that add it, which most users would not know to do. This repository may still add one for its own consistency, but the fix must not depend on it.
- The review changes diff (`review-changes.ts`, ticket 5be60610) already normalises line endings for display. Review status should agree with what that diff shows.
- `frontmatter.ts` already accepts both line endings when parsing and keeps the file's own style when writing. That behaviour does not need to change.

## Handoff
**What changed:** `packages/core/src/review.ts`: `contentFingerprint` normalises CRLF and lone CR to LF before parsing. A new exported `unchangedSinceReview(snapshot, current)` is the one test both `reviewStatus` and the changes view (`review-changes.ts`, `countsForReview`) now use: exact bytes, then the LF form of the current file against the reviewed revision or the snapshot's retained source, then the fingerprint against both the stored one and one recomputed from the snapshot source. The recomputation is what recovers reviews stored before the fix. `write.ts` and the raw revision are untouched, so write conflicts stay byte-exact. Decision recorded as D-025 in the spec's decision list and in technical design section 7 ("Line endings").

**How it was checked:** `pnpm --filter @knightbook/core test`: 244 passed, including six new tests in `review.test.ts` (LF and CRLF and mixed fingerprints, a merged paragraph in CRLF, an LF review read as CRLF, a CRLF review read as LF, real changes combined with a line-ending change, and a hand-written CRLF snapshot whose stored fingerprint no longer matches) and one in `review-changes.test.ts` (line-ending note shown, `substantive` false). Core typecheck and Prettier clean. Ran review status over this repository's real tickets before and after: tickets reporting "changed since review" went from 57 to 35.

**Not verified:** The full `pnpm check` for this ticket alone (it runs at the end of this batch). Not checked in the running app, which still uses the older build until rebuilt.

**Differs from the acceptance criteria:** Five of the seven listed tickets now report Reviewed (7ae60785, 2765e314, 62fa4846, 94a24b34, 9ca4698b). Two still report changed, correctly: 85d4faf9 and 9fe82d5a had `related_documents` rewritten after their review (`docs/ui-ux-design-direction.md` to `docs/research/…`, `docs/release-automation.md` to `docs/proposals/…`) when the docs were reorganised. That is a substantive frontmatter change, not line endings, so the fix does not hide it. Re-review them in the app if the path change is fine.
