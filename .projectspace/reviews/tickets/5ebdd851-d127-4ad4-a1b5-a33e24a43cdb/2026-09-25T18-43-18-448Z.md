# pack:dir deletes most of release/win-unpacked when the packaged app is running

## Intended outcome
Running `pnpm pack:dir` while the packaged Knightbook is open either refuses up front with a clear message, or leaves the running installation intact, instead of half-deleting it.

## Acceptance criteria
- With `release/win-unpacked/Knightbook.exe` running, `pnpm pack:dir` stops before touching `release/win-unpacked` and says the app is running from there and must be closed, or it packages somewhere that does not disturb the running copy.
- A packaging failure never leaves `release/win-unpacked` with some files deleted and the locked ones still in place.
- The MCP runtime a client is configured to use (`release/win-unpacked/resources/mcp`) is never removed as a side effect of a failed pack.
- Covered by a test or a documented manual check on Windows.

## Notes
Observed on 2026-09-25 while working the Windows icon ticket (a29754ad). With the user's packaged app open, `pnpm pack:dir` ran electron-builder, which began cleaning `release/win-unpacked`, deleted everything that was not locked (locales, `.pak` files, `icudtl.dat`, `resources/mcp`, `resources/skills`, and more), then failed with `EPERM: operation not permitted, unlink ... d3dcompiler_47.dll`. Only `Knightbook.exe`, a few DLLs and `app.asar` survived because they were in use.

The folder was put back by copying the missing files from a fresh package built into a scratch folder, without overwriting the locked ones, so the running app's own exe and `app.asar` are still the older build. A clean `pnpm pack:dir` after closing the app makes it consistent again.

`scripts/stage-mcp-runtime.mjs` already handles a locked MCP runtime safely; this is the electron-builder output step, which has no such guard.

## Handoff
**What changed:** New `apps/desktop/scripts/release-lock-guard.mjs`, run first in the desktop `pack:dir` script (`node scripts/release-lock-guard.mjs && pnpm build && electron-builder --dir`), so it refuses before anything is built or cleaned. On Windows it opens every file under `release/win-unpacked` for writing without truncating; a running exe, a loaded DLL or a file the app holds refuses that, and the pack stops with the first five held paths and what to close. On macOS and Linux it does nothing, since a running file can be deleted there. README's Packaging section says so.

**Why this probe:** Tried first in a scratch folder: renaming the folder succeeds on Windows even with an exe inside running, so it cannot detect the lock. Opening for `r+` fails with `EBUSY` while it runs, succeeds after it exits, and leaves the modification time unchanged.

**How it was checked:** `scripts/release-lock-guard.test.mjs`: no package, an idle package, macOS/Linux skip, and on Windows a copied Node runtime run from `resources/mcp` inside a fake package (refused, named, file untouched). Against the real folder on this machine, with the packaged Knightbook open (four `Knightbook.exe` processes from `release/win-unpacked`): the guard refused, listing the `.pak` files and DLLs, and `pnpm --filter @knightbook/desktop pack:dir` exited 1 with the folder listing identical before and after. Full `pnpm check` passes.

**Not verified:** A successful `pack:dir` after closing the app. I did not close your running Knightbook to try it, so packaging tests ran in their skip-without-package mode. The guard is a check before electron-builder, not a transaction: a file that becomes locked in the seconds between the check and electron-builder's cleanup would still hit the old failure. The root `pnpm pack:dir` runs `build:mcp` before reaching the guard; that writes only `packages/mcp/dist`.

**For you to check:** With Knightbook open, run `pnpm pack:dir` and confirm it refuses with the message and the app keeps working. Then close it and confirm `pnpm pack:dir` packages normally.
