# Edit plans in the app

## Intended outcome
From the Plans pane the user can create a plan, add, rename and reorder its phases, and attach or detach tickets, without asking an AI or opening the file.

## Acceptance criteria
- Create a plan from a title; add a phase; rename, reorder and remove phases, keeping each phase's id so its tickets stay attached.
- Attach an existing ticket to a phase by choosing it from the board's tickets, and detach it. Neither changes the ticket's status, dependencies or backlog order.
- Every write goes through a new host operation that carries the plan revision the window read. A stale write is refused and the pane reloads and says so, as the board does for moves.
- Validation stays in `packages/core` (`createPlan`, `updatePlan`); the host calls it rather than re-implementing it.
- Keyboard reachable, with accessible names, in both colour schemes and at a narrow width.

## Notes
Split out of "Add local Plans with phases, linked tickets, and progress" (93e45332) on 2026-09-24. The user chose a first slice that reads plans in the app and writes them through MCP or the plan's file (decision D-022). This ticket is the in-app editing that slice left out. The app has no in-app text editing yet, so editing the plan's Markdown body can stay with **Edit externally**.

## Handoff
**What changed:** Two new contract operations, in `shared/plans-contract.ts` and the preload:
- `createPlan(title)`.
- `setPlanPhases(planId, phases, revision)`, which sends the whole phase list. `PlanView` now carries its `revision`.

The host (`main/documents/plan-edit-ipc.ts`) checks only the shape of what the window sent: a plan id that is a UUID, text titles, and ticket ids. It then calls core's `createPlan` and `updatePlan`, the functions MCP uses.

In the Plans pane:
- **New plan** is in the list heading and on the empty state.
- **Add phase** is under the phases.
- Each phase's menu has Rename…, Move up/down and Remove phase…. Removing a phase that holds tickets asks first and says the tickets are unchanged.
- Each phase has an "Attach a ticket…" field listing the board's active tickets not already in that phase.
- Each ticket row has a detach ×, including a row whose ticket is missing.

Existing phases keep their ids. Scope and value are sent back as they were read. On `revision_conflict` the pane reloads and says "That plan changed somewhere else…".

`PlanDetail`'s phase rendering moved into `PlanPhase.tsx`. The preview stub edits in memory. The decision is D-039; the user guide and README are updated.

**How it was checked:**
- `pnpm check` passes.
- `plan-edit.test.ts` (12 tests, on real files) covers:
  - creating a plan;
  - add, rename, reorder and remove, keeping ids and tickets, including removing the first phase;
  - attach and detach, with the ticket file byte-identical and a three-ticket manual backlog order unchanged;
  - a stale revision refused as `revision_conflict` with the file unchanged;
  - a bad plan id refused;
  - a duplicate ticket refused by core;
  - an empty title writing nothing.
- `PlanEditing.test.tsx` (12 tests) covers:
  - each UI action, and the exact phase list and revision it sends;
  - the conflict reload and its message;
  - Tab reaching the phase menu and the attach field.
- The verifier found nothing uncovered. Its weak spots (id loss on remove, backlog order with one ticket, the empty-title write, Tab reachability) have been closed.
- Layout pass in the preview at 800px light and 1600px dark: attaching a ticket and adding a phase worked against the stub.

**Not verified:**
- Not run in the packaged app against a real project, so the IPC wiring is checked by reading, not by running it.
- There is no keyboard test for New plan, Add phase, Detach or the removal confirmation beyond their accessible names.

**For you to check:**
1. In the app, create a plan, add two phases, attach and detach tickets, rename and reorder, then open the plan file.
2. Check that phase ids stayed the same and no ticket file changed.
3. Edit the plan through MCP while the pane is open, then make a change in the pane. The pane should refuse it and reload.
