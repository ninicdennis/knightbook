# Show in-project images

## Intended outcome
An image stored inside the project, such as the logo at the top of `README.md`, renders in the Documents view and in ticket bodies. Opening a document still cannot make the app reach the network or read files outside the project.

## Acceptance criteria
- Both Markdown `![alt](path)` and a raw HTML `<img src="…">` with a relative path are resolved against the file they appear in, the same way links are.
- The host loads the image only after checking that it is inside the project boundary (real path, links resolved), is PNG, JPEG, GIF or WebP by content and not only by extension, and is under a stated size cap. The renderer receives a data URL, never a file path or `file:` URL.
- SVG stays blocked, because it can carry scripts. Remote (`http`, `https`, protocol-relative) and `data:` images stay blocked as they are today.
- An image that is missing, outside the project, of an unsupported type, or too large keeps a visible placeholder that says which, rather than disappearing or rendering as a broken image.
- Loading an image changes nothing on disk and never counts as reviewing the document.
- The rule "images are not fetched" is revised in AGENTS.md, technical design section 1, and `docs/using-knightbook.md` in the same change, and `markdown.test.tsx` covers every allowed and refused case.

## Notes
Found on 2026-09-24 while verifying the README rewrite (1924aa96): the README logo does not render in the app. That is by design today. `renderer.image` in `apps/desktop/src/renderer/markdown.ts` replaces every image with an `[image: …]` placeholder, so a document cannot cause a request or a file read just by being opened. The README ticket noted this separately and said the prose rewrite must not broaden image loading on its own.

This loosens a documented security boundary on purpose, which is why it is its own ticket. Resolving and validating paths should reuse the link-resolution checks rather than adding a second implementation.

## Verification
Unit-test the host check for an in-project PNG, a path that escapes the project, a symlink out of the project, an SVG, a file renamed to `.png` that is not one, and one over the size cap. Open `README.md` in the app and confirm the logo renders. Confirm a remote image in a test document stays blocked with no network request.

## Handoff
**What changed:**
- Core: `readProjectImage` (`packages/core/src/documents/images.ts`) checks the path, refuses `.projectspace/`, caps the size at 5 MB and decides the type from the first bytes (PNG, JPEG, GIF, WebP; never SVG). The boundary check was pulled out of `links.ts` as `resolveContentPath` and is shared by links and images, so there is one implementation.
- Host: `image:read` (`main/documents/image-ipc.ts`) returns a data URL or `{ reason, message }`; contract op `readProjectImage`.
- Renderer: every image, Markdown or raw `<img>` (any case), becomes an inert placeholder while rendering (`markdown-images.ts`, on an inert `DOMParser` document, before DOMPurify). `classifyLink` moved to `link-target.ts` so links and images resolve the same way. DOMPurify now also forbids `img`, `picture`, `source`, `video` and `audio`. `useProjectImages` asks the host for each in-project placeholder and swaps in an `<img>` with the data URL (numeric width and height kept, never wider than the text), or rewrites the placeholder to say why. Remote, `//`, `data:`, `file:`, absolute and escaping sources are never sent to the host. `MarkdownBody` now takes `rootPath` (documents, ticket bodies and plans).
- Docs: the rule is revised in AGENTS.md, technical design (Following links section, in section 1), `docs/using-knightbook.md`, and decision D-034 in the spec.

**How it was checked:**
- `pnpm check` passes; `pnpm build:mcp` rebuilt.
- Core `images.test.ts` (9): PNG, JPEG, GIF, WebP read; SVG and SVG-renamed-to-.png refused; `../` and drive-letter refused; symlink (junction) out of the project refused; over the cap refused with its size; missing, a folder, and `.projectspace/` refused; file mtime and every `.projectspace` file's contents unchanged after a read.
- Host `image-ipc.test.ts` (2, real files): the window gets `data:image/png;base64,…` with no path or `file:` in it, and refusals pass through with reason and message.
- `markdown.test.tsx` "images" (8): Markdown and raw images resolve from their own file, including from a ticket file; width sanitised; http, https and `//` stay notes; `data:`, `file:`, absolute and escaping paths stay notes; SVG is left to the host; uppercase `<IMG>` converted; no `<img>` survives rendering.
- `Images.test.tsx` (6): the logo shows from the host's data URL; placeholders say why for unsupported type, missing, outside the project, too large, and a failed read; the remote image is never requested; no review is recorded; an image in a ticket body resolves from the ticket file and shows.
- On the real repo, core read `docs/assets/knightbook-logo.png` as `image/png`, 568,276 bytes.
- Verifier: 2 covered, 3.5 weakly covered, 0.5 not a code criterion. Its gaps were then closed: the IPC data-URL test, the missing refusal reasons in the window, the ticket-body test, and the contents comparison.

**Not verified:**
- README.md was not opened in the running Electron app. Computer use cannot drive a development Electron window, and packaging was not repeated. The CSP (`img-src 'self' data:`) already allows data URLs, but that was read, not observed.
- No network capture was taken to show a remote image makes no request; that rests on the placeholder never being an `<img>` and on DOMPurify forbidding `img`.
- The symlink test returns early without asserting when the machine cannot create a junction, the same pattern as the existing link test; on this machine it ran.
- The per-reason refusal cases (missing, symlink, too large, fake PNG) are tested in core's `images.test.ts`, not in `markdown.test.tsx`, because the renderer cannot know them.

**For you to check:**
- Rebuild or run the app, open `README.md` under Documents, and confirm the logo shows at 192 px wide.
- Add `![x](https://example.com/x.png)` to a scratch document and confirm it shows "remote images are not loaded".
