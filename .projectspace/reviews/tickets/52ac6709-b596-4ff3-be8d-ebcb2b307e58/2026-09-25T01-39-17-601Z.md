# Open a ticket's file in the editor

## Intended outcome
From an open ticket, the user can open its canonical Markdown file in their own editor, which is the handoff documents already have and tickets do not.

## Acceptance criteria
- A host operation opens `.projectspace/tickets/<id>.md` in whatever the operating system associates with Markdown, mirroring `document:openExternally` in `apps/desktop/src/main/documents-ipc.ts`.
- The renderer sends a ticket id and never receives or sends an absolute path. The host reads the ticket first to prove it exists and belongs to this project, then resolves the file through the validated project boundary.
- A ticket that cannot be read, an unknown id, a non-string argument, and anything resolving outside the project root are all refused with a message, through the same `guard` wrapper the other handlers use.
- When the shell reports it could not open the file, the app says so. Nothing may look like it worked.
- The control appears in the ticket detail dialog without crowding the action bar. That row already carries five controls and its own comment says words were dropped for icons to keep them on one line; this is not a decision about the work, so it belongs with the ticket's metadata rather than among Review and Accept.
- Coming back to the window after an external edit refreshes the ticket through the existing focus refresh, and an edit made outside the app never marks the ticket reviewed or accepted.

## Notes
Technical design section 10 accepts the external editor as the fallback while the formatted editor is blocked, which is why documents have this and why the same reasoning applies to tickets. The blocked editor is ticket `b217a95f-dc62-4319-b3a1-5c649fe183d9`.

A ticket body is written mostly by an AI and is the longest text in the project, but the only way to correct a line of it today is to find the file by its UUID in the reserved folder. The document handler at `documents-ipc.ts:166` is small and is the model to copy, including its comment about why the path is resolved in the host.

Reading a ticket through core also refuses a record with conflict markers or an unsupported schema, so a broken ticket reports the problem rather than opening a file the app will not itself load. Decide deliberately whether that is the behaviour wanted here, since a broken record is exactly the one a person most wants to open by hand. Say which was chosen and why.

## Verification
Test the handler for a good id, an unknown id, a non-string argument, and an id shaped to escape the project folder. Then open a ticket in the app, use the control, and confirm the right file opens. Edit and save it outside, return to the window, and confirm the board shows the change and the review state is unchanged. Run `pnpm check`.

## Handoff
**What changed:**
- New contract operation `openTicketExternally(rootPath, id)` on IPC channel `ticket:openExternally`, handled in `src/main/ticket-file-ipc.ts`. It lives in its own file because `ipc.ts` is over 300 lines.
- `src/main/ticket-file.ts` resolves the path:
  - It accepts only a plain id: letters, digits, `.`, `_` and `-`, with no separators and no `..`.
  - It builds `.projectspace/tickets/<id>.md`, checks the result sits directly in the tickets folder, and reads it with core's `readRecord`, which proves the file exists and its real path is inside the project.
  - The result goes to `shell.openPath`. A failure `openPath` reports comes back through `guard` as "Your editor could not open the ticket file: …".
- `TicketFileRow` shows a quiet **Edit externally** control under the badges in the ticket header, matching the documents label, with any failure shown inline.

**Decision on broken records:** the file is read as raw text, not parsed as a ticket, so a record with conflict markers or an unsupported schema still opens. That is the record a person most needs to fix by hand. Existence and containment are still proven. This is recorded in technical design section 10, "Opening a ticket's file as built (2026-09-24)". The dialog only opens for tickets that loaded, so in practice this covers a record that broke after the board read it. Adding the control to the Problems list for records that never loaded is not part of this ticket.

**How it was checked:**
- Five host tests in `ticket-file.test.ts`: a good id; an unknown id; non-string and empty arguments; five traversal shapes plus an absolute path, with a real file placed outside so a refusal can't pass by luck; and a conflict-marked record that still opens.
- Three renderer tests in `TicketFile.test.tsx`: the host is asked by id only, a failure is shown as an alert, and the control sits in the header.
- A temporary Playwright run against the built app on a scratch project (deleted afterwards). `shell.openPath` was replaced with a recorder, so it could be checked without launching an editor. It was asked for exactly that ticket's file. The file was then edited on disk and a focus event sent: the dialog showed the new text, and the header, including the review badge, was unchanged. Screenshot taken.
- The full `pnpm check` is run once for this batch (see the chat summary).

**Not verified:** A real editor was never launched; the recorder stood in for `shell.openPath`. Refocusing by switching windows for real was replaced by a dispatched focus event. Not run on macOS or Linux, where the default handler for `.md` may differ.

**For you to check:** Open a ticket, press **Edit externally**, and confirm your editor opens that ticket's file. Change a line, save, return to Knightbook, and confirm the ticket shows the change while its review badge stays as it was.
