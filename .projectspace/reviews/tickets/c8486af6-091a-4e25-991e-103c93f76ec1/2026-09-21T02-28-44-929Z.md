# Reopening a Done ticket

## Intended outcome
Moving a Done ticket back leaves no misleading acceptance record.

## Acceptance criteria
- Transition rules are written down; design section 5 says they need to be explicit.
- Decide whether completion provenance is cleared or archived when a ticket leaves Done.
- No card shows Accepted by you, or Recorded by AI, on a ticket that is not Done.
- A test covers it.

## Notes
Reading updateTicket suggests a ticket moved out of Done keeps its completion record, and the card shows that badge whatever the status. Reproduce before fixing.

## Handoff

**The decision: archived, not cleared.** Moving a ticket out of Done removes its
`completion` block and appends it to an optional `previous_completions` list, oldest
first, carrying everything known when the decision was made plus `reopened_at` and
the `reopened_to` status that ended it. Deleting it would have been simpler, but both
halves of the record have to stay true: leaving `completion` in place says a Backlog
ticket is accepted work, and deleting it says the user never accepted it. The list is
history and nothing reads it as state — readiness, selection, review and the
unattributed check all ignore it.

**Reproduced first.** Two failing tests before any fix. `updateTicket` never touched
`completion`, so the block survived the move, and both `toTicketView` and the MCP
`summarize()` reported it whatever the status — so a reopened ticket carried "Accepted
by you" while sitting in In progress, exactly as the Notes predicted.

**What changed.**

*Core.* `completionSchema` is now its own schema in `schema.ts`, reused for the current
acceptance and for each archived one, so a reopened record loses nothing that was known
when it was decided. `updateTicket` calls a new `reopen()` when the record's current
status is `done` and the update sets a status. Three cases fall out of that and are
tested: an update that does not change status leaves a Done ticket's acceptance alone,
because editing a Done ticket is not reopening it; a Done ticket with no provenance has
nothing to archive; and nothing else on the record changes.

*Reading is gated on status in both surfaces.* `toTicketView` and the MCP `summarize()`
report a current completion only when the ticket is Done. Reopening already clears it,
so this is about the other way in — a file edited by hand or merged from a branch that
carries an acceptance beside a contradicting status is no longer repeated as a claim.
That makes the third criterion true by construction rather than by the card behaving.

*App.* `previousCompletions` is on the detail view only, not on `TicketView`: this
belongs to reading one ticket closely, not to scanning the board, and the card
hierarchy is left alone. A new `ReopenedRecord` section renders under Related
documents, worded in the past — "Moved to In progress on …, which took that acceptance
back."

*Written down.* `docs/project-workspace-technical-design.md` section 5 asked for these
rules explicitly ("Direct overrides and reopening Done tickets need explicit transition
rules during implementation design") and the D-017 subsection had deferred them. There
is now a "Reopening a Done ticket as built" subsection beside it. The workflow skill
gained a line telling an AI tool that `previous_completions` is history, and that a
ticket with entries there and no `completion` is not accepted work.

**How it was checked.** Every suite passes with the bundled Node: core 145, MCP 20,
desktop 204, editor-preservation 22 (3 skipped), packaging 28. Ten of those are new —
seven in `packages/core/src/reopening.test.ts`, three in
`apps/desktop/src/renderer/Reopened.test.tsx`. Lint, the formatting check and all four
typechecks are clean.

Exercised end to end against the rebuilt MCP server and a throwaway project, not only
in unit tests: accept through `ticket_record_user_completion`, reopen through
`ticket_update`, and the file on disk then holds a plain `previous_completions` block
any other tool can read, while `ticket_read` and `ticket_list` both report
`completion: null`.

Checked in a browser against the board preview, which was given one reopened ticket.
The In progress card shows no acceptance badge while the Done cards still show
"Accepted by you" and "Recorded by AI"; the new section sits quietly between Related
documents and Record details in both colour schemes, and still reads correctly at a
760px window.

**Not verified:**
- **The packaged app.** `packages/mcp/dist/server.mjs` was rebuilt, but the staged copy
  under `apps/desktop/resources/mcp/` and the one in `release/` are older and do not
  have this. Rebuild and repackage before driving it from a connected client.
- **The Electron window.** Everything visual was checked in the board preview in a
  browser, not in the real window, and not on macOS or Linux.
- **Light mode was inspected by forcing the colour scheme** rather than through the
  Settings control, which would not open under automation. The section uses the same
  components as the two beside it, so this is a weak risk, but it is not the same as
  clicking the toggle.
- **No existing record was touched.** Nothing on your board has a
  `previous_completions` block: the only ones created were in throwaway projects.

**For you to check:** take a Done ticket, move it back to In progress, and confirm the
card loses "Accepted by you" while the detail says it was reopened and when; then open
`.projectspace/tickets/<id>.md` and confirm the acceptance is still there, under
`previous_completions`, as readable Markdown. Accepting it again and reopening it again
should leave two entries, oldest first.
