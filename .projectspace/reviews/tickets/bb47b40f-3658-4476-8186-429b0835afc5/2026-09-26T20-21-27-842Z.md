# Split CI into a check job and a package job

## Intended outcome
Lint, format check, typecheck and unit tests run as their own CI job and report first. Packaging and the packaged-app tests run in a second job only after the checks pass. When a packaged-app test fails, the run keeps a screenshot and the app's logs to look at. To keep Actions minutes within the free allowance, pull requests run on Linux only, and pushes to `main` run on all three platforms.

## Acceptance criteria
- `.github/workflows/ci.yml` has two jobs:
  - a `check` job running `pnpm install --frozen-lockfile`, `pnpm build:mcp` and `pnpm check`;
  - a `package` job, with `needs: check`, running `pnpm pack:dir` and then the packaged-app tests with `REQUIRE_PACKAGED_APP=1`. Linux keeps its virtual display.
- Platforms depend on what triggered the run:
  - pull requests: Linux only, for both jobs;
  - pushes to `main` (merges): Windows, Linux and macOS, for both jobs;
  - a manual `workflow_dispatch` run can be started on any branch and runs all three platforms, so a platform-sensitive change can be checked on Windows and macOS before merging.
- The matrix is chosen in the workflow from the event, not maintained twice. The job names still say which platform they ran on.
- A failure in `check` stops the run before any packaging, so a broken lint or test costs no packaging minutes.
- The packaged-app tests still fail when they are skipped in the `package` job. They are no longer run twice: today they run once, skipped, inside `pnpm check` and again after packaging. If `pnpm check` keeps running them, the skip there is expected and must not be mistaken for coverage. Say which was chosen and why.
- When the packaged-window test fails, the workflow uploads its screenshot, plus whatever the app wrote to stdout and stderr, as a run artifact. The test's own failure message names any alert text the window showed, and where the card ended up.
- `fail-fast: false` stays, so one platform failing does not hide the others.
- External actions stay pinned to reviewed commit SHAs, with the release named in a comment, like the existing ones. The workflow keeps read-only permissions and no secrets.
- The comments in `ci.yml` and the Commands/CI paragraph in `AGENTS.md` describe the new shape, including that Windows and macOS are checked on merge and on request, not on every pull request.
- Checked on real runs, once the Actions allowance allows it:
  - a pull request with a deliberately failing lint stops before `package`, on Linux only;
  - a clean pull request runs both jobs on Linux only;
  - a manual run runs both jobs on all three platforms.
  Report which platforms actually ran. A push to `main` is not required for this check; it is observed at the next merge.

## Notes
Came from PR 28 (`feature/header-and-title-bar`), where the packaged-window test "moves a card through its menu and records it in the ticket file" failed on Windows only. The click on "In progress" succeeded, but the ticket file stayed `backlog` for 20 seconds. The same test passed 19 of 20 times locally against a packaged build, including at 1024×768, and the run left nothing to explain the failure. That is the reason for the artifact and the fuller failure message. The failure itself is not diagnosed; if it happens again with the new diagnostics, open a bug for it.

Automatic retries are deliberately out of scope. They would hide intermittent failures like that one.

Cost, decided with the user on 2026-09-26: the GitHub Actions allowance ran out on 2026-09-25. There were 66 runs from 2026-09-19 to 2026-09-26, about 9 a day. A three-platform run costs roughly 40 allowance minutes, because Windows minutes count double and macOS about 10×. That is about 10,800 minutes a month against a free allowance of about 2,000 (about 3,000 with GitHub Pro, which was considered and not worth buying for this). A Linux-only pull request run is about 4 minutes, so pull requests plus full runs on merge should fit within the free allowance. These figures are estimates from run history and remembered pricing, not from the billing page.

The trade-off, accepted by the user: a Windows- or macOS-only break is found at merge rather than on the pull request, unless a manual run is started. Windows is where the app is actually used and validated today, so platform-sensitive changes (window chrome, paths, packaging) should get a manual run before merging. Say so in `AGENTS.md`.

Other shapes considered: running both jobs in parallel gives faster packaged results but installs dependencies twice per run. Three platforms on every pull request was the old behaviour, and it is what exhausted the allowance. The user preferred check-then-package.

## Handoff
**What changed:** Branch `feature/ci-check-and-package-jobs`, uncommitted.
- `.github/workflows/ci.yml`: a `check` job (install, `build:mcp`, `pnpm check`) and a `package` job (`needs: check`; install, `pack:dir`, then `test:packaged` with `REQUIRE_PACKAGED_APP=1`, xvfb on Linux). It adds a `workflow_dispatch` trigger. The platform list is one `fromJSON` expression on `github.event_name`, Linux-only for `pull_request` and all three otherwise, inside a `strategy` block that `package` reuses through a YAML anchor (`&platforms` / `*platforms`). The shared setup steps are anchored the same way. A new step uploads `experiments/packaging/test-results/` with `actions/upload-artifact` v7.0.1, pinned to `043fb46d1a93c77aae656e7c1c64a875d1fc6a0a` (resolved with `git ls-remote` and `gh api`; it is the latest release). It runs only on failure, per platform, and keeps files 14 days. `fail-fast: false`, read-only permissions and no secrets are unchanged.
- Double run: **`pnpm check` keeps running `experiments/packaging`**, because five of its seven files (staging, documents, invalid records, shared connection, the layout unit tests) are real coverage that needs no package. Only `packaged-app` and `packaged-window` skip there, which the ci.yml comment says is expected and not coverage. The `package` job runs only files named `packaged-*` (new script `test:packaged` = `vitest run packaged-`). The naming rule is documented at `requireWhenAsked` in `packaged.ts`. If nothing matches, vitest fails with "no test files", so it cannot quietly pass.
- New `experiments/packaging/src/window-evidence.ts` collects the app's stdout and stderr from launch. The app is launched with `ELECTRON_ENABLE_LOGGING=1` so renderer console output lands there too. On any failed window test, and on a failed launch, it writes `<test name>.png` and `<test name>.log` to `experiments/packaging/test-results/` (git-ignored). The move test's failure message now appends the visible alerts and every column's count, read from the "N in Status" labels.
- Docs: `AGENTS.md` Commands/CI paragraph; the README Checks paragraph and its packaging commands (now `test:packaged`); **D-031** added to the spec's accepted decisions; one line in `docs/proposals/platform-support.md`.

**How it was checked:**
- `pnpm check` passes. A local Windows package already existed, so the window suite really ran (3 passed), along with packaging 7 files / 48 tests and desktop 429 passed / 1 skipped.
- The workflow was parsed with the `yaml` package and anchors merged: `check` and `package` have the same strategy, `package` needs `check`, and the step lists are as intended.
- Failure path, forced on Windows by temporarily expecting `verification` (then reverted and diffed). `test:packaged` ran only `packaged-app` and `packaged-window`. The failure read "Matcher did not succeed in time. Alerts showing: none. Column counts: 0 in Backlog, 1 in In progress, 0 in Verification, 0 in Done." The `.png` and `.log` were written; I looked at the screenshot and it shows the card in In progress.
- Output capture: with no probe the log said the app wrote nothing. A temporary probe then wrote to the main process's stdout and stderr, and both lines appeared in the log, so the capture works and the app is simply quiet by default.

**Not verified:**
- No GitHub Actions run; the allowance is exhausted. All three real-run checks in the acceptance criteria are still outstanding.
- YAML anchors in workflows: GitHub has said it supports them since 2025, but they have not run here. If GitHub rejects them, the first run fails to parse, visibly. The fix is to repeat the `strategy` expression in both jobs.
- The artifact upload step has not run anywhere.
- The launch-failure evidence path ("the window never opened") was not exercised.
- `pack:dir` and the xvfb step were not rerun; only their order and placement changed.

**For you to check:** read the `ci.yml` diff, especially the anchors and the `fromJSON` matrix line. Decide whether the D-031 wording in the spec says what you decided. When the allowance allows: open a PR with a deliberate lint failure (expect Linux `check` only, no `package`), a clean PR (Linux, both jobs), and a manual "Run workflow" on the branch (all three, both jobs).
