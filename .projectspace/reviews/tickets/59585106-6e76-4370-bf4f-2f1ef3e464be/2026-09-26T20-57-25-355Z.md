# Add reusable routines with ticket-based runs and completion history

## Intended outcome
Keep recurring work such as package reviews and security checks as permanent instructions. Each run becomes an ordinary ticket for execution and user verification, while the routine shows the history of its runs.

## Acceptance criteria
- A user can create, view, and edit a routine in the app. An AI tool can list and read its instructions through MCP. The routine remains available after any run completes.
- Starting a routine creates a Backlog ticket linked to that routine, with a snapshot of its title and instructions. Later edits to the routine do not rewrite past run tickets.
- The generated ticket follows the existing workflow: work is handed off in Verification, and only the user's acceptance can move it to Done. A check that finds no changes still records its findings for verification.
- The routine shows linked runs and their current status. Its completion history and dates come from run tickets accepted as Done; an open or Verification ticket is never shown as completed. Do not store a second completion flag that can disagree with the ticket.
- A routine with an open run makes that run visible and avoids accidentally creating a duplicate. The user can deliberately start another run when needed.
- Routine instructions can mention a cadence such as weekly, but Knightbook does not schedule or execute runs in the background. An external AI scheduler may request a run through MCP.
- Existing ordinary tickets, plans, dependencies, search, and board behavior continue to work. Routine tickets remain visible as ordinary tickets and can be opened from the routine's history.

## Notes
Use one permanent routine record plus linked tickets for each occurrence. Decide the smallest record and MCP operations that fit the existing Markdown, revision-check, and core-sharing architecture. Document the product decision in the specification and technical design with a numbered, dated rationale when implementing. Keep the first version free of built-in scheduling, notifications, and a separate run log.
