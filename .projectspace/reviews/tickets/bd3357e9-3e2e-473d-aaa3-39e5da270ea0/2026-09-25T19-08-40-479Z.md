# Search documents as well as tickets from Ctrl/Cmd+K

## Intended outcome
The header search finds included documents by title and content as well as tickets, so the user can reach any project text from one place.

## Acceptance criteria
- Results are grouped under Tickets and Documents, each with a short matching excerpt.
- Choosing a document result opens it in the document viewer; choosing a ticket keeps today's behaviour.
- Search reuses the core search that MCP's project_search already uses rather than a second implementation.
- No results, and a failed search, are each shown explicitly and are distinguishable.

## Notes
The current search (ticket:search) covers ticket titles and descriptions only; ticket 4ec743fa added it.

## Handoff
**What changed:** Core: new `document-search.ts` with `readSearchableDocuments` (the document scan: included list, the 512 KB bound, unreadable files) and `searchDocuments` (title matches first, a highlighted excerpt, its own limit of 20). `searchProject`, which MCP's `project_search` uses, now reads documents through that same scan, so its output is unchanged but there is one implementation of which documents are searched. The highlight helpers moved from `ticket-search.ts` to `search-text.ts` and both searches use them. Desktop: a `searchDocuments` contract operation (`shared/document-search-contract.ts`, `main/document-search-ipc.ts`). The dialog (`TicketSearch.tsx`) now asks both questions through `hooks/useHeaderSearch.ts` and shows two groups, Tickets then Documents; result rows moved to `SearchHits.tsx` to keep the dialog under the size limit. Arrow keys move through both groups; a document result opens in the Documents view. The header control and dialog are labelled "Search tickets and documents". Technical design section 9 has a note ("Header search covers documents").

**Empty and failed:** Each group has its own "No ticket contains …" / "No document contains …", its own failure ("Documents could not be searched: … Nothing was changed.") that leaves the other group's results on screen, and its own count of files that could not be read. In the Archived scope documents are not searched, and the dialog says documents are never archived.

**How it was checked:** `packages/core/src/document-search.test.ts` (empty query, excerpt highlights with collapsed whitespace, title-first order, separate limit and total, and agreement with `searchProject` on which documents match); existing core search and `project_search` tests unchanged and passing. `src/renderer/DocumentSearch.test.tsx` (grouped results with the match marked, click and Enter open the document, both empty states, document failure with ticket results kept, an unreadable document reported, no document search in Archived). Existing search, archive and type tests pass with only the label updated. In `pnpm preview:board`: grouped results at 1280×800, a document opening in the Documents view, and `?docsearch=error` at 375×812 showing the documents failure beside ticket results. `pnpm build:mcp` and full `pnpm check` pass.

**Not verified:** Not run in the packaged app. The one real-file behaviour to look at: like `project_search`, a document is matched on its whole file, so a document with frontmatter shows the frontmatter at the start of its excerpt (seen in the preview, whose sample document has frontmatter). Most included docs here have none.

**Also filed:** 0b9b5e5f, to split `shared/contract.ts`, which is at 393 lines after this and the blocker ticket.

**For you to check:** After repackaging, press Ctrl+K, search a word from one of the docs (for example "revision"), and confirm the Documents group lists it and choosing it opens the document.
