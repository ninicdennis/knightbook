# Reachable ticket actions while reading

## Intended outcome
A long ticket can be read and acted on without scrolling to the end to find its controls, using the board's visual language.

## Acceptance criteria
- Bound the dialog to the available window height. Keep its title/close control and action bar visible while a single body region scrolls; avoid guessed fixed viewport offsets and nested whole-dialog scrolling.
- Long titles wrap without displacing Close. Keep status and review state visible and visually secondary to the title.
- Arrange Move to as a secondary control and review/verification actions in a clear, consistent group. Keep review distinct from Accept as done; preserve failed-verification, resolve-issue, completion provenance, dependency and blocked notices.
- All valid action combinations fit at 900×650 and at 200% zoom using intentional wrapping or a labeled overflow menu for secondary actions. No actions may be offscreen or cover the last content line.
- Related-document links wrap or truncate accessibly without widening the modal; audit timestamps/revision form a readable secondary section rather than a dense inline string. Preserve access to full values.
- Keep focus trapped correctly, Escape/Close available, action menus positioned within the usable viewport, and return focus to the initiating card/search result when closing.
- Separate shell/action layout from the Markdown content region so a future editor and toolbar can occupy that region without rebuilding dialog navigation. Do not add an editor, placeholder Edit/Save controls, autosave, or new persistence behavior.

## Handoff

**What changed:** `TicketDetailModal.tsx` is now three parts instead of one scrolling
column. It uses Mantine's compound `Modal.Root` / `Header` / `Body` parts, with the
content laid out as a flex column: the header (title, status, review state, Close) and
the action bar are fixed, and only the middle region scrolls. The dialog's height comes
from the modal's own bound on the window, so no header or footer height is subtracted
anywhere and nothing needs correcting when the title wraps or the text size changes.
The whole-dialog `ScrollArea.Autosize` is gone, so there is no longer a scroller inside
a scroller.

The actions moved into `TicketDetailActions.tsx`. Move to sits on the left as a quiet
control; review and the verification decisions are grouped on the right, with review
separated from Accept as done by a wider gap and by being the only unstyled one of the
two — Accept as done remains the single filled, coloured control. Every row wraps.
Failed-verification, resolve-issue, completion provenance, dependency and blocked
notices are unchanged; they moved with the code, not in meaning.

The secondary sections moved into `TicketDetailSections.tsx`. Related documents are now
one control per line, each wrapping in place (`overflow-wrap: anywhere`, which unlike
`break-word` also stops a long path setting the dialog's width). The audit line became a
"Record details" section of labelled rows, and it now shows the **whole** revision rather
than the first eight characters, because that is the value a conflict message names.

Two smaller changes came out of testing: `Modal.CloseButton` had no accessible name, so
it has one now; and `.markdown-body` gained `overflow-wrap: anywhere`, because a bare
path or UUID in a ticket body would otherwise push the reading text off the side. That
last one also applies to the Documents view.

Closing now hands focus back to the card the ticket was opened from, via a
`data-ticket-handle` attribute on the card's own control. Mantine's `returnFocus` is
turned off and this replaces it: clicking a card leaves focus on the document body, and
a result opened from search belongs to a dialog that has already closed, so Mantine's
version had nothing useful to hand back in either case.

The three files replace one 360-line file, all well under the size limit, and the
reading region is a single element holding only the ticket's prose — which is what the
"editor-ready" part of this ticket asked for. No Edit or Save control was added.

**How it was checked:** `pnpm check` passes — lint, format, typecheck, and 187 desktop
tests (10 of them new, in `TicketDetailLayout.test.tsx`), with the core and MCP suites
green alongside.

The new tests assert structure rather than pixels: that Move to, the review control and
Accept as done are **not** inside the scrolling region while the Markdown body is; that
the title, status badges and Close are outside it too; that a long title reaches the DOM
whole; that each related document's full path is its accessible name; that the revision
is shown in full and "Last reviewed" is omitted rather than invented; and that focus
returns to the card after both Escape and Close without stealing focus from the
confirmation dialog that replaces the detail view.

Layout itself was checked in a real browser against `pnpm preview:board`, with the
preview stub extended to hold a long title, a long body and a 95-character document
path. At a 900×650 viewport: dialog 810×585 with its bottom at 618 of 650, all four
actions on one row, the body scrolling (1254px of content in a 466px region) and no
horizontal overflow at all. The Move to menu opens upward and lands fully inside the
viewport. Escape returned focus to the right card's control, confirmed by reading
`document.activeElement`. Both colour schemes resolve correctly: the hairline and
surface tokens flip, giving white on near-black and black on white.

**Not verified:**
- **True 200% zoom, and any window narrower than about 980px.** The browser pane would
  not emulate a viewport smaller than its own width, so 900×650 is the narrowest real
  measurement here. As a substitute I forced 2× page zoom, which gives roughly 490
  effective pixels of width: the action bar wrapped onto three rows, every button stayed
  inside the dialog, and there was still no horizontal overflow. That covers the wrapping
  claim but **not** the height claim, because page zoom does not shrink `dvh` the way real
  browser zoom does. Worth one look at 200% in the packaged app.
- **The packaged Electron window.** Everything above is Chromium through Vite. Native
  window behaviour, and the dialog against the real frame, are unchecked.
- **Light mode by eye.** Only the computed colours were read, not a screenshot: the pane
  stopped drawing partway through. The values are the same tokens the approved board pass
  uses.
- **Contrast ratios were not measured.** The dialog still takes Mantine's own body
  surface rather than the board's `--ps-card-bg`; aligning dialogs with the board's
  surfaces is ticket `7bd9152b`, not this one, so it was left alone deliberately.

**For you to check:** open a long ticket and confirm you can reach its actions without
scrolling; shrink the window and raise the text size to 200% and confirm nothing is
clipped or covered; check a ticket with several related documents and a long path; and
confirm that closing the dialog puts focus somewhere sensible when you tab afterwards.

## Sent back: the action bar was cramped (2026-09-20)

**What you said:** the row looked bad once the window was squished, icon-only buttons
would help for things like Type and review, and the modal as a whole felt tight.

**What I found first.** This was not only a narrow-window problem. The dialog is capped
at 780px, so the widest it ever gets leaves about 740px of content — and five labelled
controls (Move to · Type · Mark reviewed again · Did not pass… · Accept as done) measured
about 750px plus their gaps. They wrapped onto a second row in *any* window, and the
extra padding below would have made it slightly worse. So this is fixed for every width
rather than behind a breakpoint, which also means there is no size at which the bar
suddenly rearranges itself.

**Icons.** Move to, Type, Mark content reviewed / Mark reviewed again, and Resolve the
verification issue are now icon-only: 36px square, matching the height of the buttons
beside them, each with its full name as both its tooltip and its accessible name. The
action row went from about 750px to about 410px of controls, so it now stays on one row
with room to spare.

Did not pass… and Accept as done keep their words. Both record a decision about whether
the work is acceptable, and those two must not be told apart by an icon.

There is one implementation detail worth knowing. Mantine's Tooltip hands its child only
the event handlers and the ref, so when a Tooltip sits inside `Menu.Target` the menu's
own `aria-haspopup` and `aria-expanded` land on the tooltip instead of on the button.
Move to and Type are therefore controlled menus, and those two attributes are set by hand
— without that, an icon-only button would not announce that it opens a menu at all.

**Padding.** The dialog moved from Mantine's default `md` padding to `lg`, so the header,
the reading area and the action bar all get 20px rather than 16px, and the action bar
gets 16px above and below. Mantine also drops the body's top padding when a header sits
above it, which is what put the first line of the ticket right against the header rule;
that is put back explicitly. The gap between sections in the body went from `md` to `lg`,
and the header's title-to-badges gap from 6 to 8.

**How it was checked:** `pnpm check` passes — 201 desktop tests, 3 of them new, and the
core and MCP suites green. The new tests assert that Move to, Type and the review control
have accessible names with no visible text, that the two decisions keep their words, and
that the menu buttons report `aria-haspopup="menu"` with `aria-expanded` flipping when
one opens. Every pre-existing test passed unchanged, because the accessible names did not
move.

Measured in a browser at 900×650: dialog 810×585, header padding 20px, body padding 20px,
action bar 16px/20px, all five controls 36px tall on **one** row. Both menus open upward
and land fully inside the viewport with the current type ticked, and the tooltips appear
on hover. At roughly 490 effective pixels of width (forced 2× zoom) the bar wraps onto
three rows with everything still inside the dialog and no horizontal overflow.

**Still not verified:** the same gaps as before — true 200% browser zoom, a real window
narrower than about 980px, the packaged Electron build, and measured contrast ratios. The
browser pane will not emulate a viewport smaller than its own width, so those remain for
you.
