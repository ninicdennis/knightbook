# Concurrent-writer test flake

## Intended outcome
The write-lock test asserts the behaviour it is about, and does not fail because the machine was busy.

## Acceptance criteria
- `packages/core/src/write.test.ts` "serializes concurrent writers instead of losing an update" passes under heavy parallel load.
- The distinction it is protecting is still tested: one writer wins, the other is refused, and no update is silently lost.
- If a lock timeout is a legitimate outcome under load, the test says which outcomes it accepts and why, rather than widening the assertion until it proves nothing.

## Notes
Observed failing once on 2026-09-20 during a full `pnpm check`, while a Vite dev server and a browser were also running. It did not reproduce in five later runs (three of the core suite alone, two of the full check), so this is recorded from a single observation.

The unconfirmed hypothesis: `acquireLock` in `packages/core/src/write.ts` gives up after `LOCK_TIMEOUT_MS` (5s, retrying every 25ms). The test asserts the losing writer rejects with `revision_conflict`. Under enough load the second writer could instead exhaust the lock timeout and reject with a different code, which would fail that assertion without anything being wrong with the write path itself. The failing assertion was not captured, so this needs confirming before it is fixed.

CI runs this on windows, ubuntu and macos runners, which are exactly the kind of loaded, shared machines where it would show up again.

## Handoff
**What changed:** Only `packages/core/src/write.test.ts`; the write path is untouched. The test now gets a 30s budget instead of Vitest's default 5s. The losing writer may be refused as `revision_conflict` or `locked`, but it must be a `ProjectError`, so a raw filesystem error still fails the test. The test also reads the file back: it must hold exactly the winner's content and the revision the winner was given. A comment on the test explains which outcomes are accepted and why.

**What the investigation found:** The original failure still could not be reproduced. I ran the scenario 300 times in sequence and then 600 times in batches of 40 in parallel, both under 12 to 24 CPU-bound Node processes on a 16-core Windows machine. Every loser got `revision_conflict`, and the slowest pair finished in 108ms, far from the 5s lock timeout. So the hypothesis is not confirmed. What is confirmed is a structural flaw: `packages/core/vitest.config.ts` sets no `testTimeout`, so Vitest's default of 5s equalled `LOCK_TIMEOUT_MS`. A loser that waited out the lock would have been cut off by Vitest as "Test timed out" before it could reject as `locked`. The likeliest form of the 2026-09-20 failure is that generic timeout, but that is inferred, not observed.

**How it was checked:** `pnpm --filter @knightbook/core test` and `typecheck` pass. The core suite was then run four times under 24 CPU burners, and this test passed every time. The full `pnpm check` is run once for all of this session's tickets (see the chat summary).

**Not verified:** The `locked` branch is never actually hit in these runs. It is accepted by reasoning, not observed. Not run on Linux or macOS.

**Found along the way:** Under that same synthetic load, 10 to 29 *other* core tests failed in three of four runs, all with Vitest's 5s default timeout. A follow-up ticket for this ("Decide the core test suite's timeout budget for loaded CI runners", 8f38f496) was filed and then archived without work on 2026-09-24, at the user's decision. Knightbook is not load-sensitive: at most the app and the MCP server write to a project, and the load was far beyond real use or CI. No further load testing is planned.

**For you to check:** Read the new test and its comment, and decide whether accepting `locked` alongside `revision_conflict` is the right boundary.
