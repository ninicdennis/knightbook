# Bundle the workflow skill and add guided AI setup

## Intended outcome
A user with only the installed Projectspace application can connect their AI client and install or export the complete workflow skill without cloning the source repository or pasting a development-machine path.

## Acceptance criteria
- Bundle the complete skills/projectspace directory, including any companion files, with the installed app. Keep one source of truth and verify the shipped contents match it.
- Add Set up your AI tool to the MCP footer details panel. Present connection setup and workflow-skill installation as separate steps with clear client-specific instructions.
- Let the user preview the skill and choose an explicit installation scope. For Codex, support the project's .agents/skills/projectspace directory and optionally the user's ~/.agents/skills/projectspace directory, verifying current supported locations during implementation. Never silently modify global configuration or overwrite an existing/customized skill.
- Provide export of the complete skill folder and Copy instructions for clients without native skill support. Instructions must use shipped resources or exported files, never require a repository checkout.
- Detect matching, outdated, and locally modified installed copies where observable. Explain update choices; app updates must not silently overwrite customized copies. Do not treat a file on disk as proof that an AI loaded or followed it.
- Keep brief MCP connection instructions as a fallback. Clearly distinguish MCP configuration/connection, skill installation, and actual activation evidence. Do not claim universal client auto-discovery.
- Verify setup from an installed or relocated packaged application with the source checkout unavailable, including paths containing spaces, existing-skill conflicts, and use of exported companion files. Test documented client discovery separately from file-copy success.
- Update README/help with the shipped-app setup flow and supported client instructions.

## Research and notes
Research date: 2026-09-19. Current electron-builder configuration packages dist, package.json, and the MCP resources, but not the full skills/projectspace/SKILL.md. The MCP bundle includes short rules from packages/mcp/src/instructions.ts; these point users to the repository for the full workflow. Current README instructions assume access to that repository. Source-level guidance tests check consistency but do not prove the skill is present in the distributed app.

Official Codex documentation describes project .agents/skills and personal ~/.agents/skills discovery, plus plugin distribution: https://developers.openai.com/codex/skills. Start with bundled skill export/explicit local installation; a public plugin marketplace release is outside this ticket.

Related ticket: 1caa7fd2-e877-42b1-ad8a-0c5689825110 (MCP status and connection actions in a bottom footer). This ticket owns onboarding and skill distribution; the footer ticket owns status presentation. No implementation has started.

## Handoff
**Locations re-verified 2026-09-24 from the official docs:**
- Claude Code reads `~/.claude/skills/<name>/SKILL.md` and `.claude/skills/<name>/SKILL.md` (code.claude.com/docs/en/skills).
- Codex reads `$HOME/.agents/skills` and `.agents/skills` from the working directory up to the repository root, and needs `name` and `description` in the frontmatter (the Codex URL now redirects to learn.chatgpt.com/docs/build-skills).
- Our SKILL.md already has both fields.

**What changed:**
- *Shipping:* `electron-builder.yml` copies `skills/projectspace` straight from the repository into `resources/skills/projectspace`, so there is one source and no staged copy. A new test in `experiments/packaging/src/packaged-app.test.ts` checks that the shipped folder is identical to the source, file by file.
- *Install logic:* `src/main/skill-install.ts` (pure, tested on real folders) lists the four documented targets (Claude Code and Codex, personal and project). It reports each as `absent`, `matching`, `outdated` or `modified`.
  - `outdated` needs evidence: the folder still hashes to the fingerprint Knightbook recorded in `app-state.json` (`installedSkills`) when it installed there. Any other difference is `modified` and is never overwritten.
  - Installs are built beside the target and moved into place. The state is re-checked at write time, so a folder changed after the dialog showed it is refused.
  - Export writes a new `projectspace` folder and refuses if one is already there.
- *Handlers:* `src/main/skill-setup-ipc.ts` adds `skill:setup`, `skill:install` and `skill:export`, with types in `src/shared/skill-setup-contract.ts`. The renderer names a target by id only; every path is resolved in the host.
- *UI:* the MCP panel gains **Set up your AI tool**, which opens `AiSetupDialog`.
  - Step 1 is the connection: copy the configuration, with short notes for Claude Code `.mcp.json` / `claude mcp add-json` and Codex `[mcp_servers.knightbook]`.
  - Step 2 is the skill: a row per target with a state badge. Install for absent, Update behind a confirmation for outdated, and an explanation with no button for modified.
  - Below that: Export skill folder, Copy skill text, a SKILL.md preview, and a closing statement that the app cannot see whether a client loaded the skill.
- *Stale pointers fixed:* the MCP connect instructions no longer say the skill is "in the Knightbook repository". SKILL.md no longer points at the removed "plug button in the app header". README's "Teaching an AI tool the workflow" now describes the shipped-app flow.

**How it was checked:**
- Ten unit tests in `skill-install.test.ts`, run in a temp path with a space in it. They cover target paths, all four states, a file where the folder should be, companion files, no staging folder left behind, an outdated update, a customised copy refused for both actions, a folder appearing after the check, and export plus export refusal.
- Five renderer tests in `AiSetup.test.tsx`.
- Packaged with electron-builder into a scratch folder with a space in its path ("Relocated Knightbook"), whose `SKILL.md` is byte-identical to the source.
- A temporary Playwright test drove that relocated package with a sandboxed home folder, so the real `~/.claude` was never touched:
  - A pre-existing customised `~/.claude/skills/projectspace` showed "Changed here" and was left byte-for-byte unchanged.
  - Installing for Codex (personal) and Claude Code (project) wrote files identical to the source, and `installedSkills` recorded both.
  - Export wrote a complete folder, and a second export into the same place was refused with "already exists".
  - Screenshot taken. The temporary test was deleted afterwards.
- `pnpm check` passed.

**Not verified:**
- *Client discovery:* I did not start Claude Code or Codex against a freshly installed copy to confirm it is loaded. Only the file placement was tested.
- *Outdated update:* covered by unit tests only. A packaged build ships one version, so it could not be staged end to end.
- *Source checkout "unavailable":* the relocated app reads only `process.resourcesPath` when packaged, but the repository was still present on disk during the run.
- *No companion files yet:* the skill has none, so companion handling is tested with synthetic files.
- *Other platforms:* not run on macOS or Linux.
- *Packaging tests:* the seven that need `apps/desktop/release/` skipped, because packaging there failed while the user's Knightbook was running from it (see chat).
- *Startup with no AppData:* launching with a home folder that has no `AppData\Roaming` makes Electron's `appData` lookup fail inside `adoptStateFromPreviousName`, and no window appears. This is pre-existing and was only hit by the test setup.

**For you to check:** Open the MCP panel, choose **Set up your AI tool**, and read the steps. Install into one location and look at the folder. Edit that copy and reopen the dialog: it should say "Changed here" and offer no button. Try Export into a folder, then export into the same folder again.
