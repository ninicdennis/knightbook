# Locked runtime blocks the build

## Intended outcome
`pnpm build` succeeds while an AI client has the Projectspace MCP server running,
which on a development machine is most of the time.

## Acceptance criteria
- Staging does not delete or rewrite the Node runtime when the staged copy is
  already the one this build would produce.
- A runtime that genuinely has to be replaced but cannot be reports what is
  holding it and what to do, rather than an unhandled EPERM stack.
- Files left behind by a build for another platform are still cleaned up.
- The cross-platform limitation the script already documents is unchanged.

## Notes
Reported by the user, and not the first time:

```
[Error: EPERM: operation not permitted, unlink
 'C:\Users\Denny\Projects\projectspace\apps\desktop\resources\mcp\node.exe']
```

Reproduced: `node.exe` (PID 42832) was running from
`apps/desktop/resources/mcp/`, launched as the MCP server for this very project,
so Windows refused to unlink it. `stage-mcp-runtime.mjs` opens with
`rm(target, { recursive: true, force: true })`, which is what fails.

The staged binary and the build host's own `node.exe` were byte-identical
(SHA-256 3602F2BB…, 92,825,416 bytes), so the deletion was not achieving anything
in this case. Skipping an identical copy fixes the reported failure outright.

Windows will not delete or overwrite a running executable at all, so a runtime
that really did change still cannot be staged while a client holds it. That case
needs an explanation, not a workaround.

## Handoff
**What changed:** `apps/desktop/scripts/stage-mcp-runtime.mjs` only.

- The opening `rm(target, { recursive: true, force: true })` is gone. It deleted
  the runtime the build was about to put back, and on Windows that delete is what
  failed whenever a client had the server running.
- Each file is now compared before it is copied: sizes first, then SHA-256 only
  when the sizes match. An identical file is left alone.
- A file that has to be replaced but is held open no longer throws a raw EPERM.
  It prints what is holding it, why an operating system refuses, and the command
  to find the process, then exits 1.
- Cleaning up after a build for another platform is kept, but narrowed: anything
  in the directory other than this platform's runtime and `server.mjs` is
  removed. The runtime itself is no longer deleted to be re-copied.

**How it was checked:** With the reported server still running (PID 42832,
launched from the staged runtime and rooted at this checkout):

- `node scripts/stage-mcp-runtime.mjs` → `kept node.exe (already identical),
  staged server.mjs`, exit 0. This is the case that used to fail.
- Full `pnpm build` → same result, exit 0.
- The failure path was exercised for real, not reasoned about: running the script
  under Node 22 makes the source runtime genuinely differ from the locked Node 24
  copy. It printed the explanation and exited 1, and the staged runtime was
  afterwards confirmed unchanged (SHA-256 3602F2BB…), so a refused replacement
  does not leave a half-written binary.
- The `Get-CimInstance` command the message suggests was run and did name PID
  42832.
- `pnpm check` exits 0.

**Not verified:**
- Only on Windows. The `lsof` branch of the message and the `ETXTBSY` case were
  not exercised; macOS and Linux were not run at all.
- Hashing adds roughly a second to a build whose runtime is already staged, on a
  93 MB binary. Measured only as "not noticeable", not timed.
- `electron-builder --dir` was not run, so the packaged output was not rebuilt
  from this staging. Nothing about the resulting directory contents changed.
- The stray-file cleanup was not exercised: there was no leftover from another
  platform to remove.

**For you to check:** Run `pnpm build` normally with your client open, which is
the case that was failing. If you want to see the refusal, stop nothing and run
the script under a different Node version.
