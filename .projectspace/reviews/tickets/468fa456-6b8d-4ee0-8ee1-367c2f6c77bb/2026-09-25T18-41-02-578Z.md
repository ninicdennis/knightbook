# Set and clear a ticket's blocker in the app

## Intended outcome
The user can record why a ticket cannot move, or clear that reason, from the ticket detail view.

## Acceptance criteria
- The detail view has a control to add, edit and remove the blocker text.
- Clearing the blocker stores no blocker (null), not an empty string.
- The card's blocker badge appears and disappears to match, without a manual refresh.
- The write carries the ticket's revision and handles a conflict the same way other ticket edits do.

## Notes
Today the blocker is displayed on cards and in the detail view but can only be written through MCP or by hand.

## Handoff
**What changed:** A new contract operation `setTicketBlocker(rootPath, id, blocker | null, revision)` in `apps/desktop/src/shared/ticket-edit-contract.ts`, handled by `ticket:setBlocker` in `src/main/ticket-edit-ipc.ts` (kept out of `contract.ts` and `ipc.ts`, which are near the size limit). The host trims the text and stores blank text as no blocker, through core `updateTicket` with the read revision. In the renderer, `components/TicketBlocker.tsx` replaces the read-only Blocked alert in the detail view: "Add a blocker" when there is none; Edit and Clear blocker on the alert when there is one; the editor saves with a button or Ctrl+Enter and cancels with Cancel or Escape. The write goes through the same `apply` path as moves and type changes (`useTicketActions.setBlocker`), so the board view is replaced with what the files say and a conflict reloads and shows a message. The preview stub implements the new operation.

**How it was checked:** New `src/renderer/TicketBlocker.test.tsx` (add, edit, clear by button, clear by saving empty text, Escape cancels without closing the dialog, conflict reloads with a message) and `src/main/ticket-edit.test.ts` (trimming, null for empty or whitespace, refusal of non-text). Desktop typecheck clean. In `pnpm preview:board` at 1280×800 and 375×812: the Blocked alert shows Edit and Clear, the editor opens with the current text, Escape cancels and leaves the dialog open, and an unblocked ticket shows "Add a blocker".

**Not verified:** Not run in the packaged Electron app, so the real IPC round trip was only covered by the unit tests and the stub. As with type changes, a conflict message appears on the board behind the dialog, not inside it; that is the existing behaviour this follows.

**For you to check:** Open a ticket, add a blocker, and confirm the card shows the Blocked badge straight away; then clear it and confirm the `blocker:` line is gone from the ticket file rather than left as `blocker: ""`.
