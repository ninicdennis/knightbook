# Ticket detail view

## Intended outcome
Clicking a card opens a modal showing everything written on the ticket, so a person can read what an AI wrote without opening the Markdown file by hand.

## Acceptance criteria
- Click or Enter on a card opens the modal. A drag does not. Escape closes it and focus returns to the card.
- Shows the title, status and revision, and the body rendered with the same sanitizer as the document viewer.
- Shows dependencies: each prerequisite by title and current status, whether it satisfies readiness (Verification or Done), and any blocker text.
- Shows the completion record: who recorded it, whether it was a direct action or a reported instruction, when, and the instruction text. A Done ticket with no record shows as Unattributed.
- Shows review state with Mark reviewed, or Mark reviewed again, and the time of the last review.
- Lists related documents; choosing one opens it in the Documents view.
- Move and Accept as done are available from the modal with the same confirmation rules as the card menu.
- Tests cover open, close, and click versus drag.

## Notes
Highest priority. Found by the user while trying the app: ticket content written through MCP cannot be read anywhere in the app. The host already has a ticket:read operation and the shared contract has readTicket, but nothing calls it. Until this ships, open the file under .projectspace/tickets in an editor.

## Verification
Checked by the AI, not accepted by the user.

What was checked:
- 21 new component tests cover opening on click, the keyboard route through the card menu, Escape, dependencies (including a missing prerequisite), the blocker, an AI-recorded versus a user-recorded completion, an unattributed Done, a failed read, moving and reviewing and Accept as done from inside the dialog, following related documents and links in the body, and the refresh behavior. The desktop suite went from 28 to 49 tests and the whole workspace passes.
- Removing the two click guards on the card makes two of those tests fail, so the guards are load-bearing.
- Driven in Chromium with the real drag library: a click opens the dialog, and a real press-and-drag moves the card without opening it (the move fired, the read did not). A script in a ticket body did not run, and a javascript link was refused.
- The packaged build launches cleanly and opens this project.

Not met as written: the criteria say Click or Enter opens the dialog. Enter is not implemented on the card, because the drag library already uses Enter and Space on a focused card to start a keyboard drag. Keyboard users open it with View details in the card menu instead. Decide whether that is acceptable.

Not verified: the dialog inside the packaged Electron window itself (a screenshot of that window cannot be taken from this environment), light mode, and very long tickets.

Also done in the same change, at the user's request: a Refresh button, and a refresh whenever the window regains focus. And a packaging fix: app.asar had grown from 0.4 MB to 99 MB because the renderer libraries were listed as runtime dependencies; it is now 2.2 MB.
