# Add reusable routines with ticket-based runs and completion history

## Intended outcome
Keep recurring work such as package reviews and security checks as permanent instructions. Each run becomes an ordinary ticket for execution and user verification, while the routine shows the history of its runs.

## Acceptance criteria
- A user can create, view, and edit a routine in the app. An AI tool can list and read its instructions through MCP. The routine remains available after any run completes.
- Starting a routine creates a Backlog ticket linked to that routine, with a snapshot of its title and instructions. Later edits to the routine do not rewrite past run tickets.
- The generated ticket follows the existing workflow: work is handed off in Verification, and only the user's acceptance can move it to Done. A check that finds no changes still records its findings for verification.
- The routine shows linked runs and their current status. Its completion history and dates come from run tickets accepted as Done; an open or Verification ticket is never shown as completed. Do not store a second completion flag that can disagree with the ticket.
- A routine with an open run makes that run visible and avoids accidentally creating a duplicate. The user can deliberately start another run when needed.
- Routine instructions can mention a cadence such as weekly, but Knightbook does not schedule or execute runs in the background. An external AI scheduler may request a run through MCP.
- Existing ordinary tickets, plans, dependencies, search, and board behavior continue to work. Routine tickets remain visible as ordinary tickets and can be opened from the routine's history.

## Notes
Use one permanent routine record plus linked tickets for each occurrence. Decide the smallest record and MCP operations that fit the existing Markdown, revision-check, and core-sharing architecture. Document the product decision in the specification and technical design with a numbered, dated rationale when implementing. Keep the first version free of built-in scheduling, notifications, and a separate run log.

## Test plan
Written before the code (2026-10-23). Each criterion, the test that fails without it, and the data that makes the case happen.

- **Create, view, edit; MCP list and read; routine survives a run.** Core `routines.test.ts` creates a routine, reads it back, edits it at its revision and refuses a stale revision. A run ticket is then accepted with `recordUserCompletion` and the routine still lists and reads. MCP `routine-tools.test.ts` calls `routine_list` and `routine_read` over a real project and gets the instructions. The desktop host's routine handlers are tested for create and edit, and `Routines.test.tsx` creates and edits one through the dialog.
- **A run is a Backlog ticket with a snapshot; later edits do not rewrite it.** Core test: start a run, check the ticket is Backlog, carries the routine id, and has the routine's title and instructions. Then edit the routine's instructions and check the run ticket's body is unchanged.
- **Runs follow the normal workflow.** Core test: a run ticket moves to Verification, then a body edit through `updateTicket` keeps its routine link. `ticket_update` still cannot set Done (existing tests). Recording findings for a check with no changes is guidance in the skill, settled by reading.
- **History comes from tickets, never a second flag.** Core test with four runs: two accepted Done on different dates, one in Verification, one Done whose completion block was removed (unattributed). Completions list only the two accepted runs, newest first, with their acceptance dates; the Verification and unattributed runs are not completions. The routine file is checked to have no completion field.
- **An open run blocks an accidental duplicate; a deliberate one is allowed.** Core test: a second start while a Backlog run exists fails with `run_already_open` naming that ticket, and creates nothing. With `another_run` it creates a second run. A run that is Done, or archived, does not block. MCP test for the error code; renderer test for the "start another run" confirmation.
- **No scheduling.** Nothing in Knightbook runs on a timer; settled by reading the diff. `routine_start_run` lets an external scheduler start a run (MCP test).
- **Existing behaviour continues.** `pnpm check`, plus a test that a run ticket appears in `ticket_list` as an ordinary ticket with `routine_id` set.
- **Manual:** the layout of the Routines view at two widths in the board preview; the packaged app on Windows is for the user to check.

## Handoff
**What changed:** Routines, decision D-051. A routine is `.projectspace/routines/<id>.md`: a title, and its instructions as the Markdown body. Core (`packages/core/src/routines/`) creates, reads, lists and edits routines at a revision. `startRoutineRun` creates a Backlog ticket with a copy of the title and instructions and `routine: { id }` in its frontmatter (a new optional ticket field). If a run is still open, it refuses with `run_already_open` unless `anotherRun` is set. `routineHistory` reads runs and completions from the tickets, so the routine stores no completion. MCP adds `routine_list`, `routine_read`, `routine_create`, `routine_update` and `routine_start_run`, and `ticket_list`/`ticket_read` now return `routine_id`. The skill has a Routines section. The app has a Routines tab next to Plans: a list, the instructions, Edit (title and instructions as Markdown source), Start run (asks first if a run is open), and the run history, where each run opens as a ticket. Starting a run re-reads the board. The decision is written up in the spec (D-051 and the scope table), the technical design ("Routines as built", the storage layout, the MCP table) and the user guide.
**How it was checked:** `pnpm check` passed: lint, format, typecheck, core 294 tests, MCP 51, desktop 679 (4 skipped), website 209 (37 skipped). New tests: core `routines.test.ts` (10) and `routine-history.test.ts` (3), MCP `routine-tools.test.ts` (4), host `routines-ipc.test.ts` (4), renderer `Routines.test.tsx` (6). Each one uses data that makes its case happen: two runs accepted on different dates, one in Verification, one Done with its completion block removed, a reopened run, a Done and an archived run that must not block, a stale revision, and an unreadable ticket file. `pnpm build:mcp` was rebuilt. The Routines view was looked at in `pnpm preview:board` at 1600px dark, 1600px light and 800px light, including the "Start another run?" and Edit dialogs.
**Not verified:** The `verifier` subagent is not available in a cloud session, so it was not run. The packaged-app tests were skipped because nothing was packaged. The real Electron window was not opened, so the pane has only been seen against stub data. A connected AI client keeps its old MCP build until it reconnects. Starting a run checks for an open one and then writes, and the two steps are not atomic: two simultaneous starts could each make a ticket. This is described in the technical design. Routines are not in header search.
**For you to check:** Open the Routines tab, create a routine, edit it, start a run, and see the ticket appear in Backlog. Press Start run again and check that it asks first. Move the run through Verification, accept it, and check the history shows the acceptance date. Edit the routine and check the earlier run's ticket body has not changed.
