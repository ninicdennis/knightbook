# Show MCP status in a bottom footer

## Intended outcome
The user can see the MCP status for the currently displayed project in a bottom footer/status bar, and understand whether any action is needed. If the lifecycle can be controlled reliably from the running application, let the user start and stop it there.

## Acceptance criteria
- Add a compact MCP status indicator in a bottom footer/status bar, matching the current application styling. Place connection details, Copy MCP configuration, and any supported Start/Stop controls in or accessible from this footer.
- Keep the footer visible across Board, Documents, and Archive when available. Reserve layout space so it does not obscure content or scrolling, and keep it usable at narrow window sizes.
- Give the indicator a readable label and accessible description; color alone must not communicate status. Explain the observed state and available action in a tooltip or small details panel.
- Define what the indicator measures before implementation: runtime availability, running server instances, and an active client connection are different facts. Report only states supported by evidence; an unavailable observation must show Unknown or an equivalent explanation rather than incorrectly claiming Stopped or Connected.
- Keep status scoped to the displayed project's path. Refresh it as the observed state changes and when switching projects, without requiring the user to reopen the application. Stale observations must not remain displayed as a healthy live connection.
- Assess whether Start and Stop can reliably control the relevant server instance under the existing client-launched stdio architecture. If supported, provide controls with pending and failure feedback, prevent duplicate starts, and explain any client disconnection caused by stopping. Controls must affect only the intended project's managed instance.
- If start/stop is not supported by the current architecture, explain that the AI client manages the server and provide actionable connection guidance in the details panel. Document the limitation and any proposed architecture change; do not introduce a new service or transport merely to make the buttons possible.
- Preserve the existing ability for an AI client to use MCP while the desktop application is closed. Closing the window must not implicitly stop client-owned servers.
- Verify the indicator against an actual client connection, disconnection, project switching, and unavailable or stale status. If lifecycle controls are implemented, verify successful and failed starts/stops and that other project connections are unaffected.

## Notes
Updated placement preference (2026-09-19): use a bottom footer/status bar for MCP status and connection actions. This leaves the header available for project identity, centered ticket search, navigation, and Refresh. Consolidate the existing plug / Copy MCP configuration action into the footer so connection controls have one clear home.

The current documented architecture launches a separate stdio server from the AI client using the bundled Node runtime and a project-specific --root argument. The desktop window is not the server owner. Feasibility of app-controlled start/stop is intentionally open; accurate status is the primary outcome. Do not infer a live client connection merely because the runtime exists or a separate probe succeeds.

This ticket records the requested feature only; implementation has not started.
## Handoff

**What changed**

A bottom status bar reports MCP status for the open project, and the header's
plug button moved into it so connection actions have one home.

The window could not observe MCP at all before this: the AI client owns the
server process and both ends of the stdio pipe. The two processes share only the
project folder, so a running server now records itself there and the window reads
it — a JSON file per session under `.projectspace/runtime/sessions/`, refreshed
every 10s, removed on a clean exit, gitignored like the write lock.

Three facts are reported separately, never merged:

- **Bundled runtime** — the window checks its own installed resources.
- **Server process** — a session record with a heartbeat under 45s old.
- **Client connection** — the server marks the record when a client's opening
  handshake runs.

Indicator states: `MCP connected`, `MCP server running`, `MCP not connected`,
`MCP runtime missing`, `MCP status unknown`. A stopped heartbeat reads as stale,
never as "stopped"; an unreadable folder reads as Unknown. Each state has its own
icon as well as its own colour, and the text label carries the meaning.

**Start/Stop was assessed and deliberately not built.** Under client-launched
stdio a server the app started would have no client on the other end of its
pipes, and stopping the client's process would sever a connection from outside
the client's knowledge. Both would be theatre. The panel says the client owns the
lifecycle and gives connection steps instead. Rationale is in
`docs/project-workspace-technical-design.md` under "Observing MCP status from the
window"; README has the user-facing table.

New: `packages/core/src/mcp-sessions.ts`, `apps/desktop/src/main/mcp-status.ts`,
`apps/desktop/src/renderer/mcp-status.ts`, `hooks/useMcpStatus.ts`, and the
`McpStatusFooter` / `McpStatusDetails` / `McpStatusDot` components.

**Two bugs found and fixed while verifying**

1. Session cleanup never ran. `end()` was async and `process.exit()` raced it, so
   every shutdown left a record behind. Cleanup is now synchronous in the `exit`
   handler, and the shutdown that actually happens — the client closing stdin —
   is hooked. A hard kill still leaves a record; that is what the stale heartbeat
   and the startup sweep are for.
2. **More serious:** recording a session created `.projectspace/runtime/` in
   folders with no project, which made `project_initialize` refuse the folder as
   somebody else's. This broke 13 packaging-experiment tests. The server now
   writes nothing until the project file exists, and checks on each heartbeat, so
   a project created through MCP becomes observable within one heartbeat.
   `assertReservedDirIsOurs` also now recognises `runtime` and `.write-lock` as
   ours.

**How it was checked**

- `pnpm check` (lint, format, typecheck, tests) green: 272 tests across all
  packages, including the packaging experiment driving the rebuilt server.
- New tests: 13 in `packages/core/src/mcp-sessions.test.ts`, 5 in
  `apps/desktop/src/main/mcp-status.test.ts`, 11 in
  `apps/desktop/src/renderer/mcp-status.test.tsx`, 9 in
  `apps/desktop/src/renderer/McpFooter.test.tsx` (covering project switching
  discarding a stale reading, live refresh, and no Start/Stop controls).
- Drove the real bundled server over stdio the way a client does. Observed:
  nothing written to an unset folder → project created through MCP → recorded
  with `connected: true` on the next heartbeat → record removed when stdin
  closed.
- Exercised the design preview in a browser: all five states, footer present on
  Board and Documents, layout space reserved, and at 375px the label stays while
  "Details" collapses out. Panel width is capped at `100vw - 16px`.

**Not verified**

- Never run in the actual packaged Electron app — only the browser preview and
  the unit/integration tests. The footer has not been seen in a real window.
- Only on Windows. The `stdin` close and signal shutdown paths differ on
  macOS/Linux and were not exercised there.
- No test of two real AI clients connected to the same project at once; the
  multi-session display is covered only by fabricated records.
- Clock skew is not handled: a project folder on a share written by a machine
  with a different clock could read as stale or live incorrectly.
- Behaviour on a read-only project folder is coded for (recording fails quietly,
  status falls back) but was not actually tested against one.

**For you to check**

1. Run the real app against a project and connect an AI client to it. The footer
   should go to **MCP connected** within ~5s, and back to **MCP not connected**
   within ~45s of disconnecting.
2. Open the details panel and confirm the three facts read correctly, and that
   the Start/Stop explanation is the answer you wanted rather than a gap.
3. Confirm you are happy the header lost its plug button.
4. Judge the wording. The whole feature rests on never overclaiming, so if any
   phrase sounds like it promises more than was observed, it should change.
5. Note `43253b7e` (one local MCP connection across enabled projects) appeared on
   the board during this work and expects footer status semantics to change once
   it lands. Nothing here blocks it.
