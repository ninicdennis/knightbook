# Show Markdown changes since review for documents and tickets

## Intended outcome
The user can immediately see what changed since their last review without rereading an entire document or ticket description.

## Acceptance criteria
- Add a discoverable read-only Changes view alongside normal reading for both documents and tickets. Compare current canonical Markdown with the most recent human-reviewed source, not Git HEAD or the previous save.
- Reuse existing review snapshots and reviewedSource; label the baseline review time and current revision. Opening the comparison never marks content reviewed or tickets Done.
- Default to a unified line diff with clear additions/removals, line numbers, nearby context, and expandable unchanged sections. A single changed line in a long document is immediately visible. Color is supplemented with text/signs and accessible labels.
- Retain frontmatter changes in the comparison, while making ticket bookkeeping distinguishable from its description. Provide faithful source comparison and preserve existing rules for what invalidates review; do not hide substantive metadata edits.
- Handle unreviewed content, identical source, missing/corrupt snapshots, and errors explicitly; never pretend an absent baseline is an empty document.
- Render untrusted source as escaped text. Bound diff computation for large or highly divergent inputs and provide an explanatory fallback. Handle line endings and final-newline differences predictably.
- Refresh or flag a stale comparison if content changes while open. A subsequent review must correspond to the revision actually shown, or require a reload, rather than silently approving unseen edits.
- Keep controls and content usable with keyboard, both themes, narrow windows, and zoom.

## Handoff
Branch `feature/review-changes-diff`, uncommitted.

**What changed:**
- Core: new `packages/core/src/review-changes.ts` (`reviewChanges`, `compareSources`). It compares the current source with the newest readable snapshot, with frontmatter and body as separate sections, and tags changed lines under review's bookkeeping fields. It returns explicit states: `no_baseline`, `identical`, `changed`, `too_large`. Bounds are 20,000 lines, 1,000,000 characters, 5,000 edits and 1.5 s. Line-ending and final-newline changes are reported as notes. `review-storage.ts` now counts unreadable snapshot files instead of skipping them silently. `review.ts` exports `BOOKKEEPING_FIELDS` (same list, now shared) and lets `recordReview` / `recordTicketReview` take an expected revision, refusing with `revision_conflict` if the content moved on. Fingerprint semantics are unchanged.
- New dependency: `diff` 9.0.0 (jsdiff) in `@knightbook/core`, bundled into both the MCP server and the Electron main process.
- Desktop: new contract operations `documentChanges` / `ticketChanges` (`src/main/review-changes-ipc.ts`). Both review operations now pass the revision the user was shown. The UI has a "Read | Changes since review" switch in the document reader and the ticket dialog, plus `ReviewChanges.tsx`, `DiffTable.tsx` (3 lines of context, foldable unchanged runs, +/− signs and screen-reader labels, text only) and `review-changes.css`. A review conflict reloads and explains itself; tickets now have their own conflict message instead of "your move was not applied".
- Refactors needed to stay under the file-size limit: `contract.ts` would have reached 403 lines, so the review and documents types moved to `shared/review-contract.ts` and `shared/documents-contract.ts`, re-exported unchanged. `DocumentReader` moved out of `DocumentsView.tsx` into its own file.
- Docs: "Changes since review as built (2026-09-24)" added to technical design section 7.

**How it was checked:**
- `pnpm check` passes: core 203, mcp 40, desktop 279 (+1 skipped), packaging 47, editor-preservation 21 (+3 skipped). New tests: `review-changes.test.ts` (one-line change, additions/deletions numbering, status vs title bookkeeping, list under a bookkeeping key, body never bookkeeping, no frontmatter, CRLF/final newline, unsafe HTML kept as text, too many lines, too different, no baseline, latest snapshot, status-only = not substantive, identical, corrupt snapshot counted, review refused/accepted by revision). `ReviewChanges.test.tsx`: 13 renderer tests covering these states, stale-comparison flag, opening records nothing, and review revision/conflict for both documents and tickets. Two existing tests were updated because the review call now includes the revision.
- `pnpm build:mcp` and `electron-vite build` succeed; the preload and main bundles contain the `document:changes` / `ticket:changes` channels.
- Read-only smoke run of core against this repository's own history: 68 reviewed tickets, 31 changed and 37 identical, about 3 ms each. Nothing under `.projectspace` was written.
- `pnpm preview:board` (stub host) in the browser pane: document and ticket Changes views in dark and light mode, and the unreadable-snapshot state. With the diff container forced to 300px, lines wrap with no horizontal overflow.

**Not verified:**
- The real Electron window was not launched, so the IPC round trip against disk was only checked through tests, the build, and the core smoke run. Nothing was packaged, and the packaging tests skipped their packaged-app checks.
- The page itself could not be made narrower than about 980px in the preview, because the board has its own minimum width. Only the diff container was tested narrow. Browser zoom was not tested.
- Keyboard: the switch and fold buttons are native controls with focus styles, but a full keyboard pass was not made by hand.
- If a reviewed source began with blank lines, the snapshot format drops them (existing behavior), so those would show as a change.
- macOS and Linux were not checked.

**For you to check:**
- Whether you accept the `diff` (jsdiff) dependency. Per D-019 it is a recommendation, not a decision you have made.
- In the app, open a document or ticket that is "Changed since review", switch to "Changes since review", and check the diff reads well in both themes. Then edit the file externally while it is open and confirm that "Mark reviewed" either uses the refreshed revision or is refused with an explanation.

### Revision after first look (2026-09-24)
From the user's feedback on a screenshot of this ticket's own Changes view:
- The visible "bookkeeping" tag on every lifecycle line (`status`, `updated_at`, each line of a `completion` block) was noise. It is gone. Those lines are dimmed further, one note above the section explains the dimming, and screen readers still hear "Added, bookkeeping" per line. The tagging itself was correct; only the presentation changed.
- The Read / Changes switch is now two icons (file, file-diff) with tooltips and hidden text names, so it keeps its accessible names.
- The switch is hidden for content that was never reviewed, since there is nothing to compare. Opening an unreviewed record while in Changes mode falls back to Read. Side effect: the "unreadable review history" notice only shows when at least one snapshot is readable, because review status reports fully unreadable history as unreviewed.

Checked with `pnpm check` (desktop now 281 passing, +1 skipped; 15 in `ReviewChanges.test.tsx`, including both "never reviewed" cases and a single section note), and in the stub preview. The real Electron window was still not launched.
