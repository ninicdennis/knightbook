# Choose a public support destination and who maintains it

## Intended outcome
Visitors who hit a problem have one named place to go, and someone is responsible for answering there.

## Acceptance criteria
- A support destination is chosen (for example GitHub Issues with an issue template, GitHub Discussions, or an email address) and it is reachable without special access.
- A responsible maintainer is named.
- If the destination is GitHub Issues, a bug-report template asks for app version, OS and architecture, reproduction steps and redacted errors, and warns against posting private project content, credentials or unredacted client logs.
- The choice is recorded as a numbered, dated decision in the specification.

## Notes
Spec §7 "Troubleshooting and support" and §11. Needed by the troubleshooting guide, footer, download-failure state and privacy page (support submissions are part of the data explanation).

## Progress (2026-10-21)

Built on the default the user was told about on 2026-10-21 (GitHub Issues, with GitHub's private vulnerability reporting for security), pending the user's confirmation.

- `.github/ISSUE_TEMPLATE/bug_report.yml`: version, OS, OS version and processor, AI client, steps, expected versus actual, and redacted errors; it opens by warning that issues are public and not to paste private project content, credentials, tokens or whole client logs, and sends security reports to private reporting.
- `feature_request.yml` for ideas, and `config.yml`, which turns off blank issues and links private vulnerability reporting and the AI-tools guide.
- The app shows its version nowhere, so the template points at the installer's file name; ticket b411cc60 adds the version to the app.
