# Flag a completion block that was edited outside the app

## Intended outcome
A Done ticket whose completion record was edited by hand is not presented as an attributable user decision.

## Acceptance criteria
- A completion whose recorded fields could not have been produced by either write path is reported as unattributed, or with an equivalent distinct signal.
- At minimum, `decision_source: direct_user_action` together with `recorded_by: agent` is treated as untrustworthy: a direct in-app action is recorded by the user by definition.
- The app and MCP agree on what they show for such a ticket.
- Decide and write down whether a stronger check is wanted (for example a fingerprint over the completion fields), including the argument for not doing so.
- `completion.ts`'s docblock is corrected to describe what is actually detected.

## Notes
Found running the specification validation scenario (ticket 2e4a254f), step 9, which asks explicitly for "handling of externally edited completion fields under the selected design".

Measured, both cases on the same ticket:
- completion block deleted entirely, `status: done` left behind -> `completion_unattributed=true`. Correct.
- block left in place but edited to `decision_source: direct_user_action` + `recorded_by: agent` -> `completion_unattributed=false`, and `ticket_list` returns the forged block as a normal completion.

`isUnattributedCompletion` (packages/core/src/completion.ts:92-94) is `status === 'done' && completion === undefined`, so only the first case can ever be caught.

This is not claimed to be a security boundary — the module already says a forged assertion is outside what a local design can prevent, and that is a reasonable position. The gap is narrower: the same docblock says completion recorded outside this path "is shown as unattributed", and that sentence is only true when the block is missing. Either the check or the sentence should change. The contradictory pair above is cheap to detect and is the obvious first case.
