# Release version script loads the changelog preset through pnpm's hidden hoisting

## Intended outcome
`apps/desktop/scripts/publishing/next-version.mjs` always uses the `conventional-changelog-conventionalcommits` version that `apps/desktop/package.json` declares (^9.3.1), whatever pnpm happens to hoist.

## Acceptance criteria
- The preset semantic-release loads is resolved from `apps/desktop`, not from `node_modules/.pnpm/node_modules`.
- With the hidden hoist pointing at `conventional-changelog-conventionalcommits@10.4.0`, `scripts/publishing/next-version.test.mjs` still passes.
- A fresh `pnpm install --frozen-lockfile` and an incremental `pnpm add` elsewhere in the workspace both leave the release tests passing.

## Notes
Seen on 2026-10-06: `pnpm --filter @knightbook/website add -D …` re-linked `node_modules/.pnpm/node_modules/conventional-changelog-conventionalcommits` from 9.3.1 to 10.4.0 (10.4.0 comes in through commitlint at the root). semantic-release's plugins then loaded the 10.x preset with `conventional-changelog-writer@8.4.0`, and every test in `next-version.test.mjs` failed with "conventional-changelog-conventionalcommits requires conventional-changelog-writer@9 or newer". `pnpm install --frozen-lockfile --force` restored 9.3.1 and the tests passed again, so a clean CI install is not affected today. The fix is likely passing the preset as a resolved config or path rather than the name `conventionalcommits`.
