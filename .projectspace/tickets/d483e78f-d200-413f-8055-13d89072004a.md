# Release version script loads the changelog preset through pnpm's hidden hoisting

## Intended outcome
`apps/desktop/scripts/publishing/next-version.mjs` always uses the `conventional-changelog-conventionalcommits` version that `apps/desktop/package.json` declares (^9.3.1), whatever pnpm happens to hoist.

## Acceptance criteria
- The preset semantic-release loads is resolved from `apps/desktop`, not from `node_modules/.pnpm/node_modules`.
- With the hidden hoist pointing at `conventional-changelog-conventionalcommits@10.4.0`, `scripts/publishing/next-version.test.mjs` still passes.
- A fresh `pnpm install --frozen-lockfile` and an incremental `pnpm add` elsewhere in the workspace both leave the release tests passing.

## Notes
Seen on 2026-10-06: `pnpm --filter @knightbook/website add -D …` re-linked `node_modules/.pnpm/node_modules/conventional-changelog-conventionalcommits` from 9.3.1 to 10.4.0 (10.4.0 comes in through commitlint at the root). semantic-release's plugins then loaded the 10.x preset with `conventional-changelog-writer@8.4.0`, and every test in `next-version.test.mjs` failed with "conventional-changelog-conventionalcommits requires conventional-changelog-writer@9 or newer". `pnpm install --frozen-lockfile --force` restored 9.3.1 and the tests passed again, so a clean CI install is not affected today. The fix is likely passing the preset as a resolved config or path rather than the name `conventionalcommits`.

## Handoff
**What changed:** `apps/desktop/scripts/publishing/next-version.mjs` no longer names the changelog preset (`preset: 'conventionalcommits'`), which semantic-release's commit analyzer and notes generator looked up from their own folders and so found through pnpm's hidden hoist. It resolves `conventional-changelog-conventionalcommits` from apps/desktop with `createRequire(import.meta.url).resolve`, exports the path as `PRESET_PATH`, and passes it as the plugins' `config`. Both plugins import a `config` that starts with `/` or a drive letter as a file, so the hoist is never consulted. `presetConfig` was undefined before and still is, so the preset's options are unchanged. A new test checks the plugin config has no `preset`, its `config` is `PRESET_PATH`, that path lies inside the copy `apps/desktop/node_modules` links to, and its major version is the one apps/desktop declares.

**How it was checked:**
- Reproduced the bug: with `node_modules/.pnpm/node_modules/conventional-changelog-conventionalcommits` relinked to 10.4.0 and the fix stashed, 8 of 14 tests in `next-version.test.mjs` failed (7 with "requires conventional-changelog-writer@9 or newer", plus the new test). The 6 that passed never generate notes.
- Same relink with the fix: 14 of 14 pass.
- `pnpm --filter @knightbook/website add -D left-pad@1.3.0` moved the hoist to 10.4.0 by itself, as in the ticket; 14 of 14 pass. After reverting that and `pnpm install --frozen-lockfile --force`, the hoist was back at 9.3.1; 14 of 14 pass.
- `pnpm check` passed (Node 22 in a cloud container; the repo asks for 24).
- Verifier: criterion 1 weakly covered (the test checked only the version, which the hoist also had); the test now also checks the resolved path lies inside apps/desktop's own link. Criteria 2 and 3 are install checks, not code criteria, settled by the manual runs above. Its probe confirmed both plugins import exactly the 9.3.1 file.

**Not verified:** not run on Windows, where `PRESET_PATH` is a `C:\…` path; import-from-esm's file-module check covers drive letters, but only Linux was run. Nothing asserts the plugins import `PRESET_PATH` itself; the verifier's probe showed it once. Packaged-app and website browser tests skipped (nothing packaged or installed); they do not touch this script.

**For you to check:** the next Release run chooses its version and writes notes as before.
