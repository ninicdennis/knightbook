# Settings

## Intended outcome
A settings icon opens a settings screen, starting with a light or dark choice and leaving room for more later.

## Acceptance criteria
- A settings icon in the header opens the screen.
- Light, Dark, and Follow system. The choice is stored as local app state, not in the project.
- Every screen is checked in both schemes, including the document reader styles, the badges and the dialogs.
- Adding another setting later needs no redesign of the screen.

## Notes
Lower priority. Only the dark scheme has been looked at so far; light mode is unverified.

## Handoff
**What changed:** A gear in the project header opens a Settings drawer with an
Appearance section: Light, Dark, Follow system. The choice lives in the host's
`app-state.json` beside the remembered-project list, never in a project.

- `src/shared/contract.ts` — `ColorSchemeChoice`, `AppSettings`, and
  `readSettings` / `saveSettings` on the bridge. `saveSettings` takes a patch, so
  a second setting cannot be reset by a screen that does not know about it.
- `src/main/app-state.ts` — settings are read and merged here. An unreadable or
  unrecognized value falls back to `auto` rather than being carried through.
- `src/main/window-theme.ts` (new) — sets Electron's `nativeTheme.themeSource`
  and every window's background. This exists because `createWindow` painted a
  hard-coded `#14161a`: in the light scheme the window frame would have flashed
  dark before the interface drew. It is applied before the first window opens,
  and repainted when the operating system changes while the choice is `auto`.
- `src/main/settings-ipc.ts` (new), `src/preload/index.ts` — the two handlers.
- `src/renderer/color-scheme.ts` (new) — Mantine's colour-scheme manager, backed
  by the value the host read at startup instead of by browser local storage.
- `src/renderer/components/SettingsDrawer.tsx` (new) — the screen. Laid out as
  named sections so another setting is a new section, not a redesign.
- `src/renderer/surfaces.css` (new) — both schemes' surface shades, shared with
  the board work on ticket 4c73d142.

**How it was checked:** `pnpm check` passes (lint, format, typecheck, 245 tests).
`electron-vite build` succeeds. Four new tests in `Settings.test.tsx` cover the
three choices, that the choice is saved as app state and touches no project
record, that `auto` is stored as an intent rather than as the scheme it happened
to resolve to, and that a failed save says the choice will not survive a restart.

Both schemes were exercised in the `preview:board` harness at 1280 and 760 wide:
the board, the document reader (headings, tables, code, blocked links, the
"included but missing" warning), the ticket detail dialog and the settings drawer.

**Not verified:**
- Nothing was run in the packaged Electron app. The window background and
  `nativeTheme` changes cannot be exercised in the browser harness at all, so the
  claim that light mode no longer flashes dark on launch is reasoned from the
  code, not observed. This is the main thing to try.
- Follow system was not watched across an actual operating-system theme change.
- The Welcome screen and the uninitialized-folder setup screen render before any
  header exists, so the settings gear is unreachable there. They follow the
  stored choice, but cannot be changed from them. Left as-is because the ticket
  asks for the icon in the header; say if you want it reachable earlier.
- The default is now Follow system. Previously the app was always dark, so on a
  machine set to light this will open light the first time.

**For you to check:** Open the packaged or `pnpm dev` app, switch to Light, close
and reopen it, and see whether the window is light from the first frame. Then walk
the screens listed above in the scheme you did not use while building them.
