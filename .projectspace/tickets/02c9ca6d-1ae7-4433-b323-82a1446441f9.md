# Reordering and removal

## Intended outcome
Manual backlog order and removing a document from the workspace are reachable by a user or an AI.

## Acceptance criteria
- An MCP operation and a board interaction that edit only backlog_order in the manifest.
- A documents_remove tool exposing the existing core removal.
- Duplicate or unknown order entries are reported, never deleted.

## Notes
The core library already has both operations. Neither has a tool or a UI. Until then, backlog order is creation order.

## Handoff

**What changed:** Both operations the core library already had are now reachable, by a user and by an AI.

- `packages/core/src/backlog-order.ts` (new) wraps `setBacklogOrder`, which wrote whatever it was given without checking. `reorderBacklog` places the ids you pass at the front and keeps manifest entries you did not mention behind them, so nothing is dropped. It refuses to write the same ticket twice, and refuses to place an id with no ticket. `inspectBacklogOrder` and `backlogOrderReport` say what is wrong with an order without changing it.
- `ticket_reorder_backlog` (MCP) sets the order. `project_get` now returns `backlog_order_problems`, so an agent reading the project sees a broken order rather than discovering it by surprise.
- `documents_remove` (MCP) exposes the existing `removeFromWorkspace`. It refuses a path that is not itself a manifest entry, which is the right answer for a document included through a folder: removing it means removing the folder, and that has to be deliberate.
- On the board, a backlog card's menu has an Order section â€” Move to top, Move up, Move down â€” offered only where it means something: only in Backlog, and never an option that would do nothing. The other columns are ordered by what has happened to their cards, not by a list anyone arranges. The window sends the whole backlog in its new order, so the host writes one list rather than the window guessing what the manifest held.
- `BacklogOrderProblems.tsx` (new) reports duplicates and unknown ids above the board and says plainly that nothing was removed and that reordering keeps them.
- `skills/projectspace/SKILL.md` documents both tools. The reorder entry says the ordering is the user's: ask what order they want rather than reprioritizing their board on your own reading of it. The "what you cannot do through MCP today" list lost the two entries this ticket delivered.

**Decision worth knowing:** reordering is menu-only. Drag-to-reorder within a column was not added â€” it needs a sortable layer over the existing cross-column drag, and the board's own comment already treats the menu as the path that has to work because drag alone is not reachable by keyboard. Adding drag on top is a separate, safe change.

**How it was checked:** `pnpm check` passes: lint, formatting, typecheck and 361 tests, 0 failures. 8 new core tests in `packages/core/src/backlog-order.test.ts` and 8 new renderer tests in `apps/desktop/src/renderer/BacklogOrder.test.tsx` cover each acceptance criterion: that reordering changes only `backlog_order` and no other manifest field or the body, that `ticket_next` then follows it, that unmentioned entries are kept, that a duplicate write and an unknown id are refused without writing, that an existing duplicate or unknown entry is reported and left in place, that the board sends the whole backlog, that no dead menu item is offered, and that a refusal is explained.

Both MCP tools were also called against this real project through a freshly built server, with inputs chosen to be refused: `ticket_reorder_backlog` with an id that has no ticket, and `documents_remove` with a document that is included via its folder rather than by itself. Both were refused with the right message, and `git status .projectspace/project.md` is clean afterwards.

**Not verified:** The board's own order was deliberately not changed. Reordering is the user's decision â€” the same rule this ticket writes into the skill â€” so no successful `ticket_reorder_backlog` or `documents_remove` call was made against this project; success is covered by the core tests and the renderer tests, not end to end. Not run in a real Electron window. A `backlog_order` containing an id that is neither a duplicate nor unknown but points at a Done ticket is treated as a normal entry, which is intended but untested.

**For you to check:** Reorder the backlog from the board and confirm "Next up" follows it, and that the project file's `backlog_order` is the only thing that changed. Judge whether menu-only reordering is enough or whether you want to drag cards within a column. Try `documents_remove` from an AI tool on a document included through `docs` and see whether the refusal tells you what to do instead.

## Sent back from verification: a duplicate was being deleted (2026-09-20)

**What was wrong:** QA found that reordering silently removed an existing duplicate, against the criterion "Duplicate or unknown order entries are reported, never deleted". Starting from `[A, A, unknown, B]` and asking for `[B, A]` gave `[B, A, unknown]`: the second A was gone and its warning cleared with it. The board used the same function, so it had the same bug. The report is accurate and reproduced.

The cause was in `reorderBacklog`: it built `placed = new Set(order)` and kept `backlog_order.filter(id => !placed.has(id))`. Filtering by id removes *every* entry for a requested ticket, not the one being placed. My test for this ("keeps entries the caller did not mention") used a manifest with no duplicates, so it never exercised the case it was meant to protect.

**The fix:** placing a ticket now consumes one of its entries rather than all of them. The manifest list is copied and one matching entry is spliced out per requested id, so an existing duplicate survives the reorder and is still reported.

**A second change this forced:** `sortByBacklogOrder` built its rank map with `new Map(order.map(...))`, where a later entry overwrites an earlier one — so the *last* occurrence of a duplicated id decided its position. Once duplicates survive a reorder, that would invert the order just requested: placing A first in `[A, B, A]` would have sorted A after B. The rank map now keeps the first occurrence. This is a behaviour change for any manifest that already contains a duplicate, and it is the behaviour the board's warning already described ("the first position is the one that counts").

**How the fix was checked:** three new core tests — the exact QA scenario asserting `[B, A, A, unknown]` with both warnings still reported, that a surviving duplicate does not invert the requested order, and that a duplicated entry is read at its first position. `pnpm check` passes: 364 tests, 0 failures.

Reproduced end to end through the MCP server against a throwaway project, the way QA did. Against the packaged pre-fix build: `[B, A, unknown]` with `duplicates: []`. Against a build with the fix: `[B, A, A, unknown]` with the duplicate and the unknown id both still reported, unchanged after re-reading the project from disk, and the board order still B then A.

**Still not verified:** the same as before — not run in a real Electron window, and no successful reorder was made against this project's own board, because that ordering is yours to decide.
