# Copy the MCP helper to a persistent location when running as an AppImage

## Intended outcome
A Linux user running the AppImage can copy the MCP configuration once and have it keep working after the app closes and across AppImage updates, so AppImage can be offered alongside deb (D-028).

## Acceptance criteria
- When the app runs as an AppImage (`APPIMAGE` is set), it copies `node` and `server.mjs` from its resources into a persistent folder under the app's user data, replacing them only when they differ, and keeps the executable bit.
- `mcpLaunchCommand` names that persistent copy under AppImage and is unchanged everywhere else.
- A copy that fails is reported in the MCP panel as a failure, not as a working configuration.
- Tests cover: not an AppImage (unchanged), first copy, identical copy skipped, changed copy replaced.
- Checked on Linux with a real AppImage: configuration copied, app closed, the MCP server starts from the client. If this could only be tested in CI or not at all, say so.
- The AppImage limit is documented: after an update, a client keeps the old server until the new AppImage has been opened once.

## Notes
Today `apps/desktop/src/main/mcp/mcp-resources.ts` builds the command from `process.resourcesPath`, which under AppImage is inside `/tmp/.mount_…` and changes every launch. Technical design section 2 already says to put the helper at a persistent location for portable Linux formats. AppImage stays out of released targets until this is done and checked.

## Handoff
**What changed:**
- New `apps/desktop/src/main/mcp/appimage-runtime.ts`. When `APPIMAGE` is set, it copies `node` and `server.mjs` from the mounted resources into `<user data>/mcp-server/` after startup, in `index.ts`, after the settings carry-over.
  - A file with identical bytes is left alone.
  - A changed file is written to a temporary file and renamed over the old one.
  - `node` is set to 0755.
- `mcp-resources.ts`: the new `mcpRuntimeDir()` gives the persistent copy under AppImage and the resources folder otherwise. `mcpLaunchCommand` uses it.
- `mcp-status.ts` checks that same folder, and `McpStatusView` gains `runtimeProblem`.
- The footer reads **MCP runtime not copied** when the copy failed and no client is observed, and the details always show "Not copied — <reason>". The board preview has `?mcp=not-copied`.
- Docs: technical design section 2 has a new subsection, "The AppImage copy as built (2026-10-06)", which includes the known update limit. `docs/proposals/platform-support.md` is updated to match.
- The folder is `mcp-server/`, not `mcp-runtime/`. The verifier found that `<user data>/mcp-runtime/` already holds the shared server's session records. A test now keeps the two folders apart.

**How it was checked:**
- `pnpm check` passed: desktop 661 tests (4 skipped), core 275, mcp 47.
- New tests:
  - `appimage-runtime.test.ts` covers the first copy, an identical copy left untouched (same inode and mtime), only the changed file replaced with no leftover temporary file, the executable bit (skipped on Windows, runs on Linux CI), the folder kept apart from the sessions folder, and a failed copy reported with its reason.
  - `mcp-resources.test.ts` checks the command under AppImage and outside it, and that it never contains `.mount_`.
  - `mcp-status.test.ts` shows a failed copy reaching the status view.
  - `mcp-status.test.tsx` and `McpFooter.test.tsx` show the footer label and details text.
- Board preview with `?mcp=not-copied`, looked at 1600px dark and 800px light. The reason appears once, on the runtime line.
- Verifier, before the fixes above: covered 3 (copy behaviour, launch command, required test cases) and weakly covered 1 (the failure report). Since then the missing link from main process to status view has been tested, the folder clash fixed, and the comments and docs corrected to say the configuration stays on offer after a failure. 2 criteria are not code: the real-AppImage check (not done) and the docs (done).

**Not verified:**
- **Not run from a real AppImage on Linux.** CI builds only the deb, and nothing in the repo mounts an AppImage or sets `APPIMAGE`. To settle it: on Linux, `pnpm build:mcp`, then `pnpm --filter @knightbook/desktop exec electron-builder --linux AppImage`. Run the AppImage, copy the MCP configuration, quit, and start the client. Repeat after swapping in a rebuilt AppImage. AppImage stays out of released targets until then.
- The executable-bit test has not run on Linux yet, because it skips on Windows. It will run in Linux CI.
- If a client is connected to the copy from an earlier launch, the footer still says connected or available, and only the details say "Not copied". This is deliberate, because an observed connection wins, as it does for a missing runtime.
- Every AppImage launch reads the whole `node` binary twice to compare it. This is off the window's critical path and was not measured.

**For you to check:**
- Run `pnpm preview:board`, then open `?mcp=not-copied` and click the footer.
- If you can, try a real AppImage on Linux.
