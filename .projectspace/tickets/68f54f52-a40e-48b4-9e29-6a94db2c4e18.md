# Copy the MCP helper to a persistent location when running as an AppImage

## Intended outcome
A Linux user running the AppImage can copy the MCP configuration once and have it keep working after the app closes and across AppImage updates, so AppImage can be offered alongside deb (D-028).

## Acceptance criteria
- When the app runs as an AppImage (`APPIMAGE` is set), it copies `node` and `server.mjs` from its resources into a persistent folder under the app's user data, replacing them only when they differ, and keeps the executable bit.
- `mcpLaunchCommand` names that persistent copy under AppImage and is unchanged everywhere else.
- A copy that fails is reported in the MCP panel as a failure, not as a working configuration.
- Tests cover: not an AppImage (unchanged), first copy, identical copy skipped, changed copy replaced.
- Checked on Linux with a real AppImage: configuration copied, app closed, the MCP server starts from the client. If this could only be tested in CI or not at all, say so.
- The AppImage limit is documented: after an update, a client keeps the old server until the new AppImage has been opened once.

## Notes
Today `apps/desktop/src/main/mcp/mcp-resources.ts` builds the command from `process.resourcesPath`, which under AppImage is inside `/tmp/.mount_…` and changes every launch. Technical design section 2 already says to put the helper at a persistent location for portable Linux formats. AppImage stays out of released targets until this is done and checked.
