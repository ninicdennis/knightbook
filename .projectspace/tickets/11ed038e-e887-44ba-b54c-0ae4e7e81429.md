# Isolate invalid records

## Intended outcome
A malformed ticket or unresolved conflict marker no longer fails the whole project load.

## Acceptance criteria
- Valid tickets still render; each invalid record is listed with its file and reason.
- ticket_list reports the same problems. Nothing is rewritten automatically.
- Writes to an invalid record stay blocked (design section 3).

## Notes
listTickets currently throws on the first invalid record, which turns the whole project into the could-not-open screen.

## Handoff
**What changed:** A malformed ticket or an unresolved merge conflict no longer fails the whole project. Core has a new listTicketRecords that returns the tickets that loaded plus a problem (file, code, reason) for each file that did not; listTickets is now the loaded tickets only. The board opens with what loaded and shows a banner: "N records could not be read, so they are not on the board", with a Show files toggle listing each file and its reason, and the text that nothing was changed or rewritten and the person should fix the file in their editor and refresh. It offers no repair. ticket_list now returns { tickets, problems } (it used to return a bare array); project_get reports ticket_problems so a broken ticket never looks like zero tickets; ticket_next never chooses an unreadable ticket and reports the problems. A ticket that depends on an unreadable one is now told "whose file could not be read", not "does not exist". Search reports the unreadable ticket files. updateTicket now validates the current file before changing anything, so writes to an invalid record stay blocked; previously it only validated after writing.
**How it was checked:** pnpm check green (core 58, desktop 109, packaging 27). Tests cover conflict markers, a bad status, a mismatched id and broken YAML; that bad files are byte-identical after listing, selection and search; that updates are refused with the bytes unchanged (I removed the new guard and the schema case failed); and the same flow end to end through the packaged MCP server. The banner was viewed in real Chromium via the preview harness (?problems). The packaged build launches cleanly with a throwaway profile.
**Not verified:** the packaged window was not driven with a real corrupt ticket; only a preview harness and tests show the banner. A corrupt project.md is still fatal (this ticket covers tickets only). Recording a review for an unreadable ticket is not blocked at the core level, only unreachable from the UI and MCP. Light mode.
**Behavior change to know about:** ticket_list's output shape changed from an array to { tickets, problems }. Any AI client or saved instruction that assumed an array needs the new shape.
**For you to check:** in a scratch copy of a project, add merge-conflict markers to one ticket file (or set its status to something invalid) and open it in the app. The board should still open with the other tickets, with the banner listing that file, and the file itself should be unchanged. Then fix the file and Refresh: the banner should go away and the ticket appear.
