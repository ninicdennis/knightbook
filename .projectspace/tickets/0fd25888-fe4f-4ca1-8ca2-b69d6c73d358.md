## Intended outcome
After a release is published, the Release workflow writes the release's entry in the website's release data and pushes it to a branch, so the maintainer only reviews and merges it instead of copying sizes and checksums by hand (PR #28 did that for 0.3.0).

## Acceptance criteria
- After publishing, the Release workflow writes the new release's entry into `apps/website/src/download/releases.json` from the published release: version, preview or stable from whether it is a prerelease, the UTC publish date, the notes link, and for each of the four launch targets the file name, URL, size, and SHA-256 from the release's `SHA256SUMS.txt`.
- Known issues, each target's minimum system and its signing are copied from the newest release that was not withdrawn, for the maintainer to correct in the pull request.
- The entry passes the site's release-data validation, and the rest of the file is unchanged byte for byte.
- A missing installer or checksum stops it with a message naming every problem, and nothing is written.
- Running it again for a release already listed changes nothing.
- The workflow pushes the change to a `website/release-<version>` branch, never to `main`, keeps a branch an earlier run left, and links to open the pull request in the run summary. It opens no pull request itself, because one opened with the workflow token runs no checks.
- The decision and the new step are recorded in the specification, technical design and release automation docs.

## Notes
Decision D-055. Denny asked "Would it be possible to automate this at all?" on 2026-11-11. See [release automation](../../docs/proposals/release-automation.md).

## Handoff
**What changed:** New `apps/website/src/download/add-release.mjs` (no dependencies) builds the entry from `gh release view --json tagName,publishedAt,isPrerelease,assets` output and `SHA256SUMS.txt`, and puts it first in `releases.json`. A new `website` job at the end of `.github/workflows/release.yml` runs after `publish`, checks out the latest `main`, runs the script, and pushes `website/release-<version>` with a link in the run summary to open the pull request. D-055 in the spec; technical design and release automation docs updated.
**How it was checked:** `pnpm check` passes (website 267 tests, desktop 682). `add-release.test.ts` (13 tests) builds an entry for a fictional 0.4.0 published at 03:15 UTC (dated the next day), with an `amd64` deb, and runs it through `parseReleaseData`; copies fields from a 0.3.0 when a newer 0.3.1 is withdrawn and has different known issues and signing; refuses a missing macOS x64 installer and a missing Linux checksum in one message; refuses a non-version tag and an empty list; runs the command line twice on a temp copy and checks the second run leaves the file byte-identical; checks the checked-in file round-trips through the writer unchanged; and reads the workflow to check the job needs `publish`, runs this script and pushes only `refs/heads/$BRANCH`.
**Not verified:** The workflow job has not run on GitHub: the `gh` calls, the push with the job token, keeping an existing branch, and the summary link are only checked by reading. That nothing is written on a refusal follows from the write coming after the entry is built, not from a test of the file. The verifier agent was not run (it is not registered in cloud sessions); criteria were checked against the tests above by hand. The workflow YAML was parsed but not run through actionlint.
**For you to check:** At the next release, the run summary's "Website update" section should link to a pull request for `website/release-<version>`. Open it, correct the copied known issues (and the installation guide if it names versions), and merge to deploy.
