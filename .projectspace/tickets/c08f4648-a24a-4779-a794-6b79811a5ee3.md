# Put interim app screenshots on the homepage

## Intended outcome
The homepage shows real screenshots of Knightbook in its two image places (the hero board and the document beside "Files you can keep using"), in light and dark, while the fictional sample project from [90c7aba5](90c7aba5-c41d-436d-a4db-8519cd52c4cf.md) is still to come.

## Acceptance criteria
- The hero shows a real board screenshot and "Files you can keep using" a real document screenshot, replacing the empty slots.
- Each has a light and a dark capture, chosen by the visitor's system scheme without JavaScript.
- Images are resized and compressed at build time into several widths, with intrinsic dimensions set; the hero image loads eagerly, the document lazily.
- Each image has alt text that says what it shows; the copy around it does not depend on the image.
- The captures show Knightbook's own project, so both stay marked as drafts that a production build refuses, pointing at 90c7aba5 for the fictional replacement.
- No capture shows a personal path, username or secret.

## Notes
Decided with the user on 2026-10-20: use the screenshots taken from Knightbook's own board for now, and replace them with a fictional sample project before public launch (90c7aba5 stays open for that). Source captures were 2880×1800, taken from a copy of the project.

## Handoff

**What changed.** On branch `feature/website-screenshots-te1zus`.
- `apps/website/src/home/screenshots/`: the board and Documents captures, light and dark, scaled from 2880×1800 to 1920×1200 PNGs (about 130 KB each).
- `home/Screenshot.astro` replaces `ScreenshotSlot.astro`. Sharp resizes each capture to WebP at 640, 960, 1280 and 1920px at build time. A `<picture>` uses the dark set under `prefers-color-scheme: dark` and the light set otherwise, with no script. The `<img>` has width 1280 and height 800, `sizes`, alt text, and a caption that keeps the draft marker. The hero loads eagerly, the document lazily.
- `HomeHero.astro` and `FeatureSections.astro` use it. The document image is now 16:10, where the empty slot was 4:3.
- `drafts.ts`: the two screenshot drafts now say they are interim captures of Knightbook's own project, to be replaced by 90c7aba5. A production build still refuses them.
- The technical design has a "Homepage screenshots" entry under "The public website".
- The Website plan's phase 2 now includes this ticket. 90c7aba5 is unchanged and stays in Backlog.

**How it was checked.**
- `pnpm check` passes (after `pnpm build:mcp`, as CI runs it). Website: 101 tests, `astro check` 0 errors. Core 275, MCP 47, desktop 648 (4 skipped), editor-preservation 21 (3 skipped), packaging 46 (9 skipped, nothing packaged).
- A new test in `home/home.test.ts` builds the real site and checks, for both images, that:
  - the dark `<source>` carries the `prefers-color-scheme: dark` media query;
  - the dark and light srcsets each run from 640w to 1920w and are different files;
  - the alt text is there;
  - width and height are 1280×800;
  - the hero is eager and the document lazy.
  The existing tests still check that the drafts are exactly the listed set, that a production build fails naming all six, and that the page has no `<script>`.
- **Browser, production build (Chromium):**
  - 1440 light: hero image 624px beside the copy, 640w WebP fetched.
  - 1440 dark: the dark board and dark document were fetched.
  - 390 light: stacked under the actions, no sideways scroll.
- I looked at all 11 source captures myself: no personal path, username or secret.
- Coverage pass, done by hand: the `verifier` agent needs the knightbook MCP tools, which were not connected in this session. Criteria 1, 2, 3 and 5 are covered by built-HTML assertions, and file sizes are not asserted. Criterion 4's "copy does not depend on the image" and criterion 6 are not code criteria; I checked them by reading.

**Not verified.**
- Legibility. At the hero's 624px the board's card text is small. The brief allows a detail crop for phones, and none was added.
- Every capture shows "MCP not connected" in the status bar, and the board shows real planning text. The fictional retake (90c7aba5) should fix both.
- The captures were not taken from the installed release build, and I don't know which build they came from.
- 1024, 768 and 320 widths, 200% zoom, and high-DPI srcset selection were not looked at.

**For you to check.**
1. Run `pnpm preview:website` and look at the hero and "Files you can keep using" in both schemes.
2. Decide whether the board is readable enough at hero size, or should get a detail crop.
3. Check that the alt texts describe what you want said.
