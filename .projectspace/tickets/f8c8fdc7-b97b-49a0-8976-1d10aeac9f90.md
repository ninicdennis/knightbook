# Archive tickets without deleting project history

## Intended outcome
Keep the working board manageable as the project grows while retaining tickets as searchable records of decisions, implementation, and acceptance. Users can archive one ticket or a column's tickets, browse them in an Archive tab, and restore them.

## Acceptance criteria
- Add Archive alongside Board and Documents. Show archived tickets in a compact, browsable list with title, retained workflow status, and archive date; opening a result shows the full existing ticket detail and history.
- Provide Archive on individual ticket menus/details and Archive all in this column on column menus, including Done. Bulk action confirmation names the column and exact target count, and explains that records are preserved. When archiving unfinished work, make its retained status and removal from active suggestions explicit.
- Persist archive metadata separately from the four workflow statuses. Retain canonical ticket files, stable IDs, full bodies, links, dependencies, completion provenance, and review snapshots. Archiving is neither deletion nor a completion decision and cannot fabricate acceptance.
- Archived tickets disappear from Board columns and active counts and cannot be suggested by ticket_next. Show an archive count separately. They remain readable by ID and available as dependency targets: an archived Done/Verification prerequisite retains its existing readiness meaning; an archived unfinished prerequisite does not become satisfied and is explained as archived when it blocks work.
- Restore an individual archived ticket to its retained workflow status without reopening Done, changing completion provenance, or duplicating its file. Preserve backlog ordering where applicable. Define how ordinary edits/status changes on archived tickets work; default to restoring before resuming work.
- Global header search includes archived tickets with an Archived label and a clear All / Active / Archived scope. Archive defaults to archived-only search across titles and descriptions. Opening a result does not restore it. Integrate with the header search ticket when available, without coupling core archive storage to that UI.
- Use shared core operations for desktop and MCP. Expose archive/restore and explicit archive filtering through MCP; keep default board/list views active-only, preserve direct reads, report archived state, and document changed list/count/search semantics in the workflow skill.
- Use existing write locks and expected revisions. Bulk operations act on a captured set of IDs/revisions, do not include tickets added later, and report exact successes, conflicts, and failures. Define partial-success/retry behavior without claiming a multi-file atomic transaction. Project switching cannot redirect an in-flight operation.
- Archive/restore bookkeeping alone must not invalidate content review or lose review evidence. Substantive changes must still be detected. Existing tickets without archive metadata remain active and readable without a destructive migration.
- Verify individual and bulk archive, restore, app restart, external/MCP updates, stale revisions, partial bulk failure, retained dependencies/provenance/review state, archived search, and exclusion from next-ticket suggestions. No source files are deleted.

## Research and implementation notes
Research date: 2026-09-19. Observed code: packages/core/src/schema.ts defines four statuses and no archive metadata; tickets.ts lists all canonical ticket files; dependencies.ts treats Verification/Done as satisfied. packages/core/src/search.ts already searches title/body and documents with case-insensitive matching and a bounded result set. packages/mcp/src/tools.ts currently derives listing, counts, and next-ticket selection without archive awareness. Extend those consumers consistently rather than adding a fifth workflow status or moving files out of the ticket tree.

UI entry points: apps/desktop/src/renderer/components/ProjectHeader.tsx, Board.tsx, and App.tsx. Desktop operations cross the shared contract/preload/IPC boundary. Review handling in packages/core/src/review.ts compares ticket source, so archive metadata needs explicit coverage to avoid a misleading Changed since review badge.

## Handoff
**What changed:**

*Core (`packages/core`)* — archiving is an optional `archived: { archived_at }` on the ticket, and nothing else. Deliberately **not** a fifth status: `status` is left untouched, so the retained status and the real status are the same field and cannot drift, and restoring is removing the metadata rather than replaying a remembered value. Its absence means active, so existing tickets need no migration.
- `archiveTicket` / `restoreTicket`, both taking the expected revision. Archiving twice is refused rather than quietly moving the archive date.
- `selection.ts` skips archived tickets, so `ticket_next` cannot propose one. Skipped, not listed as ineligible — the ineligible list is about work the user can see.
- `dependencies.ts` gained `prerequisite_archived`. An archived **unfinished** prerequisite does not start satisfying its dependents, and says it was archived rather than leaving the reader hunting for a card that is not on the board. An archived Verification/Done prerequisite goes on satisfying, because archiving did not undo it.
- `review.ts`: `archived` joins `status` in the fingerprint's bookkeeping set, so filing a ticket away cannot cost a real review its evidence.
- `ticket-search.ts` gained a `SearchScope` of `active` (default) / `archived` / `all`, and each hit reports `archivedAt`.

*MCP (`packages/mcp`)* — `ticket_archive` and `ticket_restore`; `ticket_list` takes `archived: exclude | only | all` and defaults to excluding; `project_get` reports `archived_ticket_count` separately from the four statuses; every summary carries `archived`. `ticket_read` is untouched, so an archived ticket stays directly readable.

*Desktop* — an Archive tab beside Board and Documents with the count on it, a compact list showing each ticket's retained status and archive date, Restore, and opening the full detail. Archive on the card menu; "Archive all in this column…" on a new column menu. The bulk confirmation names the column and the exact count, says nothing is deleted, and warns explicitly that archiving unfinished work neither completes nor accepts it. Search gained an Active/Archived/All scope, archived hits carry an Archived badge, and searching from the Archive tab defaults to the archive.

*Docs* — a new "Archiving" subsection in the technical design covering the metadata choice and recovery behaviour; the workflow skill documents the tools, the changed `ticket_list` default, the counts, and "restore before resuming work".

**How it was checked:**
- Core: 168 tests (16 new in `archive.test.ts`). MCP: 20. Desktop: 240 (14 new in `Archive.test.tsx`). Packaging: 28. `oxlint`, repo-wide `prettier --check` and `tsc --noEmit` in all four packages: clean.
- Drove the real Electron window against a throwaway project: archived tickets absent from the board and its counts, the tab reading "Archive 2", restore returning a ticket to Backlog **in its original position**, the bulk dialog reading "Archive all in Backlog? This will archive 4 tickets from Backlog", and search finding an archived ticket only under All/Archived with the badge showing. Screenshots taken at each step.
- Drove the MCP tools over stdio end to end: archive, the three list filters, separate counts, a dependent correctly staying blocked with the archived explanation, `ticket_next` skipping it, direct read while archived, double-archive refused, restore.
- Two bugs found and fixed during the work, both now covered: opening an archived row did nothing, because the detail lookup only searched the board; and bulk archive left the project switcher enabled, so a switch could have redirected an operation already in flight. I confirmed the detail test genuinely fails without its fix.

**Not verified:**
- No `pnpm pack:dir` run on this branch, so the packaged app has not been built with these changes. I built with `electron-vite` and ran the unpacked app.
- macOS and Linux: Windows only.
- Not load-tested. Bulk archive is sequential; a column of hundreds would be slower than anything I exercised (largest run was 4).
- Restore is one ticket at a time. Nothing restores a whole archive at once, which I read as out of scope for this ticket rather than an omission — say if you disagree.

**A decision worth challenging:**
Archiving does not lock a ticket. You can still move or edit an archived ticket through its detail view, and the skill says to restore before resuming work rather than the app refusing. I took "default to restoring before resuming" as guidance rather than enforcement, since a hard block would be the first thing in this app that forbids an edit outright. Easy to tighten if you would rather it refused.

**For you to check:**
1. Open the app, archive a card from its menu, then archive a column, then restore from the Archive tab.
2. The bulk confirmation is the wording most worth reading closely — it is the sentence someone agrees to before moving work they are not inspecting one item at a time.
3. Confirm you are happy that archiving is metadata rather than a fifth column, since that choice is what everything else here rests on.
