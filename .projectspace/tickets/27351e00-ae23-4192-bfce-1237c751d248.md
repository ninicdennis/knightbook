# Release version tests time out on the Windows CI runner

## Intended outcome
The release-version tests pass on GitHub's Windows runner, so a merge to `main` can be packaged and released again.

## Acceptance criteria
- Each test in `apps/desktop/scripts/publishing/next-version.test.mjs` has a time limit that fits running real semantic-release and git on a slow runner, not vitest's default 5 seconds.
- Removing a test's temporary repository retries while Windows still holds its files, so one slow test cannot fail the next ones with `EBUSY`.
- The CI check passes on Windows.

## Notes
Found 2026-10-02. Release run 36963265976 for #37 (`817e061`) failed in the Windows check on both attempts: tests in that file hit "Test timed out in 5000ms". On the second attempt the timed-out tests left git holding their temporary folders, and `rm` failed with `EBUSY: resource busy or locked`, failing four more tests. Linux and macOS passed. Locally on Windows each test takes about 1 to 2 seconds; the runner is several times slower. Nothing was packaged or published for #37, so the next release carries its change.

## Handoff

**What changed.** PR #39, branch `feature/fix-release-test-timeouts`. In `next-version.test.mjs`:
- **Time limit:** the "version a merge to main releases" tests get a 60-second limit (`SLOW_RUNNER_TIMEOUT`), with a comment explaining why.
- **Cleanup:** `afterEach` now removes the temporary repository with `maxRetries: 10, retryDelay: 200`.

The branch has a second commit that removes `apps/website/.astro/` files committed by mistake. They were leftovers from the website branch. The diff against `main` is only the test file and this ticket.

**How it was checked.**
- Locally on Windows, all 29 publishing tests pass. The suite takes about 24 s, and each test 1 to 2 s.
- Manual CI run 37018696256 on the branch (Windows, macOS, Linux) succeeded: all three `Check` jobs and all three `Package and test the app` jobs passed.
- On the Windows runner, `next-version.test.mjs` passed 13 tests in 36 s. Individual tests took 2.5 to 5.2 s. "Releases a minor version for a feature and a patch for a fix" took 5.2 s, which is over the old 5 s limit and explains the failures.

**Not verified.**
- The `EBUSY` retry has not been seen to retry, because no test timed out in the passing run. It is there for the case that caused the cascade.
- The verifier was not run for this small test-only change.
- The Release workflow on `main` will run these tests again when #39 merges.

**For you to check.**
1. Merge #39. The Release run should pass on Windows and publish **v0.1.1**, which also carries #37's change.
2. Then merge #38 (the website).
