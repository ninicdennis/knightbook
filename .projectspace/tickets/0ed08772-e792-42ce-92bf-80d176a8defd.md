# Write the connecting-an-AI-tool guide, tested with one named client

## Intended outcome
`/docs/connecting-ai/` gets a user from the installed app to a working MCP connection in at least one named client, following steps that were actually tested.

## Acceptance criteria
- Explains MCP as optional, the bundled server, and the workflow skill as separate setup steps: tools give capabilities, the skill teaches the workflow.
- Uses the configuration copied from the installed app as the source of paths. There is no hard-coded developer checkout path, and no Windows command shown for other platforms.
- At least one client (for example Claude Code, Codex or OpenCode, which the app can already copy configuration for) is tested end to end: add the configuration, restart, run the read-only check prompt, and read the same project after closing the desktop window.
- Each client section records the app version, client version and test date.
- Covers one connection per project root, several local checkouts of the same project, moving a project, reconnecting after an app update, and working with the window closed.
- States that a "connected" indicator does not prove the client follows the workflow skill.
- Clients that were not tested are not named as supported.

## Notes
Spec §7 "Connecting an AI tool" and §10 launch criteria. Check client configuration locations against each client's current documentation while writing, not from memory.

## Handoff
**What changed:** `/docs/connecting-ai/` is written, for Knightbook 0.2.0: MCP as optional, the server and the workflow skill as two steps, allowing a project, copying the configuration, adding it to Claude Code's user settings (`~/.claude.json`, top-level `mcpServers`), installing the skill, the read-only check prompt, what "connected" does not prove, working with the window closed, several copies, moving a project, older `--root` setups, and updating. Codex, OpenCode and other clients are named only as offered by the copy menu and not tested. A "What has been tested" section records versions, date and exact scope.
**How it was checked:** Claude Code 2.1.306 on Ubuntu 24.04 (container, no desktop), 2026-10-21: `claude mcp list` read an entry in the copied shape from top-level `mcpServers` in `~/.claude.json` and showed it connected. With `pnpm pack:dir`'s Linux build, Claude Code started the bundled `resources/mcp/node` and `server.mjs` with `--registry`, and answered the check prompt with the right project name, path, two documents and one ticket, changing nothing; the window was never open. `pnpm check` passes; first-use.test.ts checks the two-step section, no developer paths or Windows program/drive in the example, the tested versions and date, the topic sections, the "connected" caveat and no "supported". Verifier: 5 covered, 1 weakly covered, 1 manual and partly met.
**Not verified:** Not with the published installer (v0.2.0 was still building). The project was allowed by writing `mcp-access.json` directly, not with the switch. The skill was not installed. The window was never opened, so "read the same project after closing the window" was not exercised as such. Not on Windows or macOS. Claude Desktop, Codex and OpenCode not tried.
**For you to check:** On Windows with v0.2.0, follow sections 1 to 4 with Claude Code: allow the project, copy the configuration, add it to `C:\Users\<you>\.claude.json`, install the skill, run the check prompt, then close Knightbook and ask again. If it works, say so and the "What has been tested" section can add Windows.
