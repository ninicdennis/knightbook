# Core tests time out under heavy load

## Intended outcome
A deliberate decision on how much time filesystem-backed core tests get, so a slow shared runner does not fail tests whose behaviour is fine.

## Acceptance criteria
- The chosen per-test timeout for `packages/core` (and whether it applies to the other packages) is recorded with its reasoning.
- Under the load described below, `pnpm --filter @knightbook/core test` either passes or fails for a reason other than Vitest's default 5s timeout.
- The timeout is not raised so far that a real hang takes minutes to surface.

## Notes
Found on 2026-09-24 while working "Make the concurrent-writer test independent of machine load". With 24 CPU-bound Node processes running on a 16-core Windows machine, three of four runs of the core suite failed: 10 to 29 tests, every one with "Test timed out in 5000ms", spread across archive, verification, checkout-access, ticket-types and others. Without that load the suite passes in about 4s.

That load is synthetic and harsher than a normal CI runner, so this is evidence that the budget is tight, not that CI fails today. `packages/core/vitest.config.ts` sets no `testTimeout`, so every test gets Vitest's 5s default, while each one creates and deletes a real temporary project. `experiments/packaging/vitest.config.ts` already sets 120s for its own reasons.

The concurrent-writer test got its own 30s budget in that ticket, because it can legitimately wait out the 5s lock timeout. This ticket is about the rest of the suite.

## Archived without work (2026-09-24)
The user decided this is not needed. Knightbook is not a load-sensitive application: at most two processes (the app and the MCP server) write to a project, and the timeouts appeared only under deliberately extreme synthetic load, not in CI or normal use. Restore this if CI ever fails with "Test timed out in 5000ms" in `packages/core`.
