# No default menu bar above the board

## Intended outcome
The stock Electron menu strip — File, Edit, View, Window, Help — is gone from above the board, without quietly taking the keyboard behaviour that hangs off it.

## Acceptance criteria
- On Windows and Linux the window has no visible menu bar, and there is no bar that reappears when Alt is pressed.
- Copy, paste, cut, select all and undo still work everywhere text can be selected or typed, including the search field and the dialogs. Those work today because the default menu registers their accelerators; whatever replaces the menu must keep them.
- The window keeps a way to reload and to open developer tools in a development run. Say where it went. A packaged build does not need to expose either.
- macOS keeps its application menu, because the platform requires one. What it contains is a deliberate choice, not the Electron default, and it must not offer items the app cannot do.
- Nothing in the board moves or resizes as a side effect. Removing the bar gives the content back its vertical space and changes nothing else.

## Notes
`createWindow` in `apps/desktop/src/main/index.ts` never calls `Menu.setApplicationMenu`, so Electron builds its default menu. It is the only part of the window that was not designed, it names actions this app does not have, and it sits above a header that already carries the project, the view switch and search.

`Menu.setApplicationMenu(null)` is the whole removal, but on Windows and Linux it also unregisters the edit accelerators, which is the part worth getting right: a board where Ctrl+C has silently stopped working is worse than a menu nobody looks at. A small menu built from the `editMenu` role, hidden with `autoHideMenuBar` and `setMenuBarVisibility(false)`, keeps the accelerators without showing anything; an empty menu does not. Confirm which of these actually behaves that way in this Electron version rather than taking it from documentation.

## Verification
Launch the app and confirm the strip is gone and that Alt does not summon it. In the search field and in a ticket dialog, type, select all, cut, copy, paste, and undo with the keyboard. Confirm reload and developer tools still work in a development run. Package with `pnpm pack:dir` and check the packaged window as well, since a development run and a packaged one differ here. Note what was seen on macOS or say plainly that it was not checked.

## Handoff

**What changed.** The window no longer carries Electron's File/Edit/View/Window/Help
strip. `src/main/app-menu.ts` builds the menu this app actually wants, `index.ts` sets
it before any window exists, and each window on Windows and Linux hides its bar with
`setMenuBarVisibility(false)`.

**Hidden, not removed, and that is the whole point.** `setApplicationMenu(null)` is the
one-line version, but on Windows and Linux the edit accelerators are the menu's to
provide: with no menu, nothing registers Ctrl+C, Ctrl+V, Ctrl+X, Ctrl+A or Ctrl+Z. So
the menu survives as `{ role: 'editMenu' }`, invisible, and `autoHideMenuBar` is left
off so Alt does not summon it back. macOS keeps a visible menu because the platform
requires one: the standard application, edit and window menus, chosen rather than
inherited.

Reload and developer tools are a `View` menu present only when `app.isPackaged` is
false. A packaged window has one hidden Edit menu and nothing else.

**Confirmed against Electron rather than against the documentation**, which the ticket
asked for. A probe ran the real `electron.exe` (44.4.2, Windows), made the same calls,
and reported:

- Development shape: top-level `Edit` and `View`; the Edit submenu registers
  `undo:CommandOrControl+Z`, `redo:Control+Y`, `cut:CommandOrControl+X`,
  `copy:CommandOrControl+C`, `paste:CommandOrControl+V`, `delete`, and
  `selectall:CommandOrControl+A`.
- Packaged shape: top-level `Edit` alone, still seven accelerators, copy still
  `CommandOrControl+C`.
- `window.isMenuBarVisible()` is `false` and `window.autoHideMenuBar` is `false`, which
  is the combination where Alt does not reveal the bar.
- `Menu.setApplicationMenu(null)` leaves `getApplicationMenu()` null, so the option not
  taken really would have left nothing to register those keys. That is the evidence for
  the approach, not an assumption about it.

**How it was checked.** Five new tests in `src/main/app-menu.test.ts`: the edit role is
present on all three platforms, the developer items appear only in development and in
that order, Windows and Linux get nothing but Edit, macOS gets the three menus the
platform expects, and the bar is hidden everywhere except macOS. Desktop suite 218
passing, 1 skipped. Lint, formatting and typecheck clean.

**Not verified:**
- **Nobody looked at the window.** The probe reads Electron's own state with the window
  never shown. That the strip is visually gone, that Alt does nothing, and that the
  board gained the vertical space are all inferred from that state, not seen.
- **Typing.** No key was actually pressed in the search field or a dialog. The
  accelerators are registered, which is the thing that breaks when a menu is removed,
  but registered is not the same as observed working.
- **A packaged build.** `pnpm pack:dir` was not run; the packaged shape was probed by
  building that template directly, not by packaging the app.
- **macOS and Linux.** Windows only. The macOS branch has tests but has never run.
- **Ctrl+W is gone**, along with the rest of the File menu. Nothing required it and
  losing an accidental window-close is arguably an improvement, but it is a change in
  behaviour rather than an oversight. Say if you want it back.

**For you to check:** open the app and confirm the strip is gone and that pressing Alt
does not bring it back; then in the search field and in a ticket dialog, type something
and use Ctrl+A, Ctrl+C, Ctrl+X, Ctrl+V and Ctrl+Z. In a development run confirm reload
and developer tools still work.
