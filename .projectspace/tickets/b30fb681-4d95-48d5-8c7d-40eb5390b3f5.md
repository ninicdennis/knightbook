Denny asked (2026-10-23) to track who clicks the website's download buttons in Umami, as a metric.

Umami (D-052) counts a click on any element with a `data-umami-event` attribute and sends its `data-umami-event-*` attributes as the event's properties. For a link it waits for the post and then follows the link, so the download itself is unchanged.

## Acceptance criteria

1. Every installer **Download** link on /download/ carries `data-umami-event="download"` with properties `target` (such as `windows-x64`), `version` and `channel` matching its card. A card with no build carries no event.
2. The homepage's **Download Knightbook x.y.z** button carries `data-umami-event="download-page"` with `version` and `channel`. With no release, the status text carries no event.
3. In a production build, clicking a Download link with Umami's tracker loaded posts the event to Umami with those properties, under the site's security policy, and the browser still goes to the file.
4. The privacy page says download clicks are counted and what an event records (which button, platform, version and channel).
5. The decision is recorded in the specification (D-054) and the technical design.

## Test plan

- 1: `download-page.test.ts`, stable 0.3.0 beside a 0.4.0 preview and a release missing one platform: each card's link carries its own target, version and channel; the missing card has no event.
- 2: `home.test.ts`, a preview release and no release: the button carries version and channel; the status text has none.
- 3: Manual in this session: Chromium against a production build, with Umami's tracker built from its current source standing in for data.aikoworks.com (the server is not reachable from the session). Not a repository test, because the tracker is Umami's code and is not vendored.
- 4: `layout.test.ts` privacy-page text check, plus reading.
- 5: Reading.

## Handoff

### What changed

- `umamiEvent()` and `DOWNLOAD_EVENTS` in `apps/website/src/layout/analytics.ts` produce Umami's `data-umami-event` attributes.
- `TargetCard` puts `download` (`target`, `version`, `channel`) on each installer link; `ReleaseOffer` passes the channel. `DownloadAction` puts `download-page` (`version`, `channel`) on the homepage button.
- The privacy page says download clicks are counted and what each records. D-054 in the specification; a "Download events" entry in the technical design.

### How it was checked

- New tests: `download-page.test.ts` "counts each Download click in Umami…" (stable 0.3.0 beside preview 0.4.0, and a release missing macOS Intel) and `home.test.ts` "counts a click on the download button…" (stable, preview-only, no release). With the component and privacy changes reverted, these and the privacy check in `layout.test.ts` fail (3 failed); with them, they pass.
- Criterion 3, by hand: Umami's current tracker, built from its source on GitHub, served in place of data.aikoworks.com in Chromium against a production build. A click on the Linux Download link posted `download` with `{target: linux-x64, version: 0.3.0, channel: stable}`, then the browser requested the GitHub installer; the homepage button posted `download-page` with `{version: 0.3.0, channel: stable}` and went on to /download/. No security-policy violation.
- `pnpm check`: lint, format, typecheck pass; core 294, mcp 51, desktop 680 (4 skipped), packaging 46 (9 skipped, no packaged app). The website suite failed 4 docs tests in the first full run because the verifier was building the site at the same time (missing file in the shared test cache); run again on its own, the website suite passed 254/254.
- Verifier: 2 covered, 0 weak, 0 uncovered, 3 not code criteria (1 manual, 2 prose). Its one note, that the privacy page left out the homepage event's channel, was fixed.
