# Lightweight ticket types

## Intended outcome
Make the kind of work visible at a glance using one optional type: ✨ Feature (new capability), 🐛 Bug (incorrect behavior), or 🛠️ Task (maintenance, research, documentation, or other work). Keep type independent from status, priority, dependencies, and review.

## Acceptance criteria
- Store an optional validated `type: feature | bug | task` in canonical ticket Markdown frontmatter. Existing tickets without a type stay valid and display no type; do not infer, bulk rewrite, or classify old records automatically.
- Provide a small Type selector in ticket details with Feature, Bug, Task, and No type. Persist through existing core writes, revision checks, and conflict feedback. Do not make type selection contingent on the future Markdown editor.
- Display a compact emoji plus sentence-case text on board cards, ticket detail, and search results. Preserve the approved board hierarchy: title first, Next up strongest, status/review/blocker signals intact. Keep title text itself unchanged.
- Emoji is decorative when adjacent text supplies its meaning; include accessible naming and a text fallback. Type must not rely on color, and Task must not use a checked/completed symbol that could imply Done.
- Extend core schema/create/update/read, desktop contracts/IPC, MCP create/update/read/list/search representations, and workflow guidance consistently. Omitted update type preserves it; explicit null clears it; invalid values produce useful validation errors. Older callers can omit the field.
- Untouched Markdown body, unrelated frontmatter, stable IDs, completion provenance, backlog order and workflow status remain preserved. A changed type follows existing content-review invalidation semantics; never silently re-mark a record reviewed or accepted.
- Document the advisory convention: Feature resembles Conventional Commits feat; Bug resembles fix; Task has no fixed version increment. Breaking compatibility can occur in any category. No automatic version bump, release automation, severity, custom label taxonomy, or filtering system is required by this ticket.

## Research and scope
GitHub's standard issue types are Task, Bug, Feature. Conventional Commits connects feat/fix to SemVer minor/patch, but that convention describes commits; SemVer describes public API compatibility of releases, not the category of a planning ticket. See linked research document for primary sources. Current schema.ts, tickets.ts, MCP ticket tools, and TicketView have no type field. The emoji mapping is a proposed Projectspace presentation choice, not a standard.

## Handoff

**What changed:** one optional `type` field, carried through every layer rather than
added as a badge.

*Core.* `TICKET_TYPES`, `TicketType` and `ticketTypeSchema` in `schema.ts`, with
`type: ticketTypeSchema.optional()` on the ticket frontmatter — optional and
deliberately **not** defaulted, so a ticket written before this has no type rather than
a guessed one. `createTicket` takes an optional `type` and writes `type: <word>` after
`status` only when one was given; `updateTicket` takes `type?: TicketType | null`, where
omitting it keeps what the ticket has and `null` deletes the field. The emoji is never
written to a record: `.projectspace/tickets/*.md` still holds `type: bug`, plain text
any other tool can read.

*Desktop.* `TicketType` on the contract, `type` on `TicketView` and on search hits, a
`ticket:setType` IPC handler, `setTicketType` across the preload bridge, and a
`setType` callback in `App.tsx` that goes through the same `apply` path as a move — so
it gets the same busy state, error banner and revision-conflict handling as every other
write. The badge renders on board cards, in the ticket detail header and on search
results; the Type selector is a menu in the detail action bar with Feature, Bug, Task,
a divider, and No type.

*MCP.* `ticket_create` accepts an optional `type`; `ticket_update` accepts
`feature | bug | task | null`. `summarize()` reports `type` (null when untyped), so
`ticket_list`, `ticket_read` and `ticket_next` all carry it, and `project_search`
carries it on ticket hits. The skill gained the field, when to set it, when to leave it
alone, and the rule that a type never implies a version bump.

**One change this forced.** `updateTicket` wrote its fields and only validated on the
read-back afterwards, so a bad value left a valid ticket looking corrupt on disk. It now
validates the serialized record before writing. That was found by a test for an invalid
type, but it was never specific to types — `title` and `blocker` had the same hole.

**Presentation decisions.** All three types use the neutral `variant="default"` badge,
so nothing is carried by colour and the type is the quietest thing on a card: Next up
keeps the filled accent, and blocked and failed work keep orange. Task is 🛠️, never a
tick, because a checkmark on a ticket reads as "done". The emoji carries `aria-hidden`
since the word beside it already says the same thing, and a visually hidden "Type: "
prefix makes the badge unambiguous when it is read on its own. In the selector the
current choice is marked with `aria-current` and a tick — that tick means "this one is
selected", not "this work is finished".

**Two files were split** because they would otherwise have gone past the project's size
limit: the nine card badges moved to `TicketCardBadges.tsx` (`TicketCard.tsx` 400 → 209
lines), and the detail dialog into shell, actions and sections under the layout ticket.

**How it was checked:** `pnpm check` passes — lint, format, typecheck, and 405 tests
across the workspace, up from 364. Thirty-one of them are new here: 16 in
`packages/core/src/ticket-types.test.ts`, 7 in `packages/mcp/src/ticket-types.test.ts`,
11 in `apps/desktop/src/renderer/TicketTypes.test.tsx`.

The core tests use real files in a throwaway project: a hand-written record from before
types existed loads and stays untyped, and an update that does not mention type does not
add one; each of the three words round-trips through the file; clearing removes the
field rather than writing an empty one; an unrelated update preserves the type; the
body, id, status, related documents and creation time are untouched by a type change; a
stale revision is refused with `revision_conflict` and the type is left alone; a
hand-edited `type: chore` makes the record invalid and is reported rather than repaired;
and changing a type changes the review fingerprint, so a recorded review goes stale the
same way it does for `depends_on`.

The MCP tests parse the real tool input schemas: the three words accepted, omission
accepted, `null` accepted on update but refused on create (there is nothing to clear),
and anything else refused with an error naming the allowed options.

Exercised end to end against the rebuilt MCP server and a throwaway project, not only in
unit tests. Creating with `type: bug` wrote `type: bug` into the frontmatter; `ticket_list`
returned `"bug"` and `null` for the untyped one; changing to `task` worked; renaming the
ticket left the type alone; `type: null` removed the field from the file; `type: "chore"`
was refused with *expected one of "feature"|"bug"|"task"*; and a hand-written pre-types
record loaded with no problems reported.

Checked visually in a browser against `pnpm preview:board`, with the preview data given
a mix of typed and untyped tickets. Cards show ✨ Feature, 🐛 Bug and 🛠️ Task; untyped
cards show nothing at all; on the Next-up card the type sits beside the accent badge
without competing with it. The detail header reads Verification · 🐛 Bug · Unreviewed.
The Type menu opens upward, fully inside the window, with the current type ticked. Search
results carry the badge on the typed hit and nothing on the untyped one. With five
actions in the bar — Move to, Type, Mark content reviewed, Resolve the issue, Accept as
done — everything still fits one row at 900×650.

- **Nothing on your board was classified.** Every existing ticket is still untyped, on

  here is the one I filed myself.
