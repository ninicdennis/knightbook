# Check that each outside pull request has agreed to the CLA

## Intended outcome
An outside pull request cannot be merged by mistake without its author agreeing to the Contributor License Agreement (D-045), and there is a record of who agreed.

## Acceptance criteria
- A required check fails on a pull request from someone outside the repository until its author has agreed to `CLA.md`, and passes for the owner.
- Each agreement is recorded with the GitHub account, the CLA version and the date, somewhere the owner controls.
- The check cannot be used by a fork to run code with write access or secrets; if it needs `pull_request_target`, it checks out nothing from the fork.
- `CONTRIBUTING.md` says how agreeing works.

## Notes
Created 2026-10-21. Until this exists, the pull-request form has a CLA checkbox and the owner checks it by hand before merging. Options include the CLA Assistant GitHub App, or a small workflow that reads the checkbox and keeps signatures in the repository. Post-launch is fine while outside pull requests are rare.

## Handoff (2026-10-21)

### What changed
- `.github/workflows/cla.yml`: a "CLA agreed" check on every pull request to `main` (decision D-049). It passes for the owner and bots. Anyone else passes once they have checked the CLA box in the pull-request form themselves; a box checked by another account (the owner included) does not count. Each agreement is written to `signatures.json` on a `cla-signatures` branch, created by the workflow with no history, as login, numeric id, CLA version (read from the "Version" line of `CLA.md`), time and pull request. The same id passes later pull requests without asking; a new CLA version asks again. While the agreement is missing, the check fails and keeps one comment on the pull request saying what to add.
- It runs on `pull_request_target`, checks out only the default branch (`.github/scripts/cla` and `CLA.md`, no credentials kept), installs nothing, uses no secrets, and reads the pull request's description only as text.
- Logic in `.github/scripts/cla/` (`cla.mjs` decides, `run.mjs` talks to the GitHub API with plain `fetch`), tested by `cla.test.mjs` with Node's own test runner. `.github/workflows/workflow-scripts.yml` runs those tests on pull requests that touch them, because `.github/scripts` is outside the pnpm workspace and `pnpm check`.
- `CONTRIBUTING.md` explains how agreeing works; `AGENTS.md` lists the test command; D-049 in the specification records the choice over CLA Assistant and CLA Assistant Lite.

### How it was checked
- `node --test '.github/scripts/**/*.test.mjs'`: 11 pass. Criterion 1: owner and bot exempt, unchecked box / no box / empty body fail, the author's checked box records and passes, a box checked by the owner fails, an earlier signature for 1.0 passes while 0.9 and a 1.10 bump fail, and an end-to-end run against a fake GitHub posts one comment and edits it when the author agrees. Criterion 2: the recorded signature holds login, id, version, ISO date and pull request; the first one creates the branch from a parentless commit; a later one is appended with the file's sha and retried after a 409. Criterion 3: a test reads `cla.yml` and fails if it references the pull request's head, sets a checkout `ref`, keeps credentials, installs packages or uses secrets. Mutation check: removing the sender check or the owner exemption makes tests 1, 4 and 10 fail.
- Criterion 4 settled by reading `CONTRIBUTING.md`.
- `pnpm check`: lint, format and typecheck pass; every suite passes except one website test (`discovery.test.ts`, "stops the real build when two guides share a title") that timed out at 5 s while all suites ran in parallel. It passed when the website tests ran alone (146 pass). This change touches no website code.
- The verifier subagent is not available in this cloud session, so the coverage review above is my own, not its.

### Not verified
- The workflow has not run on GitHub yet. Whether `pull_request_target` from a fork, the branch creation and the comment all work with the real token is only seen once it runs.
- "Required" depends on a repository setting only the owner can change (below).

### For you to check
- After merging, make "CLA agreed" a required status check on `main` (Settings > Rules > Rulesets, or branch protection). It appears in the list once it has run once.
- If a ruleset restricts creating branches, allow `cla-signatures` or create it first (empty is fine; the workflow adds `signatures.json`).
- Settings > Actions > General > Workflow permissions can stay read-only: the workflow asks for its own write permissions.
- Optionally open a pull request from a second account or a fork to see it fail, check the box, and see it pass and record.
