# Package and check the Intel Mac app in CI

## Intended outcome
A CI run on macOS packages both the arm64 and the x64 app and runs `packaged-architecture.test.ts` against each, so a runtime staged for the wrong CPU fails before a release rather than after.

## Acceptance criteria
- It is established, from a real macOS CI run, whether `pnpm pack:dir` (`electron-builder --dir`) packages both mac architectures or only the runner's own, and the packaging findings say which.
- If only one: the macOS package job packages both (for example `--mac --arm64 --x64`), within the Actions allowance the user accepts (D-031), or the user decides the release build is where x64 is first checked.
- Under `REQUIRE_PACKAGED_APP` on macOS, the packaged suite fails when either architecture's package is missing, so it cannot pass on half the release.
- Whether the x64 server was started under Rosetta on the arm runner is stated.

## Notes
Found while doing `41d9ba34` on 2026-09-29. Staging now fills `resources/mcp-arm64` and `resources/mcp-x64`, and the packaged test compares each package's Node with its app executable, but only on packages that exist. macOS minutes cost about ten times Linux ones, so doubling the mac packaging is a cost decision for the user.

Observed 2026-09-29 in manual CI run 36585090697 (branch `feature/unmet-prerequisites-macos-runtime-tickets-split`, all jobs green): on `macos-latest`, staging filled both `resources/mcp-arm64` (darwin-arm64) and `resources/mcp-x64` (darwin-x64), but `electron-builder --dir` packaged only `platform=darwin arch=arm64` into `release/mac-arm64`. `packaged-architecture.test.ts` passed on that one package. So today no CI run packages or checks the Intel app. The packaging findings still call this unchecked and need updating with this result.

## Handoff
**What changed:** Answer to the first criterion: `--dir` packages only the runner's CPU (run 36585090697). The user chose on 2026-09-29, in chat, to package both in CI. New `pnpm pack:dir:mac` (root and desktop) runs `electron-builder --dir --mac --arm64 --x64`; CI's macOS package step uses it, other platforms keep `pack:dir`. `packaged-architecture.test.ts` has a second test that, on macOS under `REQUIRE_PACKAGED_APP`, requires the packaged app executables to cover exactly arm64 and x64 (`packagedCpus` in `architecture.ts`). `packagedResources` and `packagedApp` in `packaged.ts` now pick only the package whose Node runs on this CPU, so the server and window suites never depend on Rosetta. A non-gating CI step on macOS runs `file` and `arch -x86_64 … node --version` on the Intel app's runtime. AGENTS.md command table and CI description mention `pack:dir:mac`; the packaging findings record both runs and the choice.
**How it was checked:** `pnpm check` passes locally (Windows). Manual CI run 36589398153: attempt 1 failed on an unrelated Windows renderer test (`AiSetup.test.tsx`, a 1 s wait on a cold runner; ticket a79c7639); attempt 2 on the same commit was green on all six jobs. Its macOS package log shows `packaging platform=darwin arch=x64 appOutDir=release/mac` and `arch=arm64 appOutDir=release/mac-arm64`; `packaged-architecture.test.ts` ran 2 tests, none skipped; `packaged-app` 4 and `packaged-window` 3 passed; the Rosetta step printed `Mach-O 64-bit executable x86_64` and `v24.19.0`. Verifier: 0 covered, 1 weakly covered, 3 not code criteria.
**Not verified:** The "both Mac CPUs" test has only been seen passing; its failure when one package is missing rests on reading the code plus the `packagedCpus` unit test on fake headers, and no test runs `packagedApps()` on a fake release folder with one bundle. Under Rosetta only the Intel Node's `--version` ran: the Intel app's MCP server and window were not started, so the answer to the fourth criterion is that the server itself was not started. Because that step may fail, a future runner without Rosetta stays green; the step output has to be read. The Intel app was not opened on an Intel Mac.
**For you to check:** The macOS "Package and test the app" job in run 36589398153 (attempt 2): the two `packaging` lines and the "Start the Intel Mac runtime under Rosetta" step. Whether the extra Mac packaging time is acceptable to you on merges and manual runs.
