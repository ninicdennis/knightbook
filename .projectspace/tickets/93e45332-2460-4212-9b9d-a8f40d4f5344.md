# Add local Plans with phases, linked tickets, and progress

## Intended outcome
A Plans pane beside Board and Documents lets the user maintain multiple broad roadmaps, such as MVP and launch, then use their external AI to develop phases and attach canonical tickets. Each plan shows where its work stands.

## Acceptance criteria
- Support multiple named plans per project with freeform Markdown goals, ideas, and notes; a plan can exist before it has phases or tickets.
- Support ordered phases with editable titles, scope, and value/importance rationale. External AI can propose or write the decomposition when asked; the app does not need a built-in AI provider.
- Attach and detach existing tickets to phases, navigate to their detail views, and create/link new tickets through the local AI workflow. References use stable ticket IDs and remain valid after title changes.
- Persist plan prose, phase structure, and links as portable project-local Markdown/metadata with a documented backward-compatible schema. Existing projects need no destructive migration; external edits and refresh retain authored content.
- Make plans and phase/ticket relationships discoverable and writable through the MCP/skill workflow with revision conflict checks. Creation must work explicitly: existing document_write cannot create a new file. Keep document and ticket APIs consistent rather than maintaining competing copies.
- Derive progress from canonical ticket states. Show counts per state and Done/total; show Verification separately and preserve existing unattributed-completion warnings. Count each ticket once in a plan aggregate, even if referenced in multiple phases; zero tickets is an empty/unplanned state.
- Surface missing/malformed references without blocking other plans or discarding prose. Reopening a linked ticket updates progress. Attaching a ticket does not change status, dependencies, or backlog order.
- Use the existing Board theme and responsive navigation. Preserve human-only review and completion semantics.

## Notes

Exact phase serialization and registration belong in the implementation plan; keep narrative flexible rather than imposing mandatory prose headings. Existing related_documents is useful context but does not currently represent phase membership. No cloud storage, automatic reprioritization, timeline scheduling, or second task tracker is requested.

## Handoff
**Scope decided with the user on 2026-09-24 (D-022 in the specification):**
- Each plan is one file, `.projectspace/plans/<id>.md`.
- This slice reads plans in the app and writes them through MCP or the plan's own file.
- In-app editing (creating plans and phases, attaching and detaching tickets from the pane) was split out as "Edit plans in the app" (c17fc047), which depends on this ticket.

**What changed:**
- *Core:*
  - `schema.ts` adds `planFrontmatterSchema` and `planPhaseSchema`. A phase has a stable id, a title, optional `scope` and `value`, and ticket ids.
  - `plans.ts` provides create, read, list (a broken file becomes a problem, never hides the others) and update, through the shared `writeRecord` with a revision check. Updates go through the YAML document, so unknown top-level fields and the prose body survive.
  - New phases get readable ids (`p1`, `p2`, …). Two phases with one id, or one ticket twice in a phase, is refused before writing.
  - `plan-progress.ts` counts each ticket once per plan and by state. A missing or unreadable reference counts toward the total and never as done. No tickets means `empty`. It also counts unattributed Done.
- *MCP:* `plan_list`, `plan_read`, `plan_create` and `plan_update` in `packages/mcp/src/plan-tools.ts`. `plan_update` replaces phases wholesale, and its description says to keep phase ids from `plan_read`.
  - The skill has a new Plans section. `guidance.test.ts` now recognises `plan_*` tool names, so the skill and the tools cannot drift.
- *Desktop:*
  - A **Plans** tab beside Board, Documents and Archive, laid out like Documents: a list with a per-plan state, and a detail with its progress bar, rendered body, and each phase with its progress and ticket rows.
  - Verification has its own segment. Missing tickets get a striped red segment, and each shows as a dashed "No ticket with this id" row with its id. Archived tickets are marked. Unattributed Done gets an orange note.
  - Clicking a ticket opens the usual dialog. **Edit externally** opens the plan file. Plans re-read on every project refresh, including window focus.
  - The host computes progress with the same core function MCP uses, via `plans:list` and `plan:openExternally`.
  - `useLinkNavigation.follow` now accepts no origin, so a link followed from a plan body doesn't offer a broken "Back to".
- *Docs:*
  - D-022 in the specification.
  - The storage layout in technical design section 3.
  - A Plans section in `docs/using-knightbook.md`.
  - A README capability line.

## Handoff: plans in the ticket dialog (2026-09-24, after the user's first verification)
The user asked for a ticket's plans to be visible in its dialog, so the ticket went back to In progress for this.

**What changed:**
- Core `phasesContaining(plans, ticketId)` in `plans.ts` returns every phase that lists a ticket, in plan and phase order.
- The host's `toTicketDetail` adds `plans` (plan id and title, phase id and title) to `TicketDetailView`. Plan files that could not be read are left out here; the Plans pane already reports them.
- The dialog has a **Plans** section after "Related documents". Each entry reads "<plan> · <phase>" and opens the Plans tab at that plan, closing the dialog. A ticket in no plan shows no section.
- `PlansView` takes an `openTarget`, like Documents, so it can be asked to show a given plan.
- The guide mentions the dialog section.
- Membership is read from the plans; nothing is written on the ticket.

**How it was checked:**
- `pnpm check` passes: core 219, mcp 43, desktop 361, packaging 48.
- New tests: a host test that one ticket in two phases of one plan and in a second plan gets all three memberships, in order, and a ticket in no plan gets none; two renderer tests, for clicking a membership (dialog closes, plan shown) and for no section when there are no plans.
- Seen in `pnpm preview:board`: the dialog listed "MVP · The board", and clicking it opened the MVP plan with the Plans tab selected.
- The pane happened to be narrow, so the narrow turn-taking, with its "All" back button, has now also been seen.
- All 48 packaging tests ran, including the new check that the shipped skill matches the source, because a complete package was back in `apps/desktop/release/`, built at 19:31. I did not make that build. It predates this dialog change.

**Not verified:**
- The dialog section in a packaged build.
- MCP's `ticket_read` does not report plan membership; an AI finds it through `plan_list`.

**For you to check:** Open a ticket that is in "Ship MVP" and follow its Plans entry.
