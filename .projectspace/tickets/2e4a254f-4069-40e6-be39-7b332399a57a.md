# Validation scenario

## Intended outcome
Exercise the specification's nineteen-step scenario on one small real project.

## Acceptance criteria
- Each step recorded as pass or fail with evidence; Windows first.
- Every gap becomes a ticket rather than a silent omission.

## Handoff
**What changed:**
- `docs/validation-scenario-results.md` (new): the nineteen steps, each with a verdict and the evidence that decided it. It is already discoverable through the existing `docs` entry, so no new inclusion was needed.
- No product code was changed. This ticket is a measurement; the things it found are tickets, not edits.

**Result: 14 pass, 2 fail, 3 not run here.**

**How it was checked:**
Scripted against the shipped Node runtime (`release/win-unpacked/resources/mcp/node.exe`) driving the freshly rebuilt `packages/mcp/dist/server.mjs`, spoken to over stdio the way an external AI client would. The `server.mjs` staged under `release/` is written at packaging time and lags the source, so the current bundle was used. Two throwaway projects in a temp directory — one greenfield, one folder that already had a README and docs. No Electron process was started at any point. Run twice, identical verdicts. The real board was not touched: no scenario records exist under `.projectspace/`.

**The two failures, both real:**
- **Step 3** — `ticket_read` never returns `related_documents`, although `ticket_create` accepts it and the file stores it, and `ticket_update` cannot change it. Confirmed against this project's own ticket `1924aa96`. The step is specifically about a second tool retrieving a ticket *and its context*; the context is unreachable. → ticket `6a5ed3da`.
- **Step 9** — deleting a completion block is flagged (`completion_unattributed=true`), but editing one is not. A block changed to `decision_source: direct_user_action` + `recorded_by: agent` comes back as an ordinary completion, and that pair is one the write path can never produce. `isUnattributedCompletion` only asks whether the block is missing. Worth reading the ticket for the nuance: this is not a broken security boundary, it is a docblock claiming more than the check does. → ticket `02e8bb8a`.

**Not verified:**
- **Steps 10 and 11's platform half.** Windows only. macOS and Linux are yours (ticket `5ddb9586`).
- **Step 13.** No formatted editor exists yet; ticket `b217a95f` is blocked on Milkdown.
- **Step 18.** Could not be set up at all from MCP. Recording a review is app-only by design, so the reviewed to `changed_since_review` transition needs a person first. The design is working as intended; the step is simply unvalidated.
- **The in-app half of steps 4, 6, 7 and 11.** Each passed its MCP half. The window halves are collected in ticket `25be0050` rather than left implied.
- I did not re-run the scenario against the *packaged* `server.mjs`, only the current build. If you want the packaged bundle validated too, re-stage it with `pnpm pack:dir` first.

**For you to check:**
1. Read `docs/validation-scenario-results.md` — it is the deliverable, and the summary table is the fast path.
2. The step 9 judgement is the one worth disagreeing with if you are going to disagree with anything. I called it a gap between the docblock and the check rather than a security defect. Ticket `02e8bb8a` leaves the choice of fix open, including "correct the sentence instead".
3. Four gap tickets were created and are in Backlog: `6a5ed3da`, `02e8bb8a`, `fa05d99e`, `25be0050`. They start unordered — arrange them in the app if the order matters.

Unrelated to the product: the copy of the workflow skill installed at `~/.claude/skills/projectspace` still says the backlog cannot be reordered through MCP. `ticket_reorder_backlog` exists and this repo's `skills/projectspace/SKILL.md` is correct, so only the installed copy is stale. I left it alone; it is outside this project.
