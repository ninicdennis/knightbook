# Download and install application updates without manual reinstallation

## Intended outcome
Users with an updater-enabled Knightbook installation can discover, download and apply a newer release through the app, without manually downloading and running an installer each time. Preserve project data, settings and MCP access throughout the upgrade.

## Acceptance criteria
- Settle and record update hosting, download consent, check frequency, install timing and supported platform behavior in the authoritative specification/technical design before implementation. The research recommendations are not already approved decisions.
- Integrate update checks in the desktop main process through the existing named IPC contract; provide a manual check and clear available, downloading, ready and failed states. A failed check must not appear as up to date.
- Let users defer restarting. Complete pending saves before installation, and keep normal project work usable when the update service is unavailable.
- Consume versioned release artifacts and update metadata from the release-publishing prerequisite. Validate artifact integrity and applicable signatures; select the correct platform, architecture and release channel.
- Prove an actual installed version A to version B upgrade on every platform advertised as supporting in-app updates. Begin validation with Windows NSIS; unpacked builds and mocked update events alone are insufficient.
- Preserve project Markdown, settings, the MCP access registry and saved MCP launch paths. Test installation while an AI client has the bundled MCP server running; handle locked resources safely without terminating unrelated processes, and explain any required reconnection.
- Verify the updated MCP server can reconnect and operate with the desktop window closed. Avoid transient AppImage mount paths in saved client configuration.
- Cover deferred restart, pending writes, offline checks, interrupted downloads and invalid artifacts. Document recovery from a bad release without claiming unimplemented automatic rollback.
- Explain that existing installations without an updater need one initial manual upgrade. Run pnpm check and the relevant packaging/installed-upgrade checks, reporting skipped or unverified platform cases explicitly.

## Notes
See [application update research](../../docs/research/application-updates-research.md) for evidence, sources and open decisions. The recommended starting point is electron-updater with existing Electron Builder packaging and GitHub Releases for public downloads; hosting and UX remain decisions to settle when this ticket starts.

This ticket covers the installed-app update experience. [Release publishing](356c7683-44b3-42f7-84f3-80d0e62f81ef.md) and the [supported platform decision](6b200e68-f472-4e18-a072-2c9d2a0b8558.md) remain separate prerequisites. Do not enable publishing as part of merely creating this ticket. Beta channels, custom update services and automatic rollback are not required for the first implementation.
