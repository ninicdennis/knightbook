# Download and install application updates without manual reinstallation

## Intended outcome
Users with an updater-enabled Knightbook installation can discover, download and apply a newer release through the app, without manually downloading and running an installer each time. Preserve project data, settings and MCP access throughout the upgrade.

## Acceptance criteria
- Settle and record update hosting, download consent, check frequency, install timing and supported platform behavior in the authoritative specification/technical design before implementation. The research recommendations are not already approved decisions.
- Integrate update checks in the desktop main process through the existing named IPC contract; provide a manual check and clear available, downloading, ready and failed states. A failed check must not appear as up to date.
- Let users defer restarting. Complete pending saves before installation, and keep normal project work usable when the update service is unavailable.
- Consume versioned release artifacts and update metadata from the release-publishing prerequisite. Validate artifact integrity and applicable signatures; select the correct platform, architecture and release channel.
- Prove an actual installed version A to version B upgrade on every platform advertised as supporting in-app updates. Begin validation with Windows NSIS; unpacked builds and mocked update events alone are insufficient.
- Preserve project Markdown, settings, the MCP access registry and saved MCP launch paths. Test installation while an AI client has the bundled MCP server running; handle locked resources safely without terminating unrelated processes, and explain any required reconnection.
- Verify the updated MCP server can reconnect and operate with the desktop window closed. Avoid transient AppImage mount paths in saved client configuration.
- Cover deferred restart, pending writes, offline checks, interrupted downloads and invalid artifacts. Document recovery from a bad release without claiming unimplemented automatic rollback.
- Explain that existing installations without an updater need one initial manual upgrade. Run pnpm check and the relevant packaging/installed-upgrade checks, reporting skipped or unverified platform cases explicitly.

## Notes
See [application update research](../../docs/research/application-updates-research.md) for evidence, sources and open decisions. The recommended starting point is electron-updater with existing Electron Builder packaging and GitHub Releases for public downloads; hosting and UX remain decisions to settle when this ticket starts.

This ticket covers the installed-app update experience. [Release publishing](356c7683-44b3-42f7-84f3-80d0e62f81ef.md) and the [supported platform decision](6b200e68-f472-4e18-a072-2c9d2a0b8558.md) remain separate prerequisites. Do not enable publishing as part of merely creating this ticket. Beta channels, custom update services and automatic rollback are not required for the first implementation.

## Handoff

### What changed
- Decision D-056 (spec) and "In-app updates as built" (technical design): GitHub Releases as the feed; check ~10 s after launch, every 6 h, and on request; announce only, download when the user clicks Download (Denny chose "Ask before downloading" on 2026-11-13); Restart now, or Later = install on next quit. Windows (NSIS) updates in place; macOS and Linux announce the version and link to the download page (ad-hoc Mac signing can't pass Squirrel.Mac; Linux ships only the deb).
- Main process: `src/main/updates/` (release-feed: choosing the release, skipping drafts and "Withdrawn…" titles; update-service: the state machine; held-files: probes `resources/mcp` for files an AI client's MCP server holds; updates-ipc: GitHub fetch, electron-updater `NsisUpdater` pointed at one release's `latest.yml`, will-quit hook). New contract `shared/updates-contract.ts`, preload operations `updateView`, `checkForUpdates`, `downloadUpdate`, `installUpdate`, `onUpdateView`.
- Window: corner notice (`renderer/updates/UpdateNotice.tsx`) and the Updates line + Check for updates button in Settings > About.
- Release: `electron-builder.yml` gains a `publish` section (still `--publish never`), CI keeps `latest.yml` and the `.exe.blockmap`, and the publishing job requires both and checks `latest.yml`'s version, installer name and SHA-512 against the built installer.
- Docs: using-knightbook.md "Updating Knightbook" (incl. MCP-in-use, one manual upgrade for older installs); release-automation.md (update files, withdrawing from the app by a "Withdrawn" title); the website privacy page now describes the update check instead of "checks for no updates".

### How it was checked
- `pnpm check` passed (desktop 732 passed / 4 skipped, website 267 passed) before the last added test; the update tests (`src/main/updates`, `src/renderer/updates`, `scripts/publishing`, `scripts/update-publishing.test.mjs`) pass, 80 tests.
- Layout: board preview with `?update=available|notify|downloading|ready|in-use|failed` at 800 and 1600 px, light and dark, plus Settings; screenshots in project files `updates-preview/`.
- Verifier: covered 1, weakly covered 4, uncovered 0, not a code criterion 4.

### Not verified
- No real installed upgrade A to B on any OS; the electron-updater download, its own SHA-512 check on a tampered file, resume after an interrupted download, and the silent NSIS install are only exercised through stand-ins. This needs two releases that both carry the updater.
- That electron-builder actually writes `latest.yml` and the block map on Windows: only a Windows `pack:installers` run shows it (a manual CI run on the branch was to be started).
- The held-file probe with a file really held by a running `node.exe` (Windows only). A read-only file would also read as "in use".
- Installing while an AI client runs the MCP server, and the client reconnecting afterwards with the window closed.
- "Complete pending saves" covers app-state writes (`appStateChangesSettled`); unsaved text in an open editor is not saved, and the ready notice tells the user to save first.
- No Authenticode verification: the installer is unsigned (ticket a415fdb2); the SHA-512 comes from the same release.
- Packaged-app tests skipped (nothing packaged here).

### For you to check
- Release the first version with updates and install it by hand on Windows; then release the next one and update through the app: Download, Restart now (and once with Later, then quit). Check Settings shows the new version and projects, settings and MCP access survived.
- Repeat with an AI client running the MCP server: the notice should say it cannot install yet, and installing should work after closing the client.
- On the Mac, check the notice links to the download page.
