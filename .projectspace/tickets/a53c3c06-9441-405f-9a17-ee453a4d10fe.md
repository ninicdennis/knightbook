# Download page driven by a checked-in release-data file

## Intended outcome
`/download/` shows the correct released binaries from a release-data file validated at build time, and is honest when there is nothing to download.

## Acceptance criteria
- A checked-in release-data file records, for each release: version, channel (stable or preview), date, release-notes URL, and whether it is withdrawn; and for each asset: OS, CPU architecture, package format, minimum OS version, exact version-specific HTTPS URL, filename, size, SHA-256 checksum, and signing or notarization state.
- The build fails with a clear message when the file is malformed or an asset is missing a required field.
- The page handles every state in spec §5, each covered by a test with data that triggers it: no release; supported platforms available; a target not released (no substitute platform, no dead link); preview only (labelled, with known issues); stable and preview both present (stable is the default, preview needs a deliberate choice); withdrawn release (not recommended); unknown platform or mobile visitor (all desktop choices, explained as a desktop app).
- Every asset shows its checksum with verification instructions and links to the authoritative release page.
- All download links work without JavaScript. Any platform highlighting is progressive enhancement and never claims to know the CPU architecture for certain; an Intel build is never offered as Apple silicon.
- Platform choices become labelled cards on narrow screens, and long filenames wrap without horizontal scrolling.
- Until real release data is added, the page and the site render the "Downloads are not available yet" state.

## Notes
Spec §5: prefer a small checked-in file over a live API call; updating it is part of publishing a release, after the assets exist. Launch targets (user, 2026-09-29): all three platforms, meaning Windows x64 NSIS, macOS arm64 and x64 DMG, Linux x64 deb. AppImage is not offered until ticket 68f54f52 (D-028).

## Handoff

**What changed.** The work is on branch `feature/website-shell`, alongside the header and footer work (923bbd48), and is not committed yet. A note on the download page is in the technical design ("The public website"). No dependencies were added: validation uses the zod that Astro already ships. It changes no app paths, so merging releases nothing (D-041).
- **`apps/website/src/download/releases.json`** is the checked-in data, `{ "releases": [] }` for now. Adding a release is part of publishing it, once its files are at public URLs. That waits on the public download origin (ticket 1ef49bc4), so it stays empty.
- **`release-data.ts`** is a strict zod schema with every field the ticket lists, plus `knownIssues` and `withdrawnReason`. It also rejects:
  - a URL that is not https or does not end with the filename;
  - a filename that does not contain the version;
  - a build that is not one of the four D-028 launch targets, so no AppImage;
  - two builds for one platform;
  - a preview without known issues, or a withdrawal without a reason;
  - a duplicate version.

  `parseReleaseData` throws one message naming each problem by location, for example `releases[0].assets[0].sha256: must be 64 lowercase hexadecimal characters`.
- **`download-view.ts`** decides the offer from the data alone:
  - the newest non-withdrawn stable release by default (versions compared by number);
  - otherwise the newest preview;
  - a newer preview becomes an opt-in;
  - withdrawn releases are listed, never offered;
  - each of the four platforms gets the matching build or none.

  It also holds the checksum command per OS: `Get-FileHash` in PowerShell, `shasum -a 256` on macOS, `sha256sum` on Linux.
- **`load-release-data.ts`** reads the checked-in file. Only the tests set `KNIGHTBOOK_RELEASE_DATA_FOR_TESTS` to build from a fixture.
- **`/download/`** (`pages/download/index.astro`, `ReleaseOffer.astro`, `TargetCard.astro`):
  - It always says Knightbook is a desktop app for Windows, macOS and Linux, and what to do on a phone or tablet.
  - It shows either the recommended release (version, Preview label and known issues when it is a preview, date, and a link to its release page) or "Downloads are not available yet".
  - Each platform card gives the platform and CPU name, a Download link, file, size, minimum OS, signing state, the SHA-256, and a closed "How to check this file" panel with the command. A platform without a build says "Knightbook X has no build for …" and links nothing.
  - A newer preview sits behind a closed `<details>` "Try the preview". Withdrawn releases are listed with their reason.
  - Cards are 2×2 on wide screens and one column below 720px. The filename and checksum wrap anywhere.
  - Nothing guesses the visitor's platform or CPU, and there is no JavaScript.
- **Header:** Download now carries `aria-current="page"` on `/download/`.
- **Website tests** run one file at a time (`fileParallelism: false`). Two `astro build` runs at once in one project crashed each other through Astro's shared build cache.

**For you to check.**

3. Check the copy reads right to you, in particular the signing label "Not code-signed", the phone or tablet line, and the preview opt-in wording.
