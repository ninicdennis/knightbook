# Back and forward history

## Intended outcome
Moving between documents and tickets has a history, like a browser. The mouse's Back and Forward side buttons, and the usual keyboard shortcuts, step back and forward through the places the user has been.

## Acceptance criteria
- Back returns to the previous place and Forward redoes it. A new navigation after going Back discards the forward steps, as a browser does.
- Works from the mouse's Back/Forward side buttons (X1/X2), Alt+← / Alt+→ on Windows and Linux, and Cmd+[ / Cmd+] on macOS.
- A place is a document (with the heading it was opened at, if any) or an open ticket. The "Back to …" button from [Fix internal links](db7cff48-77cf-46c4-9173-62ee9d1b3490.md) becomes part of this history rather than a separate single step.
- A step whose target no longer exists (deleted, moved, no longer included), or whose ticket has been archived, says so and moves on. It never reopens stale content or includes anything.
- History belongs to one open project and is cleared on switching projects. It is session state only: nothing is written to the project or the app's settings.
- Going back and forward changes no ticket status, review, or document inclusion, and does not fight open dialogs such as completion or verification confirmations.

## Questions to settle before building
- Which moves count as steps: only following links, or also opening a ticket from the board, closing a ticket dialog, and switching between Board, Documents and Archive?
- Should Back from a ticket that was opened from the board close the dialog, or go to whatever was before it?
- Is scroll position restored when going back, or only the heading a link named?
- Is a visible back/forward control wanted in the header, or only the mouse buttons and shortcuts?

## Notes
Requested 2026-09-24 after the internal-links work shipped a single "Back to …" step. That ticket ruled out a full history framework on purpose, so this is new scope.

The mechanics look small: replace the single `back` entry in `apps/desktop/src/renderer/hooks/useLinkNavigation.ts` with back/forward stacks of `LinkPlace`, and listen for the side buttons and shortcuts. Two ways to detect the side buttons, to check against the installed Electron: renderer mouse events with `button` 3 and 4, and the BrowserWindow `app-command` event (`browser-backward` / `browser-forward`, reported on Windows and Linux). If the host path is used, it needs a named contract operation or event, per the renderer isolation rule. No routing library or new dependency should be needed.

Not investigated yet: how either approach behaves in the packaged app on each OS, or whether the side buttons already reach the renderer as anything.

## Verification
Tests for back, forward, a new navigation truncating forward history, a missing or archived target, the project-switch reset, and each input (mouse buttons, both shortcut sets). Check the side buttons by hand in the packaged Windows app; say plainly what was not checked on macOS and Linux.

## Handoff
**What changed:** How the user settled the open questions (D-038):
- **Steps:** following a link, opening a document from the list, choosing a plan, opening or closing a ticket, and switching view all count.
- **Back from a board ticket:** closes it, and Forward reopens it.
- **Restored on Back:** the heading a link named, but not the scroll position.
- **Visible controls:** Back and Forward buttons at the start of the view-tab row.

`useProjectNavigation` now owns a history of places. The pure part is `renderer/history/navigation-history.ts` (at most 100 places). Before showing a place, `useHistorySteps` checks it still exists:
- A deleted ticket, or one archived *after it was opened*, is reported, dropped from history and stepped over.
- So is a document that is gone or no longer included, checked through the existing `resolveLink`. Nothing is included.

`useHistoryInput` listens for Alt+←/→ (Cmd+[ / Cmd+] on macOS) and for renderer `mouseup` with buttons 3 and 4. It ignores them while you are typing in a field, and while any dialog other than a ticket being read is open. That includes a ticket being edited, so a side-button press never loses a draft.

"Back to …" is now the same step as the header's Back. `useLinkNavigation` lost its single back step. There is no new host operation: the `app-command` path was not used. History is cleared when another project opens and is never written anywhere.

**Fix after the user's check (2026-09-30):** Forward from a ticket to a linked ticket that was *already* archived, such as "Fix internal links", reported it as archived and skipped it. The old rule treated every archived ticket outside the Archive view as stale. A ticket place now records whether its ticket was archived when it was opened, and only archiving after that makes it stale. A new test in `Links.test.tsx` covers the link, Back and Forward case; I confirmed it fails under the old rule.

3. Start editing a ticket and press Back: nothing should happen.
