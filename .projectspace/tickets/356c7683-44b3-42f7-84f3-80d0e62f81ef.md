# Build and publish a GitHub Release from the release branch

## Intended outcome
Merging into the designated release branch builds the desktop app for each supported target and publishes a GitHub Release, as proposed in docs/release-automation.md.

## Acceptance criteria
- The acceptance criteria in docs/release-automation.md, section 'Acceptance criteria for the later feature', are met.
- Each published build contains the Node runtime staged for its own target, not the build machine's.
- Targets match the platform decision from the OS and architecture decision ticket.
- A failed or repeated run does not publish a partial or duplicate release.
- No secret beyond what publishing needs is granted, and pull-request CI keeps its read-only permissions.

## Handoff

**What changed.** Branch `feature/release-automation`, uncommitted. Recorded as D-040 in the specification; maintainers' guide in "How releases work" at the top of docs/proposals/release-automation.md.

- `.github/workflows/release.yml` (new) runs on every push to `main`, one at a time, in three stages:
  - `version` runs semantic-release in dry-run mode (`apps/desktop/scripts/publishing/next-version.mjs`) to choose the version and notes.
  - `ci` calls `ci.yml` with that version.
  - `publish` (`publish-release.mjs`) runs only if all three platforms passed. It checks there is one installer per D-028 target, writes `SHA256SUMS.txt`, stages a draft prerelease at the tested commit, uploads, checks the draft, and publishes, which creates the tag.
- Version rules: `feat` is minor, `!` or `BREAKING CHANGE:` is major, every other type is patch, a non-Conventional commit releases nothing. The first release is 0.1.0.
- `ci.yml` no longer triggers on push to `main` (`release.yml` calls it instead, so main is not checked twice). It is now reusable and takes an optional `version`. With one, it stamps that version into the desktop and MCP `package.json` on the runner, builds installers (`pnpm pack:installers`: NSIS, both DMGs, deb only), runs the packaged tests, and uploads the installers. A manual run with a version builds them without publishing.
- `.github/workflows/pr-title.yml` + `commitlint.config.mjs`: PR titles must be Conventional Commits. AGENTS.md now tells agents the convention and how to check a title.
- `electron-builder.yml`: installer names like `Knightbook-0.1.0-macos-arm64.dmg`. The MCP server now reports its `package.json` version instead of a hard-coded 0.0.0.
- The scripts live in `scripts/publishing/` because `release/` is gitignored as electron-builder output.

**How it was checked.**
- `pnpm check` passes: core 275, MCP 47, desktop 639 (3 skipped), editor-preservation 21 (3 skipped), packaging 54 (1 skipped).
- 21 publishing tests:
  - next-version runs real semantic-release against a temporary repository with a bare origin. Observed: 0.1.0 first, 0.1.1 for docs or fix, 0.2.0 for feat, 1.0.0 for `feat!`. Nothing is released for a non-Conventional commit, or for a re-run once the tag exists.
  - publish-release runs against a fake GitHub:
    - a fresh publish produces create, upload, publish, with the tag at the tested commit;
    - a repeat run writes nothing;
    - a tag at another commit, a changed installer, or the same size with different bytes are all refused with no writes;
    - an interrupted upload leaves only an untagged draft, which the next run replaces;
    - a missing installer writes nothing.
- commitlint accepts `feat: …`, `feat!: …` and `fix(mcp): …`, and rejects a plain title.
- A real Windows installer was built locally: `Knightbook-0.0.0-windows-x64.exe`, 135 MB. It went to a scratch folder because the packaged app was running and the release-folder guard correctly refused.
- Workflow YAML parses.
- Verifier: 0 covered, 6 weakly covered, 1 uncovered, 3 not code criteria. Two gaps it found were closed afterwards (re-run after tagging, same-size rebuilt installer).

**Not verified.**
- None of the three workflows has run on GitHub. Untested in practice:
  - job gating (a failed platform skips `publish`);
  - semantic-release's push check with the real token;
  - artifact hand-off between jobs;
  - `gh` finding a draft by tag name.
- The macOS DMG and Linux deb names were not observed. The check accepts `x64` or `amd64` for the deb.
- No installer was installed or upgraded on any platform. Untested: a clean install launching the app and MCP, and an upgrade keeping the saved MCP command. The packaged tests run on the unpacked app beside the installers, not on what is inside them. This overlaps the Windows, Linux and macOS validation tickets.
- Two merges close together are untested. Serialization relies on `concurrency: release`. A third merge during a release replaces the waiting run, so the next release covers both merges under one version (documented).
- PR-from-a-fork behaviour was not observed in run logs.
- The `version` job gives semantic-release a write-capable token, which it needs for its push check. It pushes nothing, but third-party code runs with that token.
- Actions minutes: the repository is private, and every merge builds on macOS (10× minutes) and Windows (2×), as CI already did on merge.

**For you to check.**
1. Repository settings: allow squash merging only, and set the squash commit title to the pull request title. These are not in code.
2. Open the PR with a Conventional title, for example `feat: publish a GitHub prerelease on every merge to main`. The `Pull request title` check should pass.
3. Before merging, on the Actions tab run **CI** on `feature/release-automation` with version `0.0.1`. Confirm all three platforms pass and there are four installers across the `installers-*` artifacts. This is the first real sighting of the macOS and deb names.
4. After merging, the Release run should publish **v0.1.0** as a prerelease with four installers and `SHA256SUMS.txt`, at the merge commit. Re-running its jobs should succeed and change nothing.
