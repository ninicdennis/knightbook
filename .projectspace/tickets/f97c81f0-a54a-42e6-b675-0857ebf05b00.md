# Readable review history folders

## Intended outcome
The review history on disk is easy to browse: tickets and documents are separate, and folder names are real names, not percent-encoded ids. Existing review history keeps working.

## Acceptance criteria
- New reviews are written under reviews/tickets/<ticket-id>/ and reviews/documents/<project-relative path>/, with real nested folders and no percent-encoding.
- Review history already on disk in the old layout (reviews/ticket%3A... and reviews/document%3A...) keeps working. It is read as before, never moved, renamed or rewritten, and opening a project still writes nothing.
- The latest review is the newest one across both layouts, so a review recorded before the change and one recorded after it are compared correctly.
- A document path cannot place a review folder outside reviews/documents/, and a ticket id that is not a single plain folder name is refused. Both are tested, including traversal attempts.
- Snapshot file names and contents are unchanged: still one immutable file per review, holding a full copy of what was reviewed.
- The technical design's description of the layout is updated to match.

## Notes
This is option A from the review-layout research. Two things are deliberately left alone. Reviews of documents are still keyed by path, so renaming or moving a document still loses its review history; stable document ids (option B) are a separate decision. And nothing is written next to the user's documents.

## Handoff

**What changed:** Snapshot storage moved out of `review.ts` into a new `packages/core/src/review-storage.ts`, which owns both layouts.

- New snapshots go to `.projectspace/reviews/tickets/<ticket id>/` and `.projectspace/reviews/documents/<the document's own project-relative path>/`, as real nested folders with nothing percent-encoded.
- The old flat folders (`reviews/ticket%3A...`, `reviews/document%3Adocs%2F...`) are still read. They are never moved, renamed or rewritten, and nothing writes to them again.
- `readSnapshots()` reads both layouts and sorts by the recorded `reviewed_at`, with the file name as a tiebreak, so the latest review is the newest across the two rather than whichever folder was looked at first. `lastReview` and `reviewedSource` are now thin wrappers over it, which also fixed an inconsistency: `reviewedSource` previously picked by file name while `lastReview` picked by parse order.
- Record ids are validated before they become a path. A ticket id must be a single plain folder name, and every segment of a document path is checked, followed by a containment check that the result stays under `reviews/<kind>/`. A record id that cannot satisfy that is refused with `invalid_record` rather than written somewhere else.
- Snapshot file names and contents are untouched: still `<reviewed-at>.md` with the same frontmatter and a full copy of the reviewed source.
- `docs/project-workspace-technical-design.md` section 3 now shows the new tree, describes the rules, and records that the old layout keeps working.

**How it was checked:** `pnpm check` passes: lint, formatting, typecheck and 317 tests, 0 failures. 11 new tests in `packages/core/src/review-layout.test.ts` cover each acceptance criterion, including that an unreviewed record writes no folders at all, that a legacy folder is byte-identical after a new review is recorded beside it, that an old-layout review which is genuinely the most recent still wins, and traversal attempts through both a ticket id and a document path.

It was also run against this repository's own review history, which is entirely in the old layout. A freshly built MCP server (`pnpm build:mcp`) returned the same review states and timestamps for all six documents as the previously packaged server did before the change -- for example README.md still reads `changed_since_review` at 2026-09-19T23:15:41.299Z. `git status .projectspace/reviews` is clean afterwards, so nothing was moved, rewritten or created.

**Not verified:** No review was recorded against this project through the new code path, so no folder in the new layout exists on real data yet -- only in the test fixtures. Recording one would have meant asserting a human review that did not happen. Case-colliding paths on a case-insensitive filesystem are not handled here any differently than before; two documents differing only in case would share a review folder. Nothing was checked on macOS or Linux.

**For you to check:** Record a review in the app on a ticket and on a document, then look at `.projectspace/reviews/` and judge whether it reads the way you wanted. Confirm the old folders are still sitting there untouched next to the new ones, and that the app shows the same review state for a document reviewed before this change.

## Addendum: this project's own history was migrated (2026-09-20)

At the user's request, and after this ticket reached Verification, the review history in this repository was moved by hand into the new layout. This does not change what the ticket delivered: the app still never moves, renames or rewrites an old folder, and the dual-read is still there for other checkouts and older branches.

**What moved:** all 33 record folders, 39 snapshots. Every snapshot's own `record_id` was checked against its folder name first, and nothing would have moved if one disagreed. Git records all 39 as R100 renames, so no file's bytes changed.

**How it was checked:** a content inventory keyed by `record_id` was taken before and after; the record ids and every file hash are identical. Read back through a freshly built MCP server, all six documents report the same review state and timestamp as before the move, and ticket reviews still resolve to the newest snapshot. `.projectspace/reviews/` now holds only `tickets/` and `documents/`.

**Consequence worth knowing:** this project no longer exercises the old layout, so the dual-read is now covered only by the tests in `packages/core/src/review-layout.test.ts`.
