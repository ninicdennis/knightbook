# Name the installed app Knightbook, not @knightbookdesktop

## Intended outcome
The Windows install folder, the Linux executable and the Linux launcher are named after the product before the first public release, while changing them still breaks nobody's saved MCP configuration.

## Acceptance criteria
- The Linux deb installs the executable and launcher as `knightbook` (or another name the user chooses), not `@knightbookdesktop`.
- The Windows installer installs per user into a folder named Knightbook, not `%LOCALAPPDATA%\\Programs\\@knightbookdesktop`.
- The installation guide and packaging findings are updated to the new paths.
- A test fails if the package metadata would bring the `@knightbookdesktop` names back.

## Notes
Found while writing the installation guide (ticket 6281905f); details in the packaging findings, "The Linux deb in a test container (2026-10-21)". electron-builder derives both from the package name `@knightbook/desktop`: the executable from `executableName` (unset), the per-user NSIS folder from `sanitizedName` when `oneClick` is on and `perMachine` off. Both paths are written into users' MCP configurations, so the change is cheapest before 0.2.0 ships. It changes the desktop app, so it releases (D-041). The Windows folder has not been seen on a real install.

## Handoff (2026-10-21)

### What changed
- `electron-builder.yml`: `extraMetadata.name: Knightbook` (the name electron-builder derives the install names from; the workspace package stays `@knightbook/desktop`) and `linux.executableName: knightbook`.
- Linux: command `/usr/bin/knightbook`, launcher `knightbook.desktop`, binary `/opt/Knightbook/knightbook`. Windows: per-user folder `%LOCALAPPDATA%\Programs\Knightbook`, executable `Knightbook.exe` as before. Unchanged: `/opt/Knightbook`, the deb package `knightbook`, the settings folders (the app calls `app.setName('Knightbook')`), the MCP command path on Linux, the macOS bundle, the Windows uninstall registry key.
- New `apps/desktop/scripts/installed-names.test.mjs`.
- Installation guide: the Windows folder is named, and the Linux command. Packaging findings: what was seen after the fix.

### How it was checked
- `pnpm check` passed (desktop 663 passed, 4 skipped; packaged-app suites skipped, nothing packaged at the time).
- Criterion 1 (Linux): built the deb (`pack:installers --linux deb`, versions 0.0.1 and 0.0.2) and installed it on Ubuntu 24.04.5 in a container: `/usr/bin/knightbook` through update-alternatives, `knightbook.desktop` running `/opt/Knightbook/knightbook`. Launched as an ordinary user under `xvfb-run`: settings in `~/.config/Knightbook`, MCP command `/opt/Knightbook/resources/mcp/node`. Upgrade from a deb built with the old name: the `@knightbookdesktop` command and launcher were removed, `app-state.json` kept.
- Criterion 2 (Windows): built the NSIS installer on Linux with `DEBUG=electron-builder` up to the uninstaller step (needs Wine). `makensis` got `APP_FILENAME=Knightbook`; the same build with the old name got `APP_FILENAME=@knightbookdesktop`.
- Criterion 3: read; the guide and findings name the new paths.
- Criterion 4: `installed-names.test.mjs` loads `electron-builder.yml` through electron-builder's own config loader and asks its `AppInfo` and `getWindowsInstallationDirName`. With `extraMetadata` and `executableName` removed from the config it failed with `@knightbookdesktop` for both names; a second case keeps that regression proven.
- The verifier agent was not run.

### Not verified
- A real Windows install. An existing 0.1.x Windows install keeps its old folder on update, because NSIS reuses the saved `InstallLocation` (read from `multiUser.nsh`); uninstall and reinstall to move it.
- macOS (expected unaffected: the bundle comes from `productName`), the AppImage, a real desktop's menu.
- The Linux rule for the command is mirrored from `linuxPackager.js` in the test, not called.

### For you to check
- On Windows, install the next build and look for `%LOCALAPPDATA%\Programs\Knightbook`.
