# Validate on Linux (deb, x64)

## Intended outcome
The core workflow is confirmed on a real Linux x64 machine using the deb package, the Linux format D-028 ships first.

## Acceptance criteria
- The deb installs on a maintained distribution (say which one and its version) and the app starts.
- An MCP client connects with the app closed and no system Node on the PATH, and can list and update tickets.
- The saved MCP command still works after reinstalling or upgrading the deb, since the fixed install path is why deb ships first.
- Edits made outside the app (editor, Git) appear correctly after focus or Refresh.
- A project created on Windows opens on Linux without broken links, and the reverse.
- Results recorded in the packaging findings: distribution, desktop environment, package tested, what passed, what did not.

## Notes
Split from "Validate macOS and Linux" (5ddb9586) on 2026-09-26 so each platform can be validated on its own hardware. AppImage is out of scope here: it is validated on Linux as part of ticket 68f54f52, which makes the MCP helper persistent, and stays out of released targets until then (D-028). Linux arm64 and rpm are not built (D-028). The app window has only been launched on Windows so far; CI builds and tests Linux but does not open the window. The user validates on their own hardware.

## Handoff
**What changed:** No app code. The published 0.2.0 Linux deb was taken through install, first launch, the getting-started guide with Claude Code, reinstall, upgrade, remove and purge in a fresh `ubuntu:24.04` container on 2026-10-22. Results are in [the packaging findings](../../docs/experiments/packaging-findings.md#the-published-linux-deb-in-a-fresh-container-2026-10-22). The installation, getting-started and connecting-AI guides now say what this run confirmed on Linux, and the installation guide tells readers to install `libasound2t64` if the app will not start. New bug ticket [75d7db08](75d7db08-02c1-4dd6-a9c2-476e322e05e9.md): the deb does not depend on the ALSA library, so the app does not start on a minimal Ubuntu 24.04.

**How it was checked, per criterion:**
- Installs and starts: Ubuntu 24.04.5 LTS x64. `apt install ./Knightbook-0.2.0-linux-amd64.deb` (checksum matched `SHA256SUMS.txt`) installed with no warning. The app did not start until `libasound2t64` was installed (ticket 75d7db08); then the window opened to **Choose a project folder** on Xvfb.
- MCP with the app closed and no Node: with no app process and `PATH=/usr/bin:/bin`, Claude Code 2.1.308 showed `knightbook` connected through the pasted copied configuration, and the installed server listed tickets and created one over stdio. With the app open, Claude Code answered the check prompt correctly and handed off a ticket into Verification, and the window read **MCP available**.
- After reinstall or upgrade: `apt install --reinstall` of 0.2.0, then an upgrade to a 0.2.1 deb built from `main` (no newer release exists). Settings, `mcp-access.json` and `~/.claude.json` unchanged byte for byte; `knightbook` still connected and serving the project.
- Outside edits: a change to `README.md` from a shell appeared after **Refresh from disk** and not before.
- Windows project on Linux: this repository's own board, written on Windows, opened with no record problems; the README's in-project image loaded and a relative document link opened in the app.
- Findings recorded: distribution, desktop (none, Xvfb), package, what passed and what did not.
- `pnpm check` passed (run under `xvfb-run`, since a local package now exists and the packaged-window tests ran).

**Not verified:**
- A real machine. This was a container with no desktop environment, no window manager, no AppArmor and no system D-Bus; the ticket asks for a real Linux x64 machine.
- Refresh on focus: focus could not be moved away and back without a window manager.
- **Edit externally**: no editor in the container.
- Claude Code signed in on the same machine as the app: it could not sign in inside the container, so the check prompt and handoff ran from Claude Code on the host, starting the container's installed server.
- A project made on Linux opened on Windows (the reverse direction).
- The launcher in a real desktop menu, and the AppArmor profile the package installs.
- Accepting a handoff as Done in the app.
- The `verifier` agent was not run: this ticket has no code or tests, and every criterion was checked by hand as listed above.

**For you to check:** whether a container run is enough for this ticket, or it stays open for a real Linux machine (desktop, focus refresh, Edit externally, the reverse direction). The guide wording in installation, getting-started and connecting-ai, especially the `libasound2t64` note.
