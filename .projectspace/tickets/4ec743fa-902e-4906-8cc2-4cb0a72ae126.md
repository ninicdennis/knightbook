# Header ticket search

## Intended outcome
Find information in the current project's tickets without scanning columns or opening every card. A centered header search control and Ctrl+K on Windows/Linux or Cmd+K on macOS open the same focused search experience.

## Acceptance criteria
- Place a clearly labeled Search tickets control in the center area of the header, between project identity and navigation/utilities, with a platform-appropriate keyboard shortcut hint. Keep it usable at narrow window widths and alongside the planned MCP status indicator.
- Clicking the control or pressing Ctrl/Cmd+K opens and focuses search from Board or Documents (and Archive when available). It is an application-scoped shortcut, not a system-wide shortcut. Handle editable fields and existing dialogs deliberately without losing unsaved text or conflicting with editor link shortcuts.
- Search both ticket titles and the full Markdown description/body, including acceptance criteria, notes, and handoffs. Use trimmed, case-insensitive text matching; body-only matches must work. Start with predictable text matching; fuzzy search, semantic search, document search, and a general command palette are outside this ticket.
- Show matching title, workflow status, and a short relevant excerpt with highlighted matches. Prefer title matches to body-only matches with deterministic ordering. Treat ticket text as display data and render highlights safely.
- Arrow keys navigate results, Enter or a click opens the existing full ticket detail, and Escape closes search and restores focus. Provide accessible labels and sensible empty-query, no-results, loading, and error states.
- Results belong only to the selected checkout. Discard stale responses when queries or projects change, and refresh after ticket changes. Limit rendered results with an explicit indication if more results exist; documents must not consume a ticket-only search limit.
- Verify title-only and body-only matches, case and whitespace handling, keyboard navigation and focus, project switching during a request, external ticket edits, and safe rendering of unusual Markdown/HTML text. Check layout with long project names and narrow windows.

## Research and implementation notes
Research date: 2026-09-19. The technical design already calls for bounded text/title search through shared core logic, with full records loaded on demand. The live project_search MCP tool returns ticket/document snippets. Reuse the existing core search and ticket detail pathways where practical; do not assume the mixed document/ticket MCP search is already a suitable ticket-only UI API.

Mantine's official Spotlight documentation describes a modal search component, default Ctrl+K/Cmd+K shortcuts, result limits, and label/description matching: https://mantine.dev/x/spotlight/. This is a candidate consistent with the existing UI toolkit, not a requirement to add a package; check compatibility with the installed version and compare the simplest existing Mantine components during implementation.

Search can ship before archiving. The Archive ticket owns adding archived results and scope controls once archive metadata exists. Neither ticket authorizes implementation yet.
## Handoff

**What changed:** A Search tickets control sits in the centre of the header, and Ctrl+K (Cmd+K on macOS) opens the same dialog from anywhere in the window.

- `packages/core/src/ticket-search.ts` (new) does the matching: plain, case-insensitive substring matching over titles and full bodies, bounded to 20 returned hits while still counting every match. It is deliberately separate from `searchProject`, which mixes tickets and documents — sharing one budget with documents would silently drop tickets, which the ticket forbids.
- Matching and display both work on a whitespace-collapsed copy of the text, so a query spanning a line break still matches and a highlight offset means the same thing in both.
- Highlights come back as **offsets, not markup**. The renderer slices the string and puts the pieces in as React children, so a ticket containing `<script>` or an `<img onerror=…>` shows those characters instead of doing anything. That is the whole answer to "render highlights safely".
- Ordering is deterministic without a relevance score: every title match ranks above every body-only match, and inside each group the board's own backlog order decides.
- `apps/desktop/src/main/ipc.ts` adds `ticket:search`. It runs in the host because bodies are on disk, not in the window. The reply echoes the checkout path and the query, and the window discards any answer that does not match what it is currently asking — alongside a per-request sequence number, so a slow reply cannot overwrite a newer one.
- `apps/desktop/src/renderer/components/TicketSearch.tsx` (new) is the dialog: a 120ms debounce, a loading spinner in the field, and distinct empty-query, no-results, error, truncated and unsearchable states. Arrow keys move and wrap, Enter or a click opens the existing ticket detail, Escape closes.
- `apps/desktop/src/renderer/shortcuts.ts` (new) holds the chord rules. The shortcut is ignored while focus is in an input, textarea, select or contenteditable, which protects unsaved text and leaves a formatted editor's own Cmd/Ctrl+K for links alone. It is also ignored while another dialog is open, so it cannot bury something the user is answering. Each platform has exactly one chord: Cmd+K on macOS, Ctrl+K elsewhere, never both.
- Focus return is explicit rather than left to the dialog's default, so it behaves the same however search was opened and can be tested.
- The header row is now three regions (identity, search, actions). The control shrinks before it wraps and its shortcut hint hides below the md breakpoint.

**Decisions worth knowing:** Mantine Spotlight was considered and not used. It is a separate package this project does not have, and the honest states this board needs — "N ticket files could not be searched", "showing 20 of 34" — are easier to state directly than to fit into it. Two `jsx-a11y/prefer-tag-over-role` suppressions were added inline with a reason: a `select`/`option` pair cannot hold a status badge, a marked title and a two-line excerpt, so the ARIA listbox pattern is correct here. They are inline rather than switched off in `.oxlintrc.json` so the rule stays live everywhere else.

**How it was checked:** `pnpm check` passes: lint, formatting, typecheck and 341 tests, 0 failures. 12 new core tests in `packages/core/src/ticket-search.test.ts` and 12 new renderer tests in `apps/desktop/src/renderer/Search.test.tsx` cover title-only and body-only matches, case and whitespace handling including a match across a line break, ranking, the bounded limit with a full count, deterministic repeat results, keyboard navigation and wrapping, focus return, a stale reply being discarded, a failed search, an unreadable ticket file being reported, and that a title full of HTML renders as text with only the matched run marked.

It was also exercised in the design preview: results with highlighted matches, the no-results state, the loading spinner, opening a result into the ticket detail, and the header at 760px wide where the control shrinks and the shortcut hint hides.

**Not verified:** Not run in a real Electron window, so the shortcut has only been exercised as a DOM keydown — nothing confirms Electron does not swallow Ctrl/Cmd+K first. macOS was not tested at all, so the Cmd+K branch and the ⌘K label are unverified on the platform they are for. Search was not run against a project large enough to say anything about speed; every ticket body is read on each keystroke after the debounce. Switching project while a request is in flight is covered by the echo check in a test, but was not done by hand.

**For you to check:** Whether the centre of the header is where you want search, and whether the excerpt gives you enough to tell why a body-only match came back. Try Ctrl+K while typing in a ticket's reason box and confirm nothing is lost. Judge whether 20 results before "narrow the search" is the right cut.
