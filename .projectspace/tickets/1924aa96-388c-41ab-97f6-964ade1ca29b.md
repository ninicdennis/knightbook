# Rewrite README as a concise developer entry point

## Intended outcome
A new reader can understand Knightbook, run the project, and find the relevant documentation without reading naming history or an implementation diary.

## Acceptance criteria
- Lead with a short product description and the current core capabilities; retain the Knightbook identity and logo without explaining the naming decision in the introduction.
- Provide a clear getting-started sequence, prerequisites aligned with package.json, development/run commands, checks, and packaging. Distinguish the stub-data board preview from the real Electron app.
- Keep a compact repository layout and MCP/skill setup entry point. Link to detailed workflow, architecture, packaging, and troubleshooting documents rather than reproducing their internals.
- Remove the long implementation-status matrix and historical rename narrative. Preserve genuinely useful compatibility or troubleshooting instructions in the relevant existing documentation or one focused guide, linked where needed.
- Verify every documented command against scripts and every relative link against the repository. Avoid hard-coded tool counts, unverified claims that CI is green, or implying proposed features and releases already exist.
- Make command examples usable for the stated shell, including PowerShell on Windows. Do not install global tooling or change build scripts as part of the rewrite.
- Read the finished README as rendered Markdown and confirm it answers what this is, how to start, and where to learn more.
