# Set and clear a ticket's blocker in the app

## Intended outcome
The user can record why a ticket cannot move, or clear that reason, from the ticket detail view.

## Acceptance criteria
- The detail view has a control to add, edit and remove the blocker text.
- Clearing the blocker stores no blocker (null), not an empty string.
- The card's blocker badge appears and disappears to match, without a manual refresh.
- The write carries the ticket's revision and handles a conflict the same way other ticket edits do.

## Notes
Today the blocker is displayed on cards and in the detail view but can only be written through MCP or by hand.

## Handoff
**What changed:** A new contract operation `setTicketBlocker(rootPath, id, blocker | null, revision)` in `apps/desktop/src/shared/ticket-edit-contract.ts`, handled by `ticket:setBlocker` in `src/main/ticket-edit-ipc.ts` (kept out of `contract.ts` and `ipc.ts`, which are near the size limit). The host trims the text and stores blank text as no blocker, through core `updateTicket` with the read revision. In the renderer, `components/TicketBlocker.tsx` replaces the read-only Blocked alert in the detail view: "Add a blocker" when there is none; Edit and Clear blocker on the alert when there is one; the editor saves with a button or Ctrl+Enter and cancels with Cancel or Escape. The write goes through the same `apply` path as moves and type changes (`useTicketActions.setBlocker`), so the board view is replaced with what the files say and a conflict reloads and shows a message. The preview stub implements the new operation.

**How it was checked:** New `src/renderer/TicketBlocker.test.tsx` (add, edit, clear by button, clear by saving empty text, Escape cancels without closing the dialog, conflict reloads with a message, caret at the end when editing) and `src/main/ticket-edit.test.ts` (trimming, null for empty or whitespace, refusal of non-text). In `pnpm preview:board` at 1280×800 and 375×812: the Blocked alert shows Edit and Clear, the editor opens with the current text, Escape cancels and leaves the dialog open, and an unblocked ticket shows "Add a blocker". Full `pnpm check` passes.

**Packaged app, checked 2026-09-25 (build packaged 12:41, on this ticket itself):** Add a blocker with Ctrl+Enter wrote `blocker: "Test blocker from Claude: waiting on nothing."` to the file and the card showed the Blocked badge at once; Edit changed it; Clear blocker removed the line entirely; adding one again and saving empty text also removed the line (no `blocker: ""`). Review stayed "Reviewed by you" throughout, since the blocker is bookkeeping. The ticket file now ends with no blocker and a newer `updated_at`.

**Found and fixed in that run:** Edit put the caret at the start of the existing text, so typing went in front of it. The field now places the caret at the end; confirmed in Chromium through the board preview (caret at 67 of 67 characters) and by the unit test. This fix is not in the packaged build you have open; it needs `pnpm pack:dir` after closing the app.

**Not verified:** Escape in the packaged app. The desktop-control tool's Escape did not reach the app at all (it also failed to close the dialog, which normally works), so the packaged run could not test it; Escape cancelling the edit was confirmed in Chromium in the board preview and by the unit test. As with type changes, a conflict message appears on the board behind the dialog, not inside it; that is the existing behaviour this follows.

**For you to check:** After repackaging, press Edit on a blocker and confirm the caret sits after the text, and that Escape cancels the edit without closing the ticket.
