# Stage the Node runtime per macOS architecture

## Intended outcome
The macOS arm64 and x64 builds each carry the Node runtime for their own CPU, so the Intel app can start its MCP server.

## Acceptance criteria
- `pnpm build` (or the packaging script) stages a runtime for each macOS architecture being built, not one runtime shared by both.
- `electron-builder.yml` takes the MCP resources from a per-architecture folder, for example `resources/mcp-${arch}`, so one mac build produces two correct packages.
- A test checks that each packaged architecture contains the Node binary for that architecture (for example by reading the Mach-O header), and fails when they are swapped or shared.
- Windows and Linux packaging keep working, and `pnpm check` and `pnpm pack:dir` pass.
- The packaging findings say what was verified and on which machine.

## Notes
Today `scripts/stage-mcp-runtime.mjs` stages one runtime into `resources/mcp/`, and electron-builder copies that folder into every architecture in the run. The mac config builds `arm64` and `x64` together on the Apple silicon `macos-latest` runner, so both DMGs would carry the arm64 Node. Required by D-028 before macOS x64 ships. Option 1 in docs/proposals/platform-support.md; building each architecture separately (option 2) is the fallback if the `${arch}` macro does not behave as documented. Running the x64 binary on the arm runner needs Rosetta; say so if it was not available.

## Handoff
**What changed:** Option 1. `scripts/stage-mcp-runtime.mjs` stages each architecture into `resources/mcp-<arch>/`; a macOS stage fills both arm64 and x64 unless `--arch` narrows it (`--arch` takes a list; `--out` now names the resources folder). It refuses a staged runtime whose header names another CPU. `electron-builder.yml` reads `resources/mcp-${arch}`; installed it is still `mcp`, so saved client commands do not change. The unpackaged app reads `resources/mcp-<its arch>` (`mcp-resources.ts`). New `scripts/binary-architecture.mjs` reads the CPU from Mach-O, ELF and PE headers. `MAC_ARCHES` in `node-runtime.mjs` is held to the mac target in the config by a test. `experiments/packaging`: `packaged-architecture.test.ts` compares each packaged app's Node with its own executable; `architecture.test.ts` runs that rule on fake Mach-O packages. New section "One runtime per architecture" in the packaging findings; AGENTS.md gotcha path updated.
**How it was checked (Windows 10 x64):** `pnpm check` passes. `STAGE_RUNTIME_NETWORK=1` runs pass: both macOS runtimes download, checksum and read as the right Mach-O CPU, and the new `stage-mcp-runtime.test.mjs` runs the script with `--platform=darwin` and finds `mcp-arm64/node` arm64 and `mcp-x64/node` x64 (it would fail on the old single folder). `architecture.test.ts` shows a shared and a swapped pair fail. `electron-builder --dir` into a scratch output packaged `resources/mcp-x64` as `resources/mcp`; Node and `Knightbook.exe` both read x64 PE, so `${arch}` expands. Verifier: 0 covered, 3 weakly covered, 2 not code criteria; the end-to-end staging gap it named was then closed with the network-gated test above.
**Not verified:** No macOS package was built (electron-builder does not build mac on Windows) and nothing ran on a Mac or under Rosetta. Whether CI's `--dir` on macOS packages x64 at all is unknown; if not, the packaged test only sees arm64 there. That is ticket eca73450. `pnpm pack:dir` itself did not run here: its release guard refused because the packaged Knightbook was open, so packaging went to a scratch folder. Linux packaging was not run locally. The header refusal in the staging script and the unpackaged `mcp-<arch>` path have no test. The script tests that download are off in `pnpm check`. An old `apps/desktop/resources/mcp/` from earlier builds is left in place (ignored by Git, no longer packaged).
**For you to check:** Start a manual CI run ("Run workflow") on the branch so Windows and macOS package; look at the macOS job's `release/` output to see whether both `mac-arm64` and `mac` appear. Locally, close the packaged app and run `pnpm pack:dir`.
