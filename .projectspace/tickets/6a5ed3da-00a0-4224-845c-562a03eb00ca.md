# Return a ticket's related documents through MCP

## Intended outcome
An AI tool that reads a ticket can find the documents it points at, without being told the paths separately.

## Acceptance criteria
- `ticket_read` includes `related_documents` in its payload.
- `ticket_list` rows either include them or the omission is deliberate and stated in the tool description.
- `ticket_update` accepts `related_documents`, so links can be corrected after creation.
- Leaving the field out of a `ticket_update` keeps the stored value, as with the other optional fields.

## Notes
Found running the specification validation scenario (ticket 2e4a254f), step 3: "have a different AI tool retrieve one ticket **and the relevant context** through MCP".

`ticket_create` accepts `related_documents` and the record stores it — a ticket file shows `related_documents: [ "docs/spec.md" ]`. But `ticket_read` returns `summarize(ticket, …)` plus `body` (packages/mcp/src/tools.ts:227), and `summarize` does not carry the field. Observed keys from a real call: `id, title, status, type, revision, depends_on, dependency_ready, dependency_notes, verification_issue, affected_by, completion, completion_unattributed, previous_completions, body` — no `related_documents`. Confirmed against this project's own ticket 1924aa96, whose file records `related_documents: ["README.md"]` and whose `ticket_read` does not mention it.

So the field is write-once and invisible: set at creation, never readable, never changeable. The workflow skill tells agents to "read every document in its `related_documents`", which is currently impossible through MCP alone.

## Handoff
**What changed:** (uncommitted, branch `feature/easy-wins`)
- `ticket_read` and every `ticket_list` row now include `related_documents` (they share `summarize` in `packages/mcp/src/tools.ts`).
- `ticket_update` accepts `related_documents`. It replaces the whole list; leaving it out keeps the stored value, and `[]` clears it. Backed by a new `relatedDocuments` field on `updateTicket` in `packages/core/src/tickets.ts`.
- Paths are stored as given, exactly as `ticket_create` already does; neither validates that the document exists or is included.

**How it was checked:** new `packages/mcp/src/related-documents.test.ts` runs the real handlers for all four criteria (read, list rows, replace and clear, omitted keeps). MCP 38/38, core 181/181, MCP typecheck clean. The rebuilt `packages/mcp/dist/server.mjs` returns `related_documents: ["README.md"]` for this project's ticket 1924aa96, the one the note cites.

**Not verified:** the packaged app in `apps/desktop/release/` has not been rebuilt, so the server your client uses does not have this yet. The desktop ticket view was not changed, and still does not show related documents.

**For you to check:** after `pnpm pack:dir`, ask your client to `ticket_read` a ticket that has linked documents and confirm they appear; then have it change them with `ticket_update`.
