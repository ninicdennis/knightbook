# Migrate repository branding and icons from Projectspace to Knightbook

## Intended outcome
Use Knightbook consistently as the product name throughout the repository and packaged application, with icons derived from the approved PNG logo.

## Acceptance criteria
- Audit Projectspace/projectspace references and replace current product branding with Knightbook across desktop UI, window titles, application metadata, package names and imports, build scripts, CI, examples, MCP setup guidance, workflow skill, and maintained documentation.
- Update Electron Builder product naming and generated artifact names; review application IDs, executable names, settings locations, and MCP identifiers for compatibility before changing them. Document any intentionally retained legacy identifiers.
- Generate and configure the required Windows, macOS, and Linux icon assets from docs/assets/knightbook-logo.png. Preserve the approved knight/book artwork and solid white pages without an internal horizontal line. Verify legibility at normal application icon sizes.
- Use the approved PNG only. The user rejected and removed the SVG; do not recreate, trace, or redesign it. Remove stale documentation claims and links referring to an SVG companion.
- Preserve existing projects, tickets, documents, reviews, completion records, settings, and recent-project history. Any change to .projectspace/ storage or existing configuration paths must have an explicit, tested compatibility or migration strategy; do not perform a blind string replacement on stored data.
- Ensure copied MCP configuration and the packaged bundled server still work, including with the desktop window closed. Explain any client configuration changes needed after the rename.
- Keep historical decisions and user-authored project names intact where they are historical data rather than current product branding.
- Run pnpm check and pnpm pack:dir, plus the required packaged-runtime tests against the built package. Visually verify the product name and icons in the app and OS shell; record platform checks actually performed and any remaining unverified targets.

## Notes
Knightbook is documentation and Kanban tooling for preserving project context under human direction, supplementing external AI tools. The user selected the name and approved docs/assets/knightbook-logo.png. The SVG attempts were rejected; the PNG is the sole approved source artwork.

Create the branding migration as future work in Backlog; do not start implementation merely because this ticket exists. Coordinate with the existing window-title, shell styling, and guided AI setup work where changes overlap.

No domain purchase, remote repository rename, release publication, new updater, or new AI feature is part of this ticket. Repository naming conventions and internal packages are in scope; moving the user's checkout directory is not required.

Related decisions: D-020 and D-021 in docs/project-workspace-spec.md. The documentation may still contain stale SVG references from the rejected attempt; the user's PNG-only direction here supersedes them.

## Handoff

**What changed.** 83 files. The product is Knightbook in the window, the packaged
application, the workspace packages, the MCP server, the build scripts, CI and the
maintained documentation. Two names are deliberately unchanged, below.

**The find that mattered.** The migration was written against `%APPDATA%/Projectspace`,
which is what the rename obviously implies. Then the running packaged app turned out to
report `--user-data-dir="C:\Users\Denny\AppData\Roaming\@projectspace/desktop"`. The app
never called `app.setName`, so Electron fell back to the `name` in package.json — scope
and all — and that is where the real state lives. Both directories exist on this
machine: the scoped one was written minutes ago and holds the actual recent projects and
settings; `Projectspace/app-state.json` is a stale file from 2026-09-19 with an
old-format entry. A migration aimed at the obvious path would have found the stale one
and adopted it over the real one, which is worse than finding nothing.

So two things followed. The app now calls `app.setName('Knightbook')` before anything
asks for a path, making the state directory the product's name on every platform in both
development and packaged runs instead of whichever field happened to win. And the
migration takes an ordered list of candidates — the scoped path first, the older one
second — and adopts the first that exists. It copies rather than moves, so an older build
installed alongside still finds its own state, and it never overwrites state the new name
already has.

**Retained legacy identifiers**, as the ticket asks to document:

- **`.projectspace/` storage.** Unchanged, in every project. Renaming it would be a
  migration of the user's own files rather than of this product, and the ticket rules out
  a blind replacement of stored data. Recorded in the README, D-020 and the packaging
  findings.
- **`skills/projectspace/` and the skill's `name: projectspace`.** Kept because you asked
  that filenames not change, and because tools that already load the skill refer to it by
  that name. Its prose now says Knightbook throughout. `guidance.test.ts` still asserts
  the path and name, so they cannot drift by accident.
- **The project record for this repository still has `name: "Projectspace"`.** That is a
  user-authored project name inside `.projectspace/project.md`, which the ticket says to
  keep as historical data. Change it in the app if you want it to read Knightbook; I did
  not edit stored records.

**Icons.** `apps/desktop/build/icon.png` is a 1024×1024 resize of
`docs/assets/knightbook-logo.png`, made with Electron's own `nativeImage` so no image
dependency was added. electron-builder derives the Windows `.ico` and macOS `.icns` from
it at package time, so there is one source image rather than three that can drift. The
stale SVG claims are gone from the assets README, D-021 and the landing-page document.

Legibility, since the ticket asks: at 48px and 32px the knight and the book read clearly.
At 16px — a small Windows taskbar, a favicon — it reduces to a navy tile with a pale
shape. That is inherent to artwork with this much detail, not something the resize
introduced, and it is written down in the assets README rather than left to be
rediscovered.

**Client configuration.** The installed folder is named after the product, so an MCP
command saved while this was Projectspace points at a path the new install does not use.
The client fails to start the server rather than reaching a wrong one. Re-copy from the
status bar after upgrading; the entry's name in your own config is yours and need not
change. The server reports itself as `knightbook` now. Explained in the README and the
packaging findings.

**How it was checked.** Lint, formatting and typecheck clean across all five packages.
Every suite passes: core 145, MCP 20, desktop 232 (1 skipped), editor-preservation 22 (3
skipped), packaging 28. Eight of those are new, covering the migration: the scoped path
winning over the older one, falling through when it is absent, never overwriting, running
only once, leaving the old file alone, a first run, and a copy that cannot be made.

The MCP bundle was rebuilt and restaged, and the packaging experiment then passed against
it — including the test that asserts the server announces itself on stderr, which is now

### Addendum: the icon was being ignored by Git (2026-09-20)

Caught on a last pass over the diff. `.gitignore` had a bare `build/` rule, meant for
build output, and it matched `apps/desktop/build/` — electron-builder's
`buildResources` directory. The icon would have stayed on this machine: every fresh
checkout, including CI, would have packaged the app with no icon at all, and nothing
would have failed to say so.

`.gitignore` now re-includes that one directory, with a comment saying why it is
source rather than output. Confirmed with `git check-ignore`: the file is tracked.

### Addendum: CI packaged it, which retires most of the unverified list (2026-09-20)

Three platforms green on the pull request, and the macOS job did what this machine
could not.

**One real miss first.** `packaged-app.test.ts` spelled the macOS bundle out as
`Projectspace.app`. A macOS bundle is named after the product, so after the rename
CI packaged the app and then could not find it. The branding sweep covered `apps/`
and `packages/` and skipped `experiments/`, which is the kind of gap a hardcoded
name invites. The candidates are now discovered — any `*.app` inside a `mac*`
output directory — and Windows and Linux keep their literal paths, which are named
for the platform rather than the product.

Worth knowing how that would have looked without CI: this test skips when no
package is present, so a stale bundle name turns the checks into silent skips on a
developer's machine. Only `REQUIRE_PACKAGED_APP=1` made it speak. A check that
quietly stops checking is what that file exists to prevent, so the reasoning is
recorded beside the code.

**What the green run then proved:**

- **`pack:dir` works with this branding.** The desktop app packaged on all three
  platforms, which means electron-builder derived the Windows `.ico` and the macOS
  `.icns` from `build/icon.png` — the icons had never been built anywhere before
  this.
- **The `.gitignore` fix was necessary and sufficient.** CI builds from a fresh
  checkout, so the icon reaching the packager at all is the proof that it is now
  committed.
- **The packaged Knightbook server runs.** On macOS the three packaged-app checks
  ran against the real bundle rather than skipping: 28 passed, no skips, including
  the lifecycle driven with no Node on PATH and no Electron process in existence.
- **The hand-edited `pnpm-lock.yaml` was accepted** by `pnpm install --frozen-lockfile`
  on all three runners, so the `@knightbook/*` scope rename is consistent.

**Still not verified:** nobody has opened the window. The renamed title, the menu and
the icon have not been seen by a person, and the state migration has still never run
against a real Electron `userData` directory — only against temporary directories in
tests. That is the remaining thing worth doing by hand.
