# Website Content-Security-Policy and Referrer-Policy as meta tags

## Intended outcome
Every page of knightbook.xyz tells the browser what it may load (a Content-Security-Policy) and how much of its address to send on to other sites (a Referrer-Policy), so an injected script or a stray third-party resource is refused by the browser.

## Acceptance criteria
- Every page the layout renders has a `Content-Security-Policy` meta tag as the first element after `charset` in its head, and a `referrer` meta tag of `strict-origin-when-cross-origin`.
- In a production build, the policy lets Umami's script load from `https://data.aikoworks.com` and post its visit to that host; a preview build's policy does not name that host.
- Every page of a production build loads in Chromium with no CSP violation, including the inline `<style>` blocks Astro emits and the colour `style` attributes on code blocks.
- The policy is really enforced: a script from another origin, an inline script and an image from another site are refused on a built page.
- The decision is recorded in the specification, with why meta tags and what they cannot do.

## Notes
Denny scanned the site at securityheaders.com and got an F (2026-10-23). GitHub Pages sets no custom headers, so Denny chose meta tags (option 1 in the project chat) over moving DNS to Cloudflare. The scanner only reads headers, so its grade will not change; browsers do follow the meta tags. `frame-ancestors`, `X-Frame-Options`, HSTS and `Permissions-Policy` cannot be set from a meta tag. Turning on Enforce HTTPS in the Pages settings is Denny's step, outside this change.

## Handoff
**What changed:** `BaseLayout` now opens every page head with a Content-Security-Policy meta tag (from `apps/website/src/layout/security-policy.ts`) straight after charset, then `<meta name="referrer" content="strict-origin-when-cross-origin">`. The policy allows only the site's own origin, adds `https://data.aikoworks.com` to script-src and connect-src only in a production build, allows inline styles but no inline scripts, and sets object-src 'none', base-uri and form-action 'self'. New `security-policy.test.ts`; `layout.test.ts` checks the preview policy; the static file server the accessibility test used moved to `src/test/static-server.ts` so both share it. D-053 in the spec and an entry in the technical design.
**How it was checked:** `pnpm check` passes (website 252 tests, with Chromium). `security-policy.test.ts` builds for production and opens all 13 layout pages in Chromium with a stand-in Umami script that posts a visit: no violations, one post per page. It injects a remote script, an inline script and a remote image and sees all three refused. Mutation checks: dropping 'unsafe-inline' from style-src fails it (404 page's inline style), dropping Umami from connect-src fails two tests. `astro dev` also loads with no CSP errors. Verifier: 4 covered, 0 weak, 0 uncovered, 1 settled by reading (the spec decision).
**Not verified:** The real Umami script was never loaded (the cloud session cannot reach data.aikoworks.com); the stand-in posts to /api/send the way Umami's docs describe. Only Chromium was used, not Firefox or Safari. The securityheaders.com grade will not change, since it reads only headers.
**For you to check:** After deploying, open knightbook.xyz with dev tools: no CSP errors in the console, and the Umami dashboard still counts the visit. Turn on Enforce HTTPS in the repository's Pages settings.
