# Write the troubleshooting and support guide

## Intended outcome
`/docs/troubleshooting/` helps users recover from common problems without risking their project data, and shows them how to ask for help safely.

## Acceptance criteria
- Covers each symptom in the spec §7 table: installer will not run, MCP runtime missing, MCP not connected, wrong project appears, documents or changes missing, write conflict or malformed record, unexpected Done or review state, behaviour changed after an update.
- Each entry gives the first checks, the expected result, the next safe action, and when to contact support.
- Links to the chosen support destination and says what to include (app version, OS and architecture, reproduction steps, redacted errors) and what never to post (whole private projects, credentials, unredacted client logs).
- Other guides link to the matching entry here at each likely failure point.

## Notes
Spec §7 "Troubleshooting and support". Error text quoted in the guide must match what the release actually shows.

## Test plan (2026-10-21)
- Covers each symptom: `apps/website/src/docs/docs.test.ts` builds the real site and requires an anchored heading on /docs/troubleshooting/ for each of the eight symptoms and for asking for help, and that the guide is published rather than a draft.
- Each entry gives first checks, expected result, next safe action and when to contact support: the same test requires all four labels inside every symptom section, cut from its heading to the next. Whether the advice under them is right is settled by reading.
- Support destination: the test requires links to the bug-report form and to private vulnerability reporting, and the include and never-post items (version, OS and processor, steps, redacted errors; whole private projects, credentials, unredacted client logs). The wording is settled by reading.
- Other guides link here: the test collects every link to `/docs/troubleshooting/#…` in the other published guides, requires at least one from each, and fails on a fragment that names no heading on the page (the build's link check ignores fragments).
- Error text matches the release: settled by reading against the app source; seeing it in an installed build is manual.

## Handoff (2026-10-21)

### What changed
- `apps/website/src/content/docs/troubleshooting.md` is now a published guide, written for 0.1.1. It has one section per symptom in the landing-page proposal §7, and each section has **First checks**, **What you should see**, **Next safe step** and **When to ask for help**. It ends with **Asking for help**, which links the bug report form, the idea form and private vulnerability reporting, and lists what to include and what never to post.
- The two published guides link to the matching entry at each failure point: five links in Projects and documents and two in Tickets, verification and review. The installation and AI-connection drafts also link to their entries.
- New `apps/website/src/docs/troubleshooting.test.ts`. The test plan above named `docs.test.ts`, but the checks live here instead, and `docs.test.ts` only lowers its draft count from 4 to 3.

### How it was checked
- `pnpm check` passes. On the first full run, `discovery.test.ts` › "stops the real build when two guides share a title" hit the default 5 s timeout. It passed alone and on the next full run.
- The site accessibility suite was run with the container's Chromium (`REQUIRE_WEBSITE_BROWSER=1`): 37/37 passed.
- Mutation checks:
  - Renaming one section's **Next safe step** label fails that section's test.
  - A link to a fragment that does not exist fails the link test.
- Looked at the built page at 375 px and 1400 px. Neither width scrolls sideways.
- Verifier: 4 covered, 0 weakly covered, 0 uncovered. The note on error text is not a code criterion.
- The verifier also compared every quoted UI and MCP string against the source and found no mismatches. Following its notes, I described **Refresh from disk** as the refresh button, quoting its tooltip, because the button shows an icon and not those words. I also added **MCP status unknown**.

### Not verified
- The quoted strings were matched against the source on `main`, not seen in an installed 0.1.1 build. The guide's advice about installers, checksums and OS warnings was not tried on a real install on any OS.
- AppImage is not a released target, so its **MCP runtime not copied** state is not covered.
- PR #2 (app version in Settings) also edits this file, so whichever PR merges second needs a conflict resolved. Until a release shows the version in the app, this guide says to read the version from the installer's file name.
