# Make the AI setup dialog test wait long enough on a slow runner

## Intended outcome
`apps/desktop/src/renderer/mcp/AiSetup.test.tsx` passes on a cold, slow CI runner as reliably as on a developer machine, without hiding a real failure.

## Acceptance criteria
- The cause of the timeout below is identified (slow first render on a cold runner, or something the test or the footer actually waits on) and stated.
- The fix addresses that cause, for example a longer wait on the first lookup in the file, rather than retrying the test.
- The test still fails when the "MCP not connected" button really does not appear.

## Notes
Seen 2026-09-29 in manual CI run 36589398153, attempt 1, `Check (windows-latest)`: "shows connection and skill installation as separate steps" failed after 2756 ms with `Unable to find role="button" and name /MCP not connected/i` (`openSetup`, line 31, `findByRole` with the default 1 s wait). The re-run (attempt 2) passed on the same commit, and the test passed on Windows in run 36585090697 and locally. Nothing in that commit touched the renderer. One occurrence so far; D-031 rules out automatic retries because they would hide intermittent failures like this.

## Handoff
**Cause (inferred, not reproduced):** the "MCP not connected" button only exists after three asynchronous steps: the project loads, the footer mounts, and its first `mcpStatus` read returns. The first role query in a test file also walks a cold DOM. Measured locally on Windows: render about 35 ms, status text about 65 ms after render, first `getByRole` 76 to 96 ms cold against about 10 ms warm. The failing CI dump showed the header already rendered (project loaded) when the 1 s default expired, so the time went on the footer's first reading and the cold query on a shared runner with test files in parallel workers. That is an inference from the dump; the slowness was not reproduced here.
**What changed:** `test-fixtures.tsx` has `findMcpStatusButton()` with a named `FIRST_MCP_READING_MS` of 3 s and a comment giving the cause. It is used by `AiSetup.test.tsx`, `CopyMcpConfig.test.tsx` and `McpFooter.test.tsx` wherever they first look for the status button. It is a longer wait on the one slow lookup, not a retry. It stays under Vitest's 5 s test timeout, so a missing button still fails with the query's own message and DOM dump. (The first version used 5 s; the verifier pointed out that equals the test timeout, so it was lowered.)
**How it was checked:** `pnpm check` passes. New tests in `AiSetup.test.tsx`: a status reply delayed 1.5 s is still found (this would fail with the old 1 s wait); with a connected session the footer is first confirmed to show "MCP connected", then looking for "MCP not connected" rejects with `Unable to find role="button"`. Verifier: 0 covered, 1 weakly covered, 1 uncovered, 1 not a code criterion. Its gaps were then closed as above: the 5 s bound, a test that needs the longer wait, and the footer-rendered check.
**Not verified:** Not re-run on a slow CI runner; whether this stops the flake is shown only by future Windows runs.
**For you to check:** The helper and its comment in `apps/desktop/src/renderer/test/test-fixtures.tsx`, and the two new tests at the top of `AiSetup.test.tsx`.
