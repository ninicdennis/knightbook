# One local MCP connection across enabled projects

## Intended outcome
The user configures Projectspace once in their local AI client. Projects explicitly enabled in the desktop app become available through that connection without adding or editing MCP entries for every project. The AI identifies the intended checkout and targets it explicitly on every operation.

## Acceptance criteria
- Keep the client-launched local stdio transport and bundled Node/server runtime. Generate one installed-app MCP configuration that locates a persistent project-access registry instead of binding the new connection to one --root. No HTTP endpoint, network listener, hosted backend, or always-running service is introduced. Each client may launch its own process using the same configuration and registry; one connection does not promise one OS process globally.
- Add an explicit Allow AI access through MCP setting per project. Explain that this connection can access all enabled projects. Merely opening a folder or remembering it in recent projects does not grant access. Enabling or disabling a project updates availability without requiring a new per-project MCP entry; existing connections observe registry changes on subsequent operations.
- Store the durable registry outside project repositories, separately from the disposable recent-project list. Use safe, validated writes and report registry corruption or write failure rather than silently broadening access or losing grants. Preserve entries until the user removes them; no recent-item eviction policy applies.
- Add projects_list returning an opaque stable checkout identifier, project UUID, name, canonical path, and availability information. Distinguish clones/worktrees even when project UUIDs or names match. Missing/moved folders are explained and never silently rebound to a different checkout.
- Require checkout_id (or an equivalent explicit identifier) on every project-scoped tool in multi-project mode, including document, ticket, review, search, and initialization operations where supported. Resolve paths server-side from the enabled registry. Reject missing, unknown, disabled, or mismatched targets; never fall back to the last-used project or accept an arbitrary filesystem path as authority.
- Keep desktop selection independent from MCP targeting. Concurrent chats, clients, or calls must not share a mutable active-project selector. Echo project identity/path in scoped responses so the caller can verify its target. Update skill/server instructions to list projects, resolve ambiguity with the user, and carry the selected checkout identifier through calls.
- Reuse existing project-boundary checks, per-checkout locking, expected revisions, completion provenance, and user-only Done rules after resolving the target. Validate grants and checkout identity before each operation. Define revocation behavior for already-running operations; revocation must block subsequent operations without interrupting a write in a way that corrupts files.
- Keep the local connection functional when the desktop window is closed. Define initialization explicitly: an enabled existing folder without project records may be reported as uninitialized, but creation still requires explicit user intent and cannot register arbitrary paths through an ordinary tool call.
- Preserve existing --root configurations as a compatibility mode without auto-expanding their scope. Provide a documented migration to the single connection; newly generated setup defaults to one local connection. Retire duplicate client entries only through an explicit user action.
- Update footer status semantics: a client connected to a multi-project server is not proof that it is currently working on every enabled project. Distinguish overall connection availability, project access, and any observed project activity; switching the visible project cannot redirect calls.
- Verify two projects and two concurrent clients/chats; same names and cloned UUIDs; wrong/missing identifiers; project switching mid-call; enable/revoke while connected; stale revisions; missing/moved folders; corrupt registry; restart with GUI closed; and preservation of legacy --root isolation. Confirm a new project can be enabled and read with no change to the client's MCP configuration.
- Update the technical design, README, setup instructions, and bundled skill to describe the new access model and the fact that enabling multiple projects broadens that client's available project scope.

## Research and design rationale
Research date: 2026-09-19. User selected one local connection, not a shared HTTP endpoint. Multi-project routing does not require a transport change. MCP stdio launches a local server process per client; the program and registry can be shared while process instances remain independent: https://modelcontextprotocol.io/specification/2025-11-25/basic/transports.

MCP Roots are informational rather than an enforced access-control boundary, so they must not replace the registry or authorize arbitrary paths: https://modelcontextprotocol.io/specification/2026-07-28/client/roots. Do not depend on client Roots support for this feature.

Observed current implementation: packages/mcp/src/root.ts requires one --root; tools.ts and document-tools.ts bind operations to that root. apps/desktop/src/main/app-state.ts stores at most 20 recent projects as disposable app state and suppresses persistence failures; that store is unsuitable as the durable access registry. Existing core operations already enforce canonical project boundaries and revisions and should be reused. The root-bound design in technical-design section 4 will need explicit revision.

Proposed interfaces: projects_list(); ticket_list({ checkout_id }); ticket_read({ checkout_id, id }). A registry launch flag such as --registry is a proposal, not an existing supported option. Choose a stable installed location and verify packaged operation without source files.

Related tickets: 9f4177e9-cb15-430d-892b-ca1640a48aec (bundled skill and guided AI setup), and 1caa7fd2-e877-42b1-ad8a-0c5689825110 (MCP footer status). Coordinate their setup and status wording with this model. Avoid bundling unrelated board/search/archive changes.

This ticket captures approved product direction and implementation acceptance criteria. Implementation has not started.

## Handoff
**What changed:** (uncommitted, on `main`)
- **Access registry** (`packages/core/src/access-registry.ts`, `checkout-access.ts`): a JSON grant list in the app's user-data folder (`mcp-access.json`), separate from recent projects. Entries hold an opaque random `checkout_id`, canonical path, project UUID and name. Locked, temp-file writes. Missing file = nothing enabled; corrupt/invalid/unknown-version/duplicate = `registry_unreadable`, grants nothing, never overwritten. Every call re-reads it and checks the folder still exists at the same canonical path with the same project UUID (`checkout_not_enabled`, `checkout_unavailable`, `checkout_mismatch`). No fallback, no path-as-authority, no rebinding a moved folder to a clone.
- **MCP server** (`packages/mcp`): new `--registry <file>` mode beside the unchanged `--root` mode (both at once is refused). Adds `projects_list`; every project tool requires `checkout_id` and echoes a `project` block (checkout id, project id, name, path). No `project_initialize` in shared mode. No server-side current project. Separate connect instructions per mode. `root.ts` replaced by `launch-mode.ts`; tools take a `ProjectScope` (`scope.ts`).
- **Status**: shared servers heartbeat beside the registry (`mcp-runtime/sessions/`), and record per-project activity in `.projectspace/runtime/activity/` (Git-ignored). Footer states: MCP connected (project-bound only), **MCP available** (shared client + project allowed, with "last worked on this project…" reported separately), **MCP not allowed here**, **MCP access unknown** (registry unreadable).
- **Desktop**: "Allow AI access through MCP" switch in the MCP panel with the broadened-scope warning; disabling works even if project records are broken. Copy MCP configuration now yields the single `--registry` config (setup screen too).
- **Docs**: technical design §4 rewritten (launch, registry, targeting, revocation, initialization, status, compatibility), README (setup, scope warning, migration from per-project entries, status table), bundled skill (two connection kinds, choosing a project, refusals), packaging findings entry.

**Not verified:**
- No packaged installer was rebuilt (`pnpm pack:dir` not run), so `apps/desktop/release/` still holds the older server; the real Electron window was not launched against a real registry in `%APPDATA%\Knightbook`.
- No real AI client has used the new configuration.
- macOS/Linux not run. Path comparison is case-insensitive on Windows and macOS, case-sensitive on Linux; a case-sensitive macOS volume is not handled specially.
- Two chats inside one client that share one process were not simulated separately; the design holds no per-process target, and two separate processes were tested.

**For you to check:**
1. Run `pnpm check`, then `pnpm pack:dir` and open the packaged app.
2. Open a project → MCP indicator → turn on **Allow AI access through MCP**, and read the warning text.
3. Copy the MCP configuration into a client (it should contain `--registry …\Knightbook\mcp-access.json`, no project path). Ask it to call `projects_list`, then read a ticket with the returned `checkout_id`.
4. Enable a second project in the app without touching the client config and confirm the client can reach it on its next call; turn it off and confirm the next call is refused.
5. Confirm the footer reads "MCP available" (not "connected") and that an existing `--root` entry still works on its own.
